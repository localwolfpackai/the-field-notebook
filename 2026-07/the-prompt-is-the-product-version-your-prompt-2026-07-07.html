The prompt is the product — version, diff, and roll back the one file that runs your whole app.

Last volume you knocked the paint off the windows and watched your live app. So you caught a bad answer — now what? You open the code, scroll to a 400-line string, tweak a sentence, and redeploy. No version. No diff. No undo. You just edited the single most important file in your product by feel. This volume fixes that: ten moves to treat your prompt like code — pull it out, give it a version number, diff two versions, run both against your evals (Vol. 24) before you pick a winner, ship it behind a flag, and roll back in one line when the metric moves the wrong way. Run the A/B bench below.

There’s a file in your app that decides every single answer it gives, and for most beginners it lives as a giant backtick string wedged between two functions, edited live, tweaked by vibe, and shipped with a commit message that says fix prompt. It is the highest-leverage code you own and you treat it worse than a CSS margin.

Here’s how the trap springs. You catch a bad answer from Vol. 34. You open the prompt, add a line — “always confirm the order number before cancelling” — and redeploy. It fixes that one case. But you have no idea what it did to the other forty things the prompt was already handling well. A week later a different answer gets worse and you can’t even tell which edit caused it, because there was never a version to compare against. This is prompt-whack-a-mole, and every non-dev builder plays it.

The escape is boring and it works: treat the prompt like code. Code got version control, diffs, tests, and one-command rollback for exactly this reason — so a change is a thing you can see, measure, and undo. The ten moves below give your prompt all four. By the end, “let me try a new prompt” stops meaning “pray and redeploy” and starts meaning “score the challenger against the champion, ship the winner behind a flag, and keep the receipt.”

01

See the trap — the file you edit by feel. read

Every AI feature has a control surface, and it’s the system prompt. Change one sentence in it and the behaviour of the whole app shifts — tone, accuracy, what it refuses, how long the answers run. That is an enormous amount of leverage sitting inside one string. And here’s the quiet disaster: because it lives inside your code as a big backtick blob, you edit it the same careless way you’d fix a typo, with none of the safety rails you’d demand for anything else this important.

Dray’s AI-engineer framing cuts to it: a prompt is a dependency, not a comment. Your app’s output depends on it the way it depends on a library version. You’d never bump a library from v2 to v3 in production with no changelog, no diff, and no way back — but that’s exactly what “let me just tweak the prompt” does. This whole volume is about giving the most important dependency in your app the same respect as the least important one in your package.json.

buried

A prompt edited by feel — one string, no history. It lives between two functions, gets tweaked live, and ships as fix prompt. When an answer gets worse you can’t see what changed, can’t compare it to last week, and can’t roll back. Every edit is a coin flip you can’t undo.

versioned

A prompt treated like code — a file with a number. v2 is running, v3 is a diff you can read, both get scored against your evals, and the loser never ships. When something breaks, you roll back to v2 in one line. The prompt is now a decision you can see and reverse — not a mystery.

02

Pull the prompt out of the code. setup

The first move is the one that unlocks all the others, and it takes five minutes: get the prompt out of the function body and into its own file. A string wedged in api/chat.js can’t be diffed cleanly, can’t be swapped without a redeploy of logic, and can’t be pointed at by a version number. A standalone file can. Ashi’s modular instinct: separate the thing that changes often (the words) from the thing that changes rarely (the plumbing).

prompts/support.js — the words live here now, not in the route
// prompts/support.js — one export per version, plain text
export const SUPPORT_V2 = `You are Acme's support assistant.
Answer only from the policies provided. If you don't know,
say so — never invent a policy. Keep replies concise.`;

// api/chat.js — the plumbing imports the words
import { SUPPORT_V2 } from '../prompts/support.js';

const reply = await client.messages.create({
  model:  'claude-sonnet-5',
  system: SUPPORT_V2,                 // ← swappable, not buried
  messages: [{ role: 'user', content: userText }],
});
try it
Bonus you get for free: a stable system prompt in its own constant is the exact cacheable prefix from Vol. 30. Pull it out once and you’ve set up versioning and teed up a ~90%-off cache marker on the same line. Two wins, one refactor.
03

Give it a version number. setup

Now name your versions on purpose. Not promptFinal, promptFinal2, promptFinalREAL — a real integer that goes up by one every time the words change. A registry object with a single ACTIVE pointer means switching which prompt runs is a one-line change, and everything downstream (logs, evals, rollback) can refer to a version by name instead of by “the one I think I deployed on Tuesday.”

prompts/support.js — a registry with one active pointer
export const PROMPTS = {
  'v1': `...the original...`,
  'v2': `...concise, won't invent policies...`,   // current champion
  'v3': `...v2 + always confirm order # before cancel...`,
};

export const ACTIVE = 'v2';   // ← the ONLY line you change to switch prompts

// api/chat.js
import { PROMPTS, ACTIVE } from '../prompts/support.js';
const system = PROMPTS[ACTIVE];   // resolve the active version at request time
heads up
Version the words, not the whole call. Model name, temperature, and max-tokens are their own knobs (Vol. 25) — keep them separate so a prompt diff is only a prompt diff. If you change the model and the prompt in the same version, you’ll never know which one moved the metric.
04

Log which version answered. setup

Remember the one structured log line from Vol. 34? Add one field to it: promptVersion. This is the hinge that connects everything — the day an answer goes bad, the trace tells you which prompt version produced it. Without this field, a regression is a mystery; with it, it’s a lookup. Cal’s notebook habit: write down which experiment you were running, or you can’t trust the result.

api/chat.js — stamp the version into the trace from Vol. 34
console.log(JSON.stringify({
  rid,                              // the request ID from Vol. 34
  promptVersion: ACTIVE,            // ← the one field that ties a bad answer to a prompt
  input:  userText.slice(0, 400),
  output: reply.content[0].text.slice(0, 400),
  tokens: reply.usage.input_tokens + reply.usage.output_tokens,
}));
// now "every 👎 since Tuesday" and "every 👎 on v3" are the same one-line filter
try it
Combine this with the Vol. 34 thumbs. Filter your feedback by promptVersion and you get the single most useful chart in the whole stack: 👎-rate per prompt version. If v3’s thumbs-down rate is higher than v2’s, you have proof the “improvement” made things worse — before you have to argue about it.
05

Diff two versions like a PR. diff

Because the prompt is now a file, git diff just works — and a prompt diff is one of the most clarifying things you can look at. It forces the vague “I made it better” into a concrete “I added this line and removed that one.” Half the time you’ll catch a silent regression you didn’t mean to make: you added the cancel rule and accidentally deleted “be concise,” and now every answer is a paragraph longer.

git diff prompts/support.js — v2 → v3, read it like a code review
  You are Acme's support assistant.
  Answer only from the policies provided. If you don't
  know, say so — never invent a policy.
- Keep replies concise.                        // ← wait, why did this leave?
+ Before cancelling an order, always confirm the
+ order number back to the user first.          // ← the intended change
try it
Make prompt changes a real pull request, even solo. Open a branch, edit the version, and read the diff before you merge. It takes two minutes and it’s the cheapest quality gate you own — you review the words that run your product with the same eyes you’d give a database migration.
06

Score the challenger against evals. test

Here’s where Vol. 24 pays off. You built a little eval harness — golden cases, a judge, a pass bar. Now point it at both prompt versions and let it settle the argument with a number. Run v2 through the ten cases, run v3 through the same ten, compare the scores. “Is v3 better?” stops being a taste debate and becomes v3: 9/10 vs v2: 8/10 — or, just as valuable, v3: 7/10, which tells you the improvement quietly broke two things.

eval/ab.js — same golden cases, both prompts, one scoreboard
import { PROMPTS } from '../prompts/support.js';
import { GOLDEN, judge } from './harness.js';   // from Vol. 24

async function score(version) {
  let pass = 0;
  for (const c of GOLDEN) {
    const out = await run(PROMPTS[version], c.input);
    if (await judge(out, c.expect)) pass++;   // same judge for both — fair fight
  }
  return pass;
}

console.log('v2', await score('v2'));   // v2 8
console.log('v3', await score('v3'));   // v3 9  ← ship it
heads up
A one-case win is noise. Models are non-deterministic (Vol. 34), so run each version a few times and compare the totals, not a single lucky pass. And make sure a case you just fixed by hand is in the golden set — otherwise you’re grading v3 on a test that doesn’t include the thing you changed it for.
07

A/B it on real traffic. test

Evals catch the obvious wins and the obvious breaks, but the golden set is small and the real world is weird (that’s the whole reason Vol. 34 exists). So for a change you’re unsure about, let real traffic vote: send a slice of users to v3, keep the rest on v2, and compare the thumbs-down rate. Bailey’s prototyping move — it’s a coin flip on the rid, five lines, no experimentation platform required.

api/chat.js — 10% of traffic gets the challenger, logged by version
// deterministic split so the same user stays on one version
const onChallenger = hash(userId) % 10 === 0;   // ~10% see v3
const version = onChallenger ? 'v3' : 'v2';

const reply = await client.messages.create({
  system: PROMPTS[version],
  messages: [{ role: 'user', content: userText }],
});
console.log(JSON.stringify({ rid, promptVersion: version }));  // compare 👎-rate per version later
try it
Start the challenger slice small — 5-10%. If v3 has a problem your evals missed, only a handful of users hit it, and your per-version 👎-rate (move #4) surfaces it fast. This is a canary, not a coin toss: you’re risking a sliver of traffic to buy proof, then rolling the winner out wide.
08

Ship the winner behind a flag. ship

When v3 wins — better eval score, lower 👎-rate on the canary — promote it. But do it through a flag, not a code edit, so the switch is config, not a deploy. An environment variable that sets ACTIVE means promoting v3 (or reverting to v2) is a dashboard toggle that takes effect on the next request, with no build, no wait, and — crucially — the ability to flip it back the second something looks wrong.

the active version is config, so promoting = flipping an env var
// prompts/support.js — active version comes from the environment
export const ACTIVE = process.env.PROMPT_VERSION ?? 'v2';   // default = last known-good

// promote v3 with zero code change:
$ vercel env add PROMPT_VERSION v3 production
$ vercel env pull        # takes effect next request — no rebuild of logic
heads up
The flag defaulting to 'v2' matters more than it looks: if the env var is ever missing, empty, or fat-fingered, you fall back to the last known-good version, not to a crash or an undefined prompt. A safe default is the difference between “a config typo” and “the bot answered with an empty system prompt for an hour.”
09

Roll back in one line. ship

This is the move that makes all the risk of shipping a new prompt disappear. Because “which prompt is live” is one config value, and every old version still sits in the registry, undoing a bad prompt is instant — not “revert the commit, wait for the build, redeploy, pray.” The moment your per-version 👎-rate spikes or an eval alarm from Vol. 34 fires, you flip the flag back and the whole app returns to the last version you trusted, on the very next request.

v3 is misbehaving in the wild — undo it right now
$ vercel env rm PROMPT_VERSION production   # or set it back to v2
✓ removed. ACTIVE falls back to 'v2' — the known-good champion

# next request is served by v2 again. no rebuild, no scrolling
# through a 400-line string trying to remember what you changed.
try it
Never delete an old version. Keep v1, v2, v3 all in the registry forever — they cost nothing and each one is a safe harbour you can jump back to. A prompt you can roll back to in one line is a prompt you can afford to be brave with. That’s the whole trade: cheap undo buys bold iteration.
10

Keep a changelog the model can’t. diff

The last move is the one future-you will thank you for. A version number tells you that the prompt changed; a one-line changelog tells you why. Three months from now you’ll stare at v3 and have no memory of what problem it solved — unless you left a note. Tie each version to the eval or the trace that justified it, and your prompt history becomes a story you can actually read: every line earned its place because a real answer went wrong.

prompts/CHANGELOG.md — one line per version, tied to its reason
# Support prompt — changelog

## v3 — 2026-07-07
+ Confirm order # before cancelling.
  why: trace #c7d — bot cancelled the wrong order (Vol. 34).
  eval: 9/10 (was 8/10). canary 👎-rate 2% vs v2 3%. promoted.

## v2 — 2026-06-21
+ Never invent a policy; say "I don't know".
  why: the "ships to Canada" hallucination. still the fallback.
try it
This closes the loop that started in Vol. 34. A bad answer became a trace, the trace became an eval case, the eval case justified a prompt version, and the changelog remembers all of it. Observe → catch → eval → new prompt version → measured → shipped or rolled back. That’s not prompt-whacking anymore — that’s a product with a memory.

When is a prompt change actually “a new version”? read

Not every keystroke needs a version bump — that way lies a registry with forty entries and no signal. The line is simple: if it could change behaviour a user would notice, it’s a version. If it’s a typo fix in a comment nobody reads, it isn’t. Here’s the quick call.

The changeNew version?Why
Added / removed a ruleyesChanges what it does — must be scored against evals before it ships.
Reworded a rule for clarityyesWording is the behaviour with an LLM — a subtle reword can move the metric.
Changed tone / personayesUsers feel tone immediately; A/B it (move #7) before going wide.
Fixed a typo in a commentnoNo behavioural surface — just commit it.
Bumped the model or temperatureno*Real change, but it’s a different knob (Vol. 25) — version it separately so the diff stays clean.

when in doubt, bump the number — versions are free, mystery regressions aren’t.
