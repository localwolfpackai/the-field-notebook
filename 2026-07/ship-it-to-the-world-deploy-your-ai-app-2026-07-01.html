Ship it to the world — put your AI app on the internet without leaking the key or waking up to a $900 bill.

Everything in this notebook so far builds. This one ships. Your app runs on localhost — great. The moment it’s public, three things can go wrong: your API key is sitting in the browser for anyone to steal, a bored stranger loops your endpoint and runs up a bill, and the first real spike falls over. Ten moves to close all three — move the key server-side, rate-limit the door, cap the spend, add a timeout, and deploy in one command. Flip the guards below and watch the deploy gate go green.

There’s a specific kind of quiet panic that hits the first time you paste your working AI app onto a real URL and text it to a friend. It works — and then you realize you have no idea what happens next. Is the key exposed? Can they spam it? What stops the bill? For most people the honest answer is “nothing,” and they find out the expensive way.

Here’s the reframe that makes this easy: going live is not a bigger version of running locally — it’s a different job. Locally, you are the only user and you trust yourself. Publicly, every request is from a stranger, and a few of those strangers are bots. The whole job of shipping is putting a small number of guards between those strangers and your wallet. It’s not glamorous plumbing. It’s four boring guards, and every one of them is a two-minute change.

Ten moves below, in the order you’d actually do them: move the key off the browser, wrap it in a serverless route, rate-limit the door, cap the daily spend, add a timeout, deploy in one command, then watch it. None of it requires being a “real” backend engineer. It requires a checklist — which is what this is.

01

See the danger — the key is in the browser. read

Almost every “my first AI app” makes the same call: the browser hits the model API directly, with the key in the frontend code. On localhost that’s invisible and harmless. The second it’s deployed, that key is shipped to every visitor — it’s in the Network tab, in the bundle, one right-click away. Someone copies it, points it at their own script, and your key is now funding their side project until you notice the bill.

This isn’t a hypothetical you can defer. A leaked key gets scraped by bots within hours — there are literally crawlers watching public deploys for exactly this. The fix is the spine of everything below: the browser never sees the key. The browser talks to your server; your server talks to the model.

exposed

The browser calls the model — the key ships to every visitor. fetch(anthropic, { headers: { key }}) in frontend code = the secret is in the bundle. Free to steal, impossible to un-ship. This is the default, and it’s the one thing you must never deploy.

shipped

The browser calls your server — the key lives only on the server. Browser → your /api/chat route → the model. The stranger can see your route all day; the key stays behind it. This one move removes ~80% of the risk.

02

Move the call to a serverless route. setup

You don’t need a server you rent and babysit. A serverless function is one file that runs on demand — a folder called api/ with a chat.js in it is a working backend on Vercel, Netlify, and Cloudflare. Ashi’s modular habit applies here: this route is one small, self-contained piece that does exactly one thing — take a message, call the model, return the answer.

api/chat.js — the whole backend, one file
import Anthropic from '@anthropic-ai/sdk';

// the key is read from the environment — never hard-coded
const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

export default async function handler(req, res) {
  if (req.method !== 'POST') return res.status(405).end();

  const msg = await client.messages.create({
    model: 'claude-sonnet-5',
    max_tokens: 1024,
    messages: [{ role: 'user', content: req.body.text }],
  });

  res.json({ reply: msg.content[0].text });
}
try it
The frontend change is tiny: swap the direct model call for fetch('/api/chat', { method: 'POST', body: JSON.stringify({ text }) }). Same app, same UI — the only difference is the request now goes to your door first. Hand this whole move to a coding agent and it’s a five-minute refactor.
03

Put the key in an env var — never in a file you commit. secure

Now the key lives on the server — but how it gets there matters. The rule is absolute: the key is an environment variable, and it is never written into any file that goes to git. The classic disaster is hard-coding it “just for now,” committing, and pushing — git remembers forever, even after you delete the line. Bots scan public repos for exactly this pattern.

.env.local (dev) + .gitignore — keep the secret out of git
# .env.local — used only on your machine, LISTED in .gitignore
ANTHROPIC_API_KEY=sk-ant-•••••••••••••••••••

# .gitignore — this line is not optional
.env*

# sanity check before you ever commit:
$ git status --ignored | grep env
  .env.local   (ignored ✓ — good, it will NOT be pushed)
heads up
If you already committed a key once, deleting it isn’t enough — it’s in the git history. Rotate it. Go to the console, revoke the old key, generate a new one. Treat any key that ever touched a commit as burned. This is the one panic where Vol. 07’s undo book doesn’t save you — the fix is a new key, not a rewind.
04

Rate-limit the door. guard

The key is safe now — but the route is wide open. Anyone can hit /api/chat in a loop, and each hit costs you money. A rate limit is the bouncer: N requests per minute per visitor, and the (N+1)th gets a polite 429 instead of a model call. Dray’s AI-engineer framing: you’re not calling the model on every request — you’re calling it on every allowed request, and you decide what “allowed” means.

api/chat.js — a small in-memory limiter (per IP)
const hits = new Map();  // ip → [timestamps]
const LIMIT = 10, WINDOW = 60_000;  // 10 / minute

function allowed(ip, now) {
  const recent = (hits.get(ip) || []).filter(t => now - t < WINDOW);
  recent.push(now);
  hits.set(ip, recent);
  return recent.length <= LIMIT;
}

// inside the handler, before the model call:
const ip = req.headers['x-forwarded-for'] || 'anon';
if (!allowed(ip, Date.now()))
  return res.status(429).json({ error: 'slow down' });
try it
The in-memory version resets whenever the function goes cold — fine for a demo or a small launch. For anything real, back it with a shared store (Upstash Redis has a drop-in @upstash/ratelimit that’s a few lines). Start with the Map, upgrade when you have actual traffic to protect.
05

Cap the spend before it caps you. guard

Rate-limiting slows one attacker. A spend cap is the circuit breaker for everything else — a bug that loops, a launch that goes viral, ten users who each hit the limit. It’s the same instinct as the budget in Vol. 25 (The Two Dials), moved up to the account level. Two layers: a hard limit in the console (belt) and a rough per-day counter in your route (suspenders).

two layers of spend protection
# LAYER 1 — the account belt (do this first, in the console):
# Anthropic Console → Billing → set a monthly usage limit + alerts.
# This is the hard stop nothing in your code can override.

# LAYER 2 — a rough in-app counter (suspenders):
let spentToday = 0, day = new Date().getDate();
const CAP = 5.00;  # dollars/day for this route

# after each call, add the est. cost (tokens × price):
spentToday += estimateCost(msg.usage);
if (spentToday > CAP)
  return res.status(503).json({ error: 'daily budget reached' });
heads up
The console limit is the one that actually saves you — set it today, before you deploy anything. The in-app counter is approximate and resets on cold starts; treat it as a courtesy brake, not the real one. Belt first, suspenders second. Never ship with neither.
06

Add a timeout and a max-tokens ceiling. guard

The last guard is about a single request going wrong instead of a stranger being malicious. A prompt can trigger a very long generation; a network hiccup can leave a call hanging. Without a timeout and a max-tokens ceiling, one bad request can hold a function open (you pay for the wall-clock) and stream out far more than you meant to (you pay for the tokens). Both are one line.

two ceilings on a single request
const msg = await client.messages.create(
  {
    model: 'claude-sonnet-5',
    max_tokens: 1024,        # the token ceiling — can't overrun
    messages: [{ role: 'user', content: clean(req.body.text) }],
  },
  { timeout: 20_000 }         # 20s wall-clock — no hanging call
);

# and a length ceiling on INPUT too — trim what users can send:
function clean(t) { return String(t || '').slice(0, 4000); }
try it
Trimming the input is the quiet one people skip. A user (or a bot) can paste a novel into your text box; without a .slice() you’re paying to send all of it to the model. Cap what comes in and what goes out — both ends of the request have a ceiling.
07

Deploy in one command. ship

Here’s the part that feels like it should be hard and isn’t. With the guards in place, going live is a single command — Bailey’s whole prototyping ethos is that the distance from “runs locally” to “has a URL” should be seconds, not a DevOps project. Vercel, Netlify, and Cloudflare Pages all detect the framework, build it, and hand you a live HTTPS URL.

localhost → the internet, one command
$ npm i -g vercel
$ vercel
? Set up and deploy? yes
? Which scope?          your-name
? Link to existing?     no
🔗  Building...  api/chat.js → serverless function
✅  Production: https://your-app.vercel.app  [live]

# push a change later? just run it again:
$ vercel --prod
try it
Connect the repo to Vercel once and every git push auto-deploys — which is the real reason “we aren’t pushing to git yet, but it’s coming” matters. The moment this notebook is a repo, shipping a new entry becomes: commit, push, done. The deploy pipeline is waiting for the git step.
08

Wire the secret in the dashboard, not the repo. secure

Your .env.local stays on your machine (Move 3) — so the deployed function has no key unless you give it one, in the right place. Every host has an Environment Variables panel in the project dashboard. That’s where the production key goes. It’s encrypted, it’s never in the code, and you can rotate it without touching a line.

set the production secret — CLI or dashboard
# option A — one command:
$ vercel env add ANTHROPIC_API_KEY production
? Value:  sk-ant-••••••••••••  (paste; hidden)
✅  Added — encrypted, injected at runtime, not in the repo

# option B — dashboard:
# Project → Settings → Environment Variables → Add
#   Name: ANTHROPIC_API_KEY   Value: sk-ant-...   Env: Production

$ vercel --prod   # redeploy so the function picks it up
heads up
Setting the env var does not apply to the already-live build — you have to redeploy after adding it, or the function still has no key and every call 500s. First-deploy checklist: add the secret, then ship. If your live app throws auth errors, this is almost always why.
09

Watch it — logs, spend, and a one-line status ping. ship

Shipped isn’t done — shipped is when you start watching. Cal’s open-notebook habit is the right one here: keep the logs open for the first day like a diary and actually read what real traffic does to your assumptions. Three things to watch, all free: the function logs, the billing dashboard, and a dead-simple health endpoint.

the three things you watch on day one
# 1 — live function logs (tail them like a heartbeat):
$ vercel logs your-app.vercel.app --follow
POST /api/chat  200  1.2s   (real user ✓)
POST /api/chat  429  0.0s   (rate limit held ✓)

# 2 — spend: Anthropic Console → Usage. check it once a day.

# 3 — a status ping anyone can hit, no key, no cost:
// api/health.js
export default (req, res) => res.json({ ok: true, ts: Date.now() });
try it
The 429s in your logs are good news — that’s a guard doing its job, logged in real time. The first time you see one fire against actual traffic instead of your own test, that abstract “rate limit” becomes a real thing you built that’s protecting a real wallet. That’s the moment it stops being a tutorial.
