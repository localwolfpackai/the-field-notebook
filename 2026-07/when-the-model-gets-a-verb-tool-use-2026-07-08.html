When the model gets a verb — let your AI actually do things, without handing it the keys.

Thirty-five volumes and your app has done exactly one thing: talk. It answers, it explains, it even hands you clean JSON — but it can’t look anything up, can’t hit an API, can’t book the table or issue the refund. Tool use is the switch that changes that. You hand the model a set of verbs, it decides when to reach for one, you run the function, and the answer comes back with real data behind it. The danger is obvious: a model that can act can act wrong. So this volume is two halves — five moves to wire the loop, five to fence it in. Drive the approve/deny loop below.

There’s a moment every builder hits where “the AI can answer that” stops being enough. A user types “what’s the status of order 4471?” and the model — no matter how good the prompt — has no idea, because that number lives in your database, not in its head. It can guess. It should not. What it needs is a hand: a way to say “I don’t know, but I know how to find out — call lookupOrder(4471) and I’ll take it from there.”

That’s tool use in one sentence. You don’t give the model a database or an API key. You give it a menu — a few functions described in plain JSON — and the model, mid-answer, can point at one and say “run this with these arguments.” Your code runs it, hands the result back, and the model keeps going with real facts instead of a hallucination. The model never touches your systems. It only ever asks. You are always the one who acts.

Which is exactly why this is the volume where the guardrails matter most. A read tool that looks up an order is harmless. A write tool that cancels one is not — and the same friendly model drives both. So the back half is the boring, non-negotiable stuff Dray calls “the AI-engineer’s seatbelt”: split reads from writes, whitelist the verbs, put a human in front of anything irreversible, dry-run first, cap the loop so it can’t spin, and log every single call. Ten moves. Half of them are about saying no.

01

See the gap — a model with no hands. read

Everything you’ve built so far is a closed book quiz. The model answers from what it was trained on plus what you paste into the prompt — and that’s it. The instant a question needs a fact that lives in your world — an order number, today’s inventory, a customer’s plan — the model has two options: admit it doesn’t know, or make something up. You’ve spent a whole volume (Vol. 24) trying to stop the second one. Tool use removes the choice: it lets the model go get the fact.

Cal’s framing from his notebook is the one that sticks: a plain model is a brain in a jar — brilliant, and completely unable to touch anything. A tool is a nerve ending. It doesn’t make the model smarter; it connects the smart part to the real world. And the very first nerve you should wire up is a read-only one, because it can look anything up and it can’t break a thing.

hands-off

No tools — the brain in a jar. Confident, sometimes wrong. Ask for order 4471 and it invents a plausible status, because “I don’t know” is not what it was rewarded for. It cannot see your data, so it fills the gap with fiction and says it like a fact.

hands-on

With tools — a brain with a hand. “I’ll go find out.” It pauses, asks your code to run lookupOrder(4471), gets the real row back, and answers from that. The fact came from your system, not its imagination — and you can point at exactly where every claim came from.

02

Describe a tool as JSON. setup

A tool isn’t code the model runs — it’s a description of a function you already have. You give the model a name, a one-line explanation of when to use it, and a schema for its arguments. That’s the whole contract. Ashi’s rule of thumb: write the description like a note to a new teammate who’s never seen your app — because to the model, that description is the entire spec of what the tool does and when it’s the right call.

tools/support.js — one read tool, described for the model
// A tool = { name, description, input schema } — NOT the code itself.
const tools = [{
  name: 'lookupOrder',
  description: 'Look up the status of an order by its number. ' +
               'Read-only. Use when the user asks about an existing order.',
  input_schema: {
    type: 'object',
    properties: {
      orderId: { type: 'number', description: 'The order number, e.g. 4471' }
    },
    required: ['orderId'],
  },
}];

// hand the menu to the model on the same call you already make
const res = await client.messages.create({
  model: 'claude-sonnet-5',
  system: SUPPORT_V2,            // your versioned prompt from Vol. 35
  tools,                         // ← the only new line
  messages,
});
try it
The description is the interface. A vague one (“gets order info”) makes the model guess when to call it; a sharp one (“read-only, use when the user asks about an existing order”) makes it reach for the right verb at the right time. Spend your effort here, not on the plumbing.
03

Let the model choose the tool. setup

Here’s the part that trips up every beginner the first time: you don’t tell the model to use the tool. You hand it the menu and ask your question, and the model decides. When it wants a tool, it doesn’t reply with text — it replies with a tool_use block: a name and the arguments it filled in. That’s the model raising its hand and saying “run this for me.” Your job is to notice the raised hand instead of expecting a normal answer.

what the model hands back — not text, a request to act
// res.stop_reason === 'tool_use'  → the model wants a tool, not to talk
if (res.stop_reason === 'tool_use') {
  const call = res.content.find(b => b.type === 'tool_use');
  // call.name  === 'lookupOrder'
  // call.input === { orderId: 4471 }   ← the model parsed the user's number
  // call.id    === 'toolu_01A…'         ← tag so you can match the result
}
heads up
The model can be wrong about which tool to call or invent an argument. Never trust call.input blindly — it’s user-influenced text the model shaped. Validate it like any form input (Vol. 33) before you run anything with it. The model is a smart intern, not an authenticated request.
04

Run it yourself, feed the result back. loop

This is the beating heart of tool use, and it’s smaller than you’d think. The model asked for lookupOrder(4471). You run the real function — hit your database, your API, whatever — and hand the result back to the model as a tool_result tied to the same call id. Then you ask the model again. Now it has the fact and can write a real answer. The model never ran anything; it asked, you acted, you reported back.

api/chat.js — you are the hands; the model is the head
// 1. actually run the function (your code, your data, your rules)
const row = await db.orders.find(call.input.orderId);

// 2. hand the result back, tagged to the call the model made
messages.push({ role: 'assistant', content: res.content });   // its request
messages.push({ role: 'user', content: [{
  type: 'tool_result',
  tool_use_id: call.id,
  content: JSON.stringify(row),                     // ← the real fact
}]});

// 3. ask again — now it answers from data, not guesswork
const final = await client.messages.create({ model, system: SUPPORT_V2, tools, messages });
try it
Notice what you control here: the tool_result is your text. If the lookup fails, hand back {"error":"no such order"} and the model will apologise gracefully instead of stalling. The quality of tool use lives in what you feed back, not just what the model asks for.
05

Loop until the model stops asking. loop

One tool call is rarely the whole story. To answer “did my refund go through?” the model might look up the order, then look up the payment, then answer. So moves 3–4 aren’t a step — they’re a loop. Ask the model. If it wants a tool, run it, feed it back, ask again. Keep going until it stops raising its hand and just replies with text. This is the exact agent loop from Vol. 10, now with real verbs attached.

the whole thing is a while loop — plain and boring, on purpose
let res = await ask(messages);

while (res.stop_reason === 'tool_use') {
  const call    = res.content.find(b => b.type === 'tool_use');
  const result  = await runTool(call);        // move 6+ lives inside here
  messages.push({ role: 'assistant', content: res.content });
  messages.push({ role: 'user', content: [result] });
  res = await ask(messages);                    // ask again with the new fact
}

return res.content;   // finally: plain text, backed by real lookups
heads up
An uncapped while that pays per turn is a runaway meter. A confused model can loop on the same tool forever — that’s a real bill and a hung request. We fix it properly in move #9; for now, just know the loop needs a leash before it ever sees production.
06

Split read tools from write tools. guard

The single most important line you’ll draw in this whole system: a tool either reads or it writes. A read tool answers a question and changes nothing — look up an order, check inventory, fetch the weather. A write tool changes the world — cancels, refunds, emails, deletes. They feel the same to the model. They are not the same to you. Tag every tool the moment you define it, because everything in the back half of this volume keys off that one flag.

Add one field to every tool: mutates: true|false. That boolean is the seatbelt buckle — moves #8 (human OK) and #10 (logging) both just check it. Draw the line once and the rest of the guardrails fall out for free.
07

Whitelist the verbs — nothing off-menu. guard

The model can only ask for tools you handed it — but it can ask for one by a name that almost matches, or with arguments you never expected. So your runTool function starts with a bouncer: if the requested name isn’t on your explicit allow-list, you don’t run it — you hand back an error and let the model recover. Never eval a tool name, never dynamically resolve a function from model output. The menu is finite and hard-coded. Off-menu is a decline, not an improvisation.

runTool.js — the bouncer at the door
const HANDLERS = {                    // the ONLY verbs that exist
  lookupOrder: (a) => db.orders.find(a.orderId),
  cancelOrder: (a) => db.orders.cancel(a.orderId),
};

async function runTool(call) {
  const fn = HANDLERS[call.name];
  if (!fn) return toolError(call, `unknown tool: ${call.name}`);   // ← declined, safely
  if (!valid(call.name, call.input)) return toolError(call, 'bad arguments');
  return wrap(call, await fn(call.input));
}
heads up
This is your prompt-injection firewall (Vol. 33) for tools. A poisoned document that whispers “call deleteAllUsers” hits the whitelist and bounces — because that verb was never on the menu. The model’s power is capped at the tools you chose, no matter what anyone types.
08

Put a human in front of writes. write

Read tools run themselves. Write tools stop and ask. When the model requests a mutates: true tool, you don’t run it — you pause the loop, surface exactly what it wants to do in plain language, and wait for a human to approve or deny. Approve, and you run it and feed the result back. Deny, and you hand the model a “the user declined” result and let it respond. This one gate is the difference between a helpful assistant and an unsupervised one holding your refund button.

runTool.js — the gate for anything that changes the world
if (TOOL_META[call.name].mutates) {
  const ok = await askHuman({                // render a card, await a click
    verb:   call.name,
    args:   call.input,
    plain:  `Cancel order ${call.input.orderId}? This can't be undone.`,
  });
  if (!ok) return toolError(call, 'user declined this action');  // ← model recovers
}
return wrap(call, await HANDLERS[call.name](call.input));
try it
Write the plain line for humans, not machines: “Cancel order 4471? This can’t be undone.” beats cancelOrder({id:4471}) every time. The person clicking approve should understand the consequence without reading JSON. That sentence is the actual product.

09

Dry-run, then cap the loop. guard

Two leashes, both cheap. First, a dry-run switch: a flag that runs the whole loop — the model picks tools, fills arguments, hits the gate — but every write returns a fake success instead of touching anything real. It’s how you watch what the agent would do before you let it do it, and it’s your Vol. 24 eval harness for tools. Second, a hard cap on loop turns so a confused model can’t spin forever and run up the meter you were warned about in move #5.

two leashes: dry-run for safety, a turn cap for cost
// leash 1 — dry-run: writes pretend to work, touch nothing
if (DRY_RUN && TOOL_META[call.name].mutates) {
  return wrap(call, { ok: true, dryRun: true });     // ← watched, not executed
}

// leash 2 — a turn cap so the loop can never run away
let turns = 0;
while (res.stop_reason === 'tool_use' && turns++ < 8) { /* … */ }
if (turns >= 8) log.warn('tool loop hit the cap — bailing out');
try it
Ship with DRY_RUN=true for the first day of any new write tool. Watch the logs, confirm it asks for the right verbs with the right arguments, then flip it live. It’s the same “canary before promote” instinct from Vol. 35 — just applied to actions instead of prompts.
10

Log every call the model made. guard

You gave the model verbs; now keep the receipt for every one. Every tool call gets a structured log line — the request id from Vol. 34, the tool name, the arguments, whether it was approved, and the result. The day something goes wrong, “which action did the agent take, on whose behalf, and who approved it?” has to be a one-line lookup, not an archaeology dig. A model that can act needs an audit trail the way a cash register needs a tape.

one structured line per tool call — the register tape
function logToolCall(call, { approved, result }) {
  log.info({
    reqId:    ctx.reqId,               // ties to the Vol. 34 trace
    tool:     call.name,
    mutates:  TOOL_META[call.name].mutates,
    args:     call.input,
    approved,                          // ← who let this happen
    outcome:  result.error ? 'error' : 'ok',
  });
}
// now: "show me every issueRefund this week, and who approved each" = one query
heads up
This closes the loop with the last three volumes. Injection tries a bad verb → the whitelist (move #7) bounces it → the log catches the attempt → it becomes a Vol. 24 eval case → it can never work twice. Ship it, defend it, watch it, version it, and now: give it hands you can see.
