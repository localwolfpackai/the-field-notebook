The answer you never see — watch your live AI app, then turn its worst reply into a fixed one.

Last volume you kept the model on-task when a stranger tried to break it. But the strangers who don’t try to break it are a bigger blind spot: they ask a real question, get a real answer, and you never read a word of it. Your app is shipped, capped, and defended — and completely dark. This is observability: ten moves to see inside the box. Trace every call, tag it with an ID, add a thumbs-up/down, sample the real conversations, replay the bad one, watch cost and latency drift — and then the move that makes all the others worth it: feed the worst answer straight back into your evals so it never happens twice. The week after I put a little AI helper live, I checked the spend dashboard, saw a healthy little curve of usage, and felt great. Then a friend texted me a screenshot: my bot had confidently given her a wrong answer about a thing I’d never even tested. My reaction wasn’t “how do I fix it” — it was “how many other people got that answer, and I just never knew?”

That’s the gap this volume closes. When you build a normal app, a bug throws an error and something turns red. When you ship an AI app, the failure mode is quieter and worse: it produces a fluent, confident, wrong answer, hands it to a stranger, and moves on. Nothing turns red. The only person who ever sees it is the user — and they just leave. You are flying a plane with the windows painted over.

Observability is knocking the paint off the windows. It’s three questions you should be able to answer about any live app: what did it actually say, to whom, and was it any good? The ten moves below build that up from a single log line to a real loop — and the loop is the point. Every bad answer you catch becomes a test case (Vol. 24) that guards the next version. Watching without acting is just a sadder dashboard.

01

See the blind spot — silence isn’t success. read

The dangerous thing about a shipped AI app is that nothing tells you it’s failing. A crashed server pages you. A 500 shows up in red. But a model that hands a confident wrong answer to a stranger looks identical, from your side, to one that nailed it — same 200 response, same happy latency graph, same little bump in the usage chart. Cal’s daily-experiment instinct is the fix: you don’t guess whether it’s good, you go read what it actually said.

So the whole discipline starts with a mindset flip. Your spend dashboard tells you the app is alive. It tells you nothing about whether it’s right. Those are two completely different questions, and almost every beginner ships the first dashboard and calls it monitoring. The moves below build the second one: the one that can answer “was that answer any good?”

blind

You see that it ran — green graphs, zero insight. Requests count up, latency looks fine, spend ticks along. Every one of those requests could be a wrong answer and the dashboard would look exactly the same. You find out something’s broken when a user tells a friend, not you.

instrumented

You see what it said — you can read the conversation. Every call leaves a trace: the prompt, the reply, who gave it a thumbs-down, how long it took. A bad answer is now a row you can find and fix — not a rumor you hear about a week late.

02

Log the one line that matters. setup

You don’t need a vendor to start. The first real move is one structured log line per call, written from the same serverless route you shipped in Vol. 32. Dray’s plain-developer framing: it’s just a console.log of a JSON object — but log the right fields, as structured JSON (not a string), so future-you can actually search it.

api/chat.js — one structured line, right after the model replies
const t0 = Date.now();
const reply = await client.messages.create({ /* … */ });
const ms = Date.now() - t0;

// one searchable line — not a paragraph, not a string blob
console.log(JSON.stringify({
  at:      new Date().toISOString(),
  input:   userText.slice(0, 400),   // truncate — you want shape, not liability
  output:  reply.content[0].text.slice(0, 400),
  model:   reply.model,
  tokens:  reply.usage.input_tokens + reply.usage.output_tokens,
  ms,                                    // latency, for free
  stop:    reply.stop_reason,            // 'end_turn' vs 'max_tokens' matters later
}));
try it
On Vercel, these lines land in the runtime logs you already watched in Vol. 32 — no new tool. Log as structured JSON, never a formatted string: the day you want “every call over 4 seconds,” a JSON field is one filter and a string is a regex nightmare.
03

Tag every call with a request ID. setup

The moment you have more than one log line, you need a way to say “that one.” A short request ID, generated at the top of the route and stitched into every log line, every error, and — crucially — returned to the browser, is the thread that ties a user’s complaint to the exact conversation in your logs. Ashi’s modular habit: one ID, threaded through every piece.

generate once, thread everywhere, hand it back to the client
const rid = crypto.randomUUID().slice(0, 8);   // 'c7d4a1f0' → short + unique enough

try {
  const reply = await client.messages.create({ /* … */ });
  console.log(JSON.stringify({ rid, ok: true, /* …the fields from move 2… */ }));
  return Response.json({ rid, text: reply.content[0].text });  // ← rid goes to the UI
} catch (e) {
  console.error(JSON.stringify({ rid, ok: false, err: e.message }));   // same rid on failure
  return Response.json({ rid, error: 'Something went wrong' }, { status: 500 });
}
try it
Show the rid somewhere quiet in your UI — a tiny grey #c7d4a1f0 under the reply. Now a bug report is “it broke, ref #c7d” and you jump straight to the one line instead of scrolling a thousand. This one ID is the spine every later move hangs off.
04

Add the thumbs — let users grade you. signal

Here’s the highest-value, lowest-effort widget you will ever add: a 👍 / 👎 under each reply. You cannot read every conversation, but your users can, and a thumbs-down is them pointing at the exact bad answer for you. Bailey’s prototyping energy applies — it’s two buttons and one fetch, and it turns silent strangers into a free labelling team.

the feedback endpoint — attach a vote to the rid from move 3
// client: the two buttons post the rid + the vote, nothing else
function vote(rid, score) {          // score: +1 or -1
  fetch('/api/feedback', { method: 'POST',
    body: JSON.stringify({ rid, score }) });
}

// server /api/feedback: write it next to the trace, keyed by rid
export async function POST(req) {
  const { rid, score } = await req.json();
  await db.feedback.insert({ rid, score, at: Date.now() });
  console.log(JSON.stringify({ rid, feedback: score }));   // 👎 is now findable
  return Response.json({ ok: true });
}
heads up
Thumbs are biased and sparse — most people vote on nothing, and the angry ones vote loudest. Treat a 👎 as “go look at this,” not “this is objectively broken.” It’s a spotlight pointed at conversations worth reading, which is exactly what you were missing — not a grade you can average and trust.
05

Trace the whole call, not just the reply. signal

For a bare model call, move 2’s log line is the whole trace. But the second your app does more than one thing — retrieves a doc (Vol. 26), calls a tool (Vol. 19), runs an agent loop (Vol. 10) — the interesting failure lives between the steps. A trace records each step as a span under one rid, so when the answer is wrong you can see which step went sideways, not just that the final text was bad.

a hand-rolled trace — an array of spans, one rid, no vendor needed
const trace = { rid, spans: [] };
const span = (name, fn) => async () => {
  const t = Date.now(), out = await fn();
  trace.spans.push({ name, ms: Date.now() - t });
  return out;
};

const docs  = await span('retrieve', () => search(userText))();
const reply = await span('generate', () => model(userText, docs))();
console.log(JSON.stringify(trace));
// → spans: [ {retrieve, 80ms}, {generate, 1400ms} ]  ← now you know WHERE the time (or the bug) went
try it
Start hand-rolled — an array of {name, ms} is a real trace and costs nothing. When it gets busy, tools like Langfuse, Helicone, or plain OpenTelemetry give you the same spans in a searchable UI. Same idea, more chrome. Don’t buy the tool before you feel the pain.
06

Sample real conversations on purpose. watch

You can’t read all of it and you shouldn’t only read the complaints — the thumbs-down crowd is a skewed slice. So carve out fifteen minutes and read a random handful of real sessions, the way a restaurant owner eats their own food unannounced. This is where you discover the failures nobody bothered to downvote: the merely-mediocre answer, the slightly-off tone, the thing that technically worked but felt wrong.

a two-minute daily habit — pull 10 random traces and actually read them
$ node read-samples.js --n 10 --since 24h

#a1f  👍  "when do refunds process?"        → clean, on-task
#c7d  👎  "do you ship to Canada?"          → WRONG — invented a policy
#e02  🐢  "summarize my last 3 orders"      → right, but 6.2s (slow)
#f5a  --  "what's your return window?"      → fine
#b93  🚫  "cancel order #4821"              → refused a legit request
// 3 of 10 worth fixing — you'd never have found #e02 or #b93 from votes alone
try it
Make it a ritual, not a project: ten random sessions with coffee, once a day, for a week. You’ll learn more about your real threat model than any spec — because it’s your users asking your app the questions you never imagined.
07

Replay the bad one exactly. signal

You found a 👎. Now the trap: you tweak the prompt, ask the model a slightly different question, get a good answer, and declare victory — but you never reproduced the original miss, so you have no idea if you fixed it. The fix is to replay the exact input from the trace: same user text, same retrieved docs, same everything, so “before” and “after” are actually comparable.

replay.js — rebuild the failing call from its stored trace
const t = await db.traces.find({ rid: 'c7d' });   // the downvoted one

// feed the SAME inputs back in — this is the "before"
const before = await runChat(t.input, { system: t.system });
console.log('before:', before.text);   // "Yes, we ship to Canada in 2 days" ← invented

// now change ONE thing (the system prompt) and replay the identical input
const after = await runChat(t.input, { system: fixedSystem });
console.log('after: ', after.text);   // "I can only confirm US shipping — let me get a human." ✓
heads up
Models are non-deterministic — the same input can vary run to run. Replay a fix a few times, not once, before you trust it. One good replay is luck; five good replays is a fix. (Set temperature: 0 for the eval in the next move to squeeze most of the wobble out.)
08

Watch the drift — cost, latency, refusals. watch

Single bad answers are one failure mode; slow trends are the other, and they’re sneakier. Your p95 latency creeping from 2s to 5s. Your average tokens-per-call doubling because someone made the system prompt longer. Your refusal rate quietly climbing after a prompt tweak. None of these throw an error — they just make the product worse by degrees. The fields you logged in move 2 are exactly the fields you now chart over time.

SignalFrom the log fieldWhat a bad trend means
p95 latencymsSlower tail — users bounce before the tokens finish.
Tokens / calltokensCost creep — a longer prompt or runaway context (Vol. 14).
Refusal rateoutput matchOver-guarded — the app is now saying “I can’t” too often.
Cut-off ratestop = max_tokensAnswers getting truncated mid-thought — raise the ceiling.

watch the percentile, not the average — the average hides your worst 5%.

09

Alarm on the spike, not the average. watch

A dashboard only helps when you’re looking at it — and you won’t be, at 2am on a Saturday. So set one or two cheap alarms that ping you (a Slack webhook, an email) when something crosses a line you’d actually care about. The art is picking thresholds that fire on real problems and stay quiet otherwise, or you’ll mute them in a week — and a muted alarm is worse than none.

a cron that checks the last hour and pings you only on a real spike
const last = await db.traces.since('1h');

const downRate = last.filter(t => t.feedback === -1).length / last.length;
const spend    = last.reduce((s, t) => s + t.cost, 0);

if (downRate > 0.15)              // >15% thumbs-down in an hour = something regressed
  ping(`👎 rate ${(downRate*100)|0}% last hour — go read the traces`);

if (spend > 5)                    // backstops the daily cap from Vol. 32 at hourly resolution
  ping(`💸 $${spend.toFixed(2)}/hr — check for a loop or an abuser`);
try it
Start with exactly two alarms: a thumbs-down spike and an hourly-spend spike. They map to your two real fears — “it got worse” and “it got expensive” — and they pair perfectly with the daily spend cap you already set in Vol. 32. Add more only when a real incident teaches you the third one you needed.
10

Close the loop — the bad reply becomes an eval. loop

This is the move the other nine exist for. A bad answer you merely fixed can silently come back the next time you touch the prompt. A bad answer you turn into a test case is guarded forever. Take the downvoted trace, write down what the right answer looks like, and drop it into the eval harness from Vol. 24. Now your CI grades every future version against the exact mistakes your real users already caught.

one downvoted trace → one golden eval case (the whole loop, in code)
// the loop, start to end:
//   user 👎 → trace captured → you read it → you write the expectation

evals.push({
  id:     'ships-canada-honestly',
  from:   'trace #c7d — real user, downvoted 2026-07-06',   // provenance
  input:  'do you ship to Canada?',
  expect: (out) => !/yes|2 days/i.test(out)         // must NOT invent a policy…
             && /US|human|can't confirm/i.test(out),   // …must hedge or escalate
});
// next deploy, CI runs this. the exact miss a stranger found can never ship again.
try it
This is the flywheel that separates a toy from a product: every real-world miss makes the app permanently harder to break. Observe → catch → replay → add-to-evals → guarded. Do this ten times and your eval suite becomes a museum of every dumb thing your app ever said — and a wall against it saying them again.
