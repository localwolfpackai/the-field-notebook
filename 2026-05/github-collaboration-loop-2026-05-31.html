The Collaboration Loop ⇄

your first PR to someone else's repo, without the cold sweat

Every guide before this one taught Git as a solo sport — your laptop, your repo, your commits. But the moment a second person shows up, a new map appears: forks, upstream, pull requests, review. Eleven moves for shipping code with people instead of just near them.

verified Open notebook · keep it bookmarked · every command adversarially verified

The first time I sent a pull request to a repo I didn't own, I froze. Solo Git I had down — branch, commit, push, done. But this had two copies of everything and a word I'd never used as a verb: "upstream." I clicked Fork, then sat there not knowing what I'd actually just made.

Here's the whole thing in one breath. Collaboration on GitHub is a loop, and once you can see it, every command lands in a slot. You take a copy (fork), do your work on a branch, push it to your copy, and open a pull request that asks the original repo to pull your work in. People review, you adjust, it merges. Then you sync your copy back up and go again.

🔁 The loop, one lap

fork their repo→ branch for the change→ push to your fork→ open PR→ review + adjust→ merge→ sync your fork ↩ back to top

Two remotes hold the whole mental model: origin is your fork (where you push), upstream is their original (where updates come from). Get those two straight and the rest is just steps around the circle.

// the eleven moves
the move · fork

Take your own copy of someone else's repo

You usually can't push directly to a repo you don't own — you don't have write access, and that's by design. A fork is your personal copy living under your account, that you can push to. One gh command forks it, clones the fork to your machine, and wires up both remotes for you, so you skip the part everyone fumbles by hand.

fork + clone + wire remotes in one shot
$ gh repo fork owner/their-repo --cloneForks it to your account, clones that fork locally, and adds an 'upstream' remote pointing at the original. $ cd their-repoDrop into the freshly cloned folder. $ git remote -vSanity check: 'origin' = your fork, 'upstream' = the original. This is the whole map.

⚠ footgunA fork is a snapshot in time — the second the original gets new commits, your fork is stale. It won't update itself. That's what move 04 is for. Also: forking is for repos you don't own. If you have write access already, skip the fork entirely and just branch in the real repo.

◆ claude codeSay "confirm my git remotes are wired right for a fork workflow" — it reads git remote -v and tells you whether origin and upstream point where they should before you waste a push.

the move · remotes

origin vs upstream — the only model you need

This one idea unlocks everything else. A remote is just a nickname for a repo URL. You keep two: origin points at your fork (you have write access — you push here), and upstream points at the original (you only read — you pull updates from here). If you cloned with plain git instead of gh, upstream won't exist yet. Add it once and forget it.

add upstream by hand (only if it's missing)
$ git remote add upstream https://github.com/owner/their-repo.gitNames the ORIGINAL repo 'upstream'. Swap in the real owner/repo from the project's GitHub page. $ git remote -vYou should now see four lines: origin (fetch + push) and upstream (fetch + push).

⚠ footgunTrying to git push upstream and getting "permission denied" isn't a bug — you don't own upstream, so you can't push to it. That's the entire point of the fork. You push to origin; the pull request is how your work reaches upstream. If push asks for a password and fails, it's almost always this confusion.

◆ claude codePaste a "permission denied" or "remote rejected" error and it'll tell you whether you're pushing to the wrong remote — the single most common first-PR mistake.

the move · branch

Never do the work on main

It's tempting to just edit files on your fork's main and push. Don't. main is the clean line you sync from upstream (move 04) — if your changes live there, every future sync turns into a tangle. Make a fresh branch named for the change instead. One branch, one pull request, one idea. It keeps the review readable and your main pristine.

branch off main for the actual work
$ git switch mainStart from a clean, synced main (see move 04 for keeping it fresh). $ git switch -c fix-readme-typoNew branch named for the change. -c means 'create'. Now do your edits here. $ git add . && git commit -m "fix: correct install command in README"Small, focused, conventional message. Future reviewers (and you) will thank you.

⚠ footgunCommitting straight onto your fork's main is the slow-motion mistake — it works today, then move 04's sync wants to fast-forward main and can't, because main has diverged. Keep main as a mirror of upstream, always. Real work lives on branches, every time.

◆ claude codeAsk it to "branch off a clean main and commit these changes with a conventional message" — it stages, names the branch sensibly, and writes the commit so the PR reads well later.

the move · sync

Keep your fork from drifting into last month

While your fork sat there, the original kept moving. A stale fork is the number-one source of "why is my PR full of conflicts." The fix: pull upstream's latest into your main, regularly. Easiest is one gh command; the manual version is worth knowing so you understand what it does — fetch upstream, fast-forward your main, push that to your fork.

two ways to catch your fork up
$ gh repo sync your-name/their-repo --branch mainThe one-liner: pulls upstream/main into your fork's main, on GitHub and locally if it's clean. $ git fetch upstream--- or do it by hand --- download upstream's latest, without changing your files yet. $ git switch main && git merge upstream/mainFast-forward your main up to upstream. Clean because you never commit to main (move 03). $ git push origin mainPush the caught-up main back to your fork so GitHub shows it as current too.

⚠ footgunForgetting to update your working branch after syncing main. Syncing only catches up main — your feature branch is still based on the old code. Rebase it forward with git switch fix-readme-typo then git rebase main so your PR sits cleanly on top of the latest. Sync before you branch, and again right before you open the PR.

◆ claude codeSay "my fork is behind upstream, catch it up and rebase my branch on top" — it runs the fetch/merge/rebase in order and pauses if a real conflict needs your eyes.

the move · pull request

Push, then open the pull request

A pull request is you saying "here's a change — please pull it into your repo." First push your branch to your fork (origin), then open the PR against upstream. The gh CLI does it without leaving the terminal. The PR body is the part beginners skip and reviewers live by: what changed, why, and how to test it. That paragraph is the difference between a fast merge and silence.

branch → fork → pull request
$ git push -u origin fix-readme-typoPush your branch to your fork. -u links them so future pushes are just 'git push'. $ gh pr create --fillOpens a PR against upstream, using your commit message as the title + body. Fastest path. $ gh pr create --webOr open the PR form in your browser to write a fuller body and add screenshots. $ gh pr view --webPop the live PR open anytime to watch checks, comments, and the merge button.

⚠ footgunOne giant PR with twelve unrelated changes is where review goes to die — nobody wants to approve a change they can't fully read. Keep each PR to one idea. And check the base: gh pr create defaults to upstream's default branch, which is usually right, but confirm it's targeting main and not some release branch.

◆ claude codeSay "write a PR body from my diff — what changed, why, how to test" and it drafts the description from the actual commits, then you run gh pr create --body-file. Best-spent thirty seconds in the whole loop.

the move · respond

They requested changes — you don't start over

This is the part that surprised me most: when a reviewer asks for changes, you do not open a new PR. A pull request tracks a branch, not a snapshot. So you just keep committing to the same branch and push — the open PR updates itself, live, with your new commits stacked on. The conversation stays in one place and the reviewer sees exactly what moved.

address feedback — same branch, same PR
$ git switch fix-readme-typoMake sure you're back on the PR's branch before editing. $ git add -pStage your edits chunk by chunk so the new commit is exactly the fix they asked for. $ git commit -m "review: rename var for clarity" && git pushPush to the same branch. The PR picks up the new commit automatically — no new PR needed. $ gh pr comment --body "Done — renamed and added the test you flagged."Tell the reviewer you addressed it, so they know to look again.

⚠ footgunReaching for --amend + --force-with-lease to "keep history clean" mid-review. Resist it — adding plain commits lets the reviewer see just what changed since they last looked. Save the tidy-up (squash) for the merge button, which most repos offer. Force-pushing a branch someone's actively reviewing scrambles their view.

◆ claude codePaste the review comment and the file — it makes the exact change requested and writes a commit message that references the feedback, so the thread reads as a clean back-and-forth.

flip sides · review

Now you're the reviewer — read with your hands

Collaboration runs both ways, and reviewing well is half of being trusted on a team. The trick nobody tells beginners: don't review from the diff alone — check the branch out and run it. The gh CLI pulls someone's PR onto your machine in one command, so you can actually exercise the change before you bless it. Then leave a review: approve, comment, or request changes.

pull a PR down, run it, leave a verdict
$ gh pr listSee open PRs with their numbers. Pick the one to review. $ gh pr checkout 42Checks out PR #42's branch locally — now run it, test it, poke at it for real. $ gh pr diff 42Read the full change in the terminal, colored, without opening a browser. $ gh pr review 42 --approve -b "Tested locally, ships clean. Nice fix."Or --request-changes -b "..." to ask for edits, or --comment -b "..." for a non-blocking note.

⚠ footgunApproving from the diff without running it. Diffs hide whole categories of problems — does it actually build, does the test pass, does the button work. If you can't run it, say so in the review rather than rubber-stamping. A review that says "looks right but I didn't run it" is honest and useful; a blind approval isn't.

◆ claude codeAfter gh pr checkout 42, ask it to "review this PR for correctness and edge cases" — it reads the diff in repo context and flags risky spots, giving you a second set of eyes before you sign off.

the scary one · conflicts

"This branch has conflicts with the base"

GitHub greys out the merge button and says your branch conflicts with the base. It's not broken — while your PR sat in review, the base branch (main on upstream) moved, and both sides touched the same lines. Git won't guess which wins. The web editor handles tiny conflicts; for anything real, resolve it locally. Pull the base in, fix the marked spots, push — the PR re-checks itself and the button lights up.

resolve a PR conflict against the base, locally
$ git switch fix-readme-typoBe on your PR's branch. $ git fetch upstreamGrab the latest base branch you'll be merged into. $ git merge upstream/mainPull the base into your branch. Git stops at the conflicting files and marks them. $ git add . && git commit && git pushAfter you delete the <<< === >>> markers and keep the right lines, this finishes it and updates the PR.

⚠ footgunTwo traps. First: leaving even one conflict marker (<<<<<<< / ======= / >>>>>>>) in a file ships broken code — they're Git's notes, not yours. Second: resolving against the wrong branch. It's the base you're merging into (usually upstream/main) you want to pull in, not a random branch. When in doubt, git merge --abort rewinds you to safety.

◆ claude codeDrop a conflicted file in and ask "what was each side trying to do?" — it reads both branches' intent so you resolve by meaning instead of guessing which block to keep, then double-checks no markers are left behind.

the move · draft

Share early without pinging anyone for approval

You don't have to wait until a change is perfect to open a PR. A draft pull request is the "work in progress, eyes welcome, don't merge yet" signal. It runs the CI checks and lets people comment, but it can't be merged and doesn't nag reviewers for a final sign-off. When it's ready, flip it to ready-for-review in one command. Great for getting direction before you've sunk hours into the wrong approach.

open as draft, flip to ready when done
$ gh pr create --draft --fillOpens a draft PR — checks run, people can comment, but the merge button stays locked. $ gh pr readyWhen it's polished, marks the PR ready for review and notifies reviewers.

◆ tipUse a draft to ask one early question — "am I solving this the right way?" — before you write the whole thing. Cheap course-correction beats a finished PR pointed at the wrong target.

◆ claude codeSay "open this as a draft PR with a body that asks reviewers about my approach" — it frames the description as a question so you get direction, not just a rubber stamp.

the move · cleanup

It merged — now close the loop

Your PR went in. Two small habits keep the next lap clean: sync your fork so its main includes the merge, and delete the branch you're done with. GitHub usually offers to delete the remote branch right on the merged PR — take it. Then tidy the local copy. A fork without a branch graveyard, and a main that matches upstream, means tomorrow's change starts from a clean line.

sync up, sweep up, ready for the next one
$ git switch mainLeave the merged branch. $ gh repo syncPull the merge (your change, now in upstream) down into your fork's main. $ git branch -d fix-readme-typoDelete the local branch. -d is the safe version — it refuses if the work wasn't merged. $ git push origin --delete fix-readme-typoOnly if GitHub didn't already auto-delete the remote branch when you merged.

⚠ footgunSkipping the sync and starting your next branch off a stale main — now you're building on yesterday's code and walking straight back into move 08's conflicts. The lowercase -d (not -D) is deliberate: it's the seatbelt that won't let you delete a branch whose work never actually landed.

◆ claude codeSay "my PR merged, clean up my fork and local branches" — it syncs main and removes the merged branch with the safe flag, refusing to delete anything that didn't actually ship.

the human layer · etiquette

The part that isn't a command

Every move above is mechanical. What actually gets your PRs merged — and gets you invited back — is the human layer. A pull request is a conversation, not a transaction. The maintainer is a person doing you a favor by reviewing. These five habits did more for my open-source standing than any Git trick.

the unwritten rules, written down
small > cleverOne focused change per PR. A 40-line PR gets reviewed today; a 1,400-line one gets "I'll look later" forever. explain the whyThe diff shows WHAT changed. The body explains WHY — that's the context a reviewer can't reconstruct alone. read CONTRIBUTING.mdMost repos tell you their rules — commit style, tests, formatting. Following them is free goodwill. reply to every commentEven "good catch, fixed." Silence reads as ghosting; a one-liner keeps the thread alive and warm. assume good intentBlunt review feedback is about the code, not you. Thank them, adjust, move on. It compounds into trust.

◆ claude codeBefore you open a PR to a new repo, ask it to "check this repo's CONTRIBUTING.md and tell me what they expect" — it reads the contributor guide and flags the commit format, tests, or lint you need to pass so you don't get bounced on a technicality.

The one shape underneath all eleven

Read the moves back and the same circle keeps turning: your fork is yours, upstream is theirs, and the pull request is the bridge between them. You push to origin, you pull from upstream, and you talk in the PR. Almost every "wait, which copy am I even in" moment dissolves the instant you can name the two remotes out loud.

Solo Git teaches you to save your work. Collaboration teaches you to offer it — and to receive someone else's the same way. That's the actual unlock, and it's less about commands than it looks: keep the changes small, keep your fork synced, and treat every review like the conversation it is. Do one full lap of the loop on a real repo this week. The cold sweat is gone by the second.
