01the basics

The three commands that actually matter on day one

There are 150+ git commands. You will use three of them 95% of the time. Start there.

Everyone tries to teach you the whole tree at once. Don’t learn the whole tree. Learn status, add, and commit. That’s it. The rest comes when you need it.

$ git status              # what changed?
$ git add .                # stage everything I changed
$ git commit -m "first one"  # save a snapshot

If you can run those three in a loop without panicking, you’re already past the wall. Everything else — branches, remotes, rebases — is a flavor of save, restore, or share.

Hot take

Memorizing flags before you understand the loop is like memorizing keyboard shortcuts in an app you’ve never opened. Get the loop first. The flags will find you.

02mental model

What “staging” really means (and why it’s a gift)

Staging isn’t bureaucracy. It’s a quiet room where you decide what’s ready to ship.

The thing nobody tells you: git has three places your file can live.

working

The mess. Whatever you’ve typed but haven’t marked as ready.

staging

The waiting room. You picked this. It’s about to be saved.

commit

The save point. A snapshot you can rewind to.

Staging lets you commit two things separately even when you changed them in the same session. That sounds boring until you’ve done it — then it feels like a superpower.

$ git add src/button.tsx        # stage just this one
$ git commit -m "fix button hover"
$ git add src/utils/colors.ts
$ git commit -m "new oklch palette"

Two commits. Two stories. Future-you reads the log and instantly knows what happened.

03craft

Commit messages future-you will actually thank you for

A commit message is a note to a stranger. That stranger is you, six months from now, debugging at 1am.

The rule I stole and haven’t broken: start with a verb, finish the sentence “if applied, this commit will...”

weak

updates
fix stuff
final final v2

strong

add OKLCH color picker to settings
fix race condition in upload queue
remove dead auth middleware

50 character subject line. Imperative mood. If you need a body, blank line, then the why — not the what. The diff already shows the what.

Field note

I write the commit message before I write the code now. If I can’t describe the change in one line, the change is too big. Split it.

04safety net

The .gitignore you forget until it’s too late

Everyone learns about .gitignore the day they commit their API key. Be the rare bird who learns it the day before.

Before your second commit, drop a .gitignore at the project root. Here’s the version I paste into every new repo:

# dependencies
node_modules/
.venv/
__pycache__/

# secrets — never commit these
.env
.env.local
.env.*.local
*.pem
*.key
auth.json
credentials.json

# builds & caches
.next/
dist/
build/
.cache/
*.log

# macOS junk
.DS_Store
Thumbs.db

# editor noise
.vscode/
.idea/
*.swp
If you already committed a secret

Rotate the key first. Today. Right now. Then deal with git history. The internet has already scraped it — assume compromise, rotate, move on.

05branches

Branches are cheap. Use them like sticky notes.

A branch is not a commitment. It’s a workspace. Make one for every idea, even the dumb ones.

I used to be scared of branches. I treated main like a museum floor and tiptoed around it. Then I learned: a branch is just a label that says “these commits belong together.” You can throw it away. You can keep it. You can do five at once.

$ git switch -c try-new-hero    # new branch + switch to it
$ # mess around freely
$ git switch main                # back to safety
$ git branch -D try-new-hero     # nuke it if it sucked

The pattern: one branch per idea. Don’t mix “fix the bug” and “refactor the header” on the same branch. Future-you can’t review what’s tangled.

06escape hatch

git stash — the “save and step away” button

You’re mid-thought. Someone Slacks you to fix a typo on the live site. git stash exists for this exact moment.

stash shoves your in-progress work into a hidden pocket so you can switch tasks without losing it. Then you pop it back out when you’re done.

$ git stash                       # hide my mess
$ git switch main
$ # do the urgent thing, commit it
$ git switch my-feature-branch
$ git stash pop                    # bring my mess back
Real-world

I use stash almost every day. It’s the closest git has to “pause.” If you remember nothing else from this guide, remember this one.

07collaboration

Pull requests are conversations, not bureaucracy

A PR isn’t a final exam. It’s a draft you’re showing a friend before it goes on the wall.

If you’re the only person on your project, you’ll still benefit from PRs. They give you a moment to read your own diff before merging. That moment catches more bugs than every linter combined.

The structure I use for every PR description:

## What
One sentence. What does this change do.

## Why
Two sentences. Why does this change need to exist.

## How to test
- Open the homepage
- Click the button
- Confirm the thing happens

## Screenshots
(drag and drop — GitHub auto-uploads)

Write it for someone who has never seen your project. Half the time, that someone is you in three months.

08presentation

README is your storefront. Treat it that way.

Nobody scrolls. Your README has six seconds to explain what this is and why anyone should care.

The order I use, top to bottom, every time:

01 / one-liner

What this is. No clever metaphors. Plain English.

02 / screenshot

One image. Hero shot. Above the fold matters here too.

03 / quickstart

Three commands. install, run, open.

04 / what’s here

Bullet list of features. Verbs first.

05 / how it works

One paragraph. The architecture, if relevant.

06 / license

Pick one. MIT is fine. Don’t agonize.

Pro move

Add badges (build status, license, version) only if they say something true. Decorative badges are the corporate trophies of open source — they impress nobody and make your repo look older than it is.

09power tool

The gh CLI is criminally underrated

GitHub’s website is fine. GitHub’s command-line tool is a different planet. Install it on day one.

gh is GitHub’s official CLI. It runs PRs, issues, releases, gists, and more — without leaving the terminal. The five commands I run weekly:

$ gh repo create my-thing --public   # new repo from CLI
$ gh pr create                       # PR from current branch
$ gh pr view --web                    # open it in browser
$ gh issue list --label bug           # scan open bugs
$ gh pr checkout 47                   # pull down someone’s PR

The first one alone is worth it. Going from “I have a folder” to “it’s on GitHub” is now a single command. No clicking through the new-repo wizard.

10leverage

Let AI write your commit messages (mostly)

Commit messages are the perfect job for AI: short, repetitive, easy to verify. Hand it off.

I use Claude or gh copilot suggest to draft commit messages from the diff. The workflow:

$ git diff --staged | claude -p "write a commit message"
# Claude reads the diff, suggests a message
# I edit it (usually shorten it), then commit
$ git commit -m "<the message>"

The trick: always edit it. AI writes fine commits. AI writes great commits when you remove its hedging and tighten its verbs. You’re the editor, not the typist.

The bigger pattern

This is the AI sandwich. Humans on top and bottom — you choose what to commit and you ship the result. The model is the filling. Use it everywhere the task is mechanical and the judgment is yours.

Same pattern works for: PR descriptions, README sections, changelog entries, release notes. Anywhere structured prose lives, AI does the first draft. You do the second.

The whole thing in one sentence: git is a save button with branches.

Everything else is a refinement of that idea. Don’t let anyone make it feel bigger. The fancy commands — rebase, cherry-pick, reflog — are tools you reach for once you’ve hit the problems they solve. Until then, status · add · commit · push.

The platform feels less scary the moment you stop treating it as a test and start treating it as a workshop. Branches are cheap. Mistakes are recoverable. Your repo is yours.

—Lupo

What to try this week

  • Create a throwaway repo. Make ten commits in one sitting. Get the loop in your hands.
  • Install the gh CLI and run gh repo create once.
  • Open one PR — even on your own project — just to feel the review surface.
  • Add a real .gitignore to every project you currently have running.
  • Pipe one diff into your AI of choice and read the suggested commit message.
