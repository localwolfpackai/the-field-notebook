GitHub Field Notebook — twelve habits that actually stick.

Open notebook. Daily-driver workflows. Real commands, not abstractions. Written for the non-developer who already lives inside Claude Code and just wants GitHub to stop feeling like a wall of menus.

— scribbled by Lupo, somewhere between coffee #2 and the first commit of the day.

I'm not a developer. I orchestrate. The first time I opened the GitHub dashboard I saw seventeen tabs and closed the tab. That was 2024. Now I push code daily and the only command I actually type by hand is gh pr create. Everything else gets delegated.

What follows is the field notebook — the twelve habits that took me from refusing to look at it to shipping pull requests in a week. Each one is short. Each one comes with the exact command. No theory unless the theory unblocks the move.

I write it casual because that's how I learned it — from Cal's open notebooks, Ashi's modular breakdowns, Bailey's step-by-step prototyping. So this is mine, in that lineage. Steal what works.

01

Install the CLI, skip the web.

setup

The browser dashboard is a museum. The CLI is the workshop. Install gh once and 80% of the buttons disappear.

$ brew install gh
# …a few seconds later…
$ gh --version
gh version 2.62.0

That's it. You now have a tiny machine that talks to GitHub on your behalf. Everything below builds on it.

02

Auth once, then forget about it forever.

setup

Personal access tokens, SSH keys, browser logins — three different rabbit holes. Skip them. gh auth login bundles all of it into one walkthrough.

$ gh auth login
? Where do you use GitHub?  GitHub.com
? Preferred protocol?        HTTPS
? Authenticate Git?           Yes
? How would you like to auth? Login with a web browser
# copy the one-time code, paste in the browser, done.
✓ Logged in as your-username
why this matters → You just told both the CLI and git itself how to push. No more "permission denied" errors at the worst possible moment.
03

Clone like a grown-up.

setup

Stop copy-pasting URLs. Use the CLI to grab any repo you can see. You can also clone with HTTPS or SSH without remembering which is which — gh figures it out.

$ gh repo clone anthropics/anthropic-cookbook
$ cd anthropic-cookbook
$ ls
README.md  misc/  multimodal/  skills/  third_party/ …

For your own repos: gh repo create my-experiment --public --clone creates and clones in one shot. The next paragraph of your morning is a working folder.

04

Branches are scratch paper.

daily driver

Mental model: main is the published version of the book. A branch is a sticky note you slap on the desk while you try things. If the experiment works, you fold it back into the book. If it doesn't, you throw the sticky note away — the book is fine.

main → checkout -b feature/new-hero → commit commit commit → merge back 
$ git checkout -b feature/landing-tweak
# …make changes, save files…
$ git checkout main          # bail out, no harm done
$ git branch -D feature/landing-tweak  # throw the sticky note away
rule of thumb → One branch per thought, not per feature. If you change direction halfway through, start a new branch. It's free.
05

Commit small, commit often.

daily driver

A commit is a save point in a video game. The cost of a save is zero. The cost of not having a save when something breaks is the rest of your afternoon.

don't do this git commit -m "stuff"
git commit -m "more stuff"
git commit -m "fixed everything"
do this git commit -m "add hero copy"
git commit -m "swap CTA color to sky"
git commit -m "fix mobile h1 wrap"

Subject in the imperative mood: add, fix, remove. Read it as "If applied, this commit will …". Then it scans correctly in git log six months later when past-you is a stranger.

06

The status / diff / log triad.

daily driver

Three commands. Memorize them. They answer 90% of the questions you'll have inside a repo.

  • git status — what files have I changed?
  • git diff — what's different inside those files?
  • git log --oneline -10 — what did I (or someone else) do recently?
$ git status
On branch feature/landing-tweak
Changes not staged for commit:
  modified:   site/index.html
  modified:   site/styles.css

$ git diff site/styles.css
# scrollable side-by-side of every line you touched

$ git log --oneline -5
a3f1d20 add hero copy
b22ee01 swap CTA color to sky
…
tiny upgrade → Add --graph to git log to see branches as ASCII art. Strangely satisfying once you spot the merges.
07

Pull requests, straight from the terminal.

PR flow

The web UI for opening a PR is twelve clicks. The CLI is one command. Ship the branch, open the PR, all in one breath.

$ git push -u origin feature/landing-tweak
remote: Resolving deltas …
branch 'feature/landing-tweak' set up to track 'origin/feature/landing-tweak'

$ gh pr create --fill --web
# --fill auto-uses your commit history as the PR title/body
# --web opens the draft in the browser for review

Skip --web if you're already happy with the title/body and just want it created. Add --draft if it's not ready to be reviewed — keeps reviewers off your back until you're ready.

08

Let Claude write the PR body.

AI workflow

Half the friction of opening a PR is staring at the empty description box. So don't. Pipe the diff to Claude Code (or whatever you have wired in) and let it draft the prose. You edit, you ship.

$ git diff main...HEAD | pbcopy
# paste into Claude:
# "Write a PR description: summary, test plan, anything worth flagging.
#  Two bullets max per section. Imperative mood."
$ gh pr create --title "Landing page: tighten hero copy" --body-file /tmp/pr.md
why it works → The diff is the source of truth. You're not asking the model to invent — you're asking it to summarize what's already there. That's its strongest mode. Always read the draft before posting; you're still the author.
09

.gitignore before your first push. Always.

safety

The single most public mistake a beginner makes: pushing .env with an API key in it. Once it's on GitHub, treat that key as burned even if you delete the commit. Set the gitignore before you push, not after.

$ cat > .gitignore <<'EOF'
.env
.env.local
.env.*.local
node_modules/
.DS_Store
*.log
.next/
dist/
build/
.vscode/
.idea/
EOF
$ git status   # confirm .env is no longer listed

If you already committed a secret — rotate the key first, then scrub. Order matters. Tools: git filter-repo for the scrub, the provider's dashboard for the rotate. Don't do this from memory at midnight.

10

Stash beats panic.

recovery

You're mid-experiment on Branch A. Slack pings — urgent fix needed on main. You have uncommitted changes. Panic? No. Stash.

$ git stash push -m "wip: hero layout exploration"
Saved working directory and index state On feature/hero: wip: hero layout exploration

# …go fix the thing on main, push, return to your branch…
$ git stash list
stash@{0}: On feature/hero: wip: hero layout exploration

$ git stash pop
On branch feature/hero
Changes not staged for commit:
  modified: site/index.html

Stash is the universal pause button. Anything you weren't ready to commit, you can shelve, switch branches, and pop back exactly where you were. It has saved me more afternoons than coffee.

11

Aliases for the lazy (recommended).

setup

I type these phrases 30 times a day. Why type them in full? Drop these into ~/.gitconfig once.

$ git config --global alias.s "status -sb"
$ git config --global alias.lg "log --oneline --graph --decorate -20"
$ git config --global alias.co "checkout"
$ git config --global alias.cm "commit -m"
$ git config --global alias.last "log -1 HEAD --stat"
# now:
$ git s
$ git lg
$ git cm "fix mobile h1 wrap"
bonus → Add a shell alias too: alias gp='git push', alias gpl='git pull --rebase'. Past-you will thank present-you within a week.
12

Read the diff before you ship. Every time.

safety

This is the rule that separates a habit from a hobby. Before you push, before you open the PR — open the diff. Scroll through it. Read it like a stranger would.

$ git diff --stat origin/main...HEAD
 site/index.html | 12 +++++++-----
 site/styles.css | 24 ++++++++++++++----------
 2 files changed, 21 insertions(+), 15 deletions(-)

$ git diff origin/main...HEAD
# the full prose of every line you've changed.
# scroll. read. delete debug lines you forgot. ship.
often slips through console.log("here")
console.log(data)
// TEMP — remove me
what you ship (nothing — that's the point.)

Reading the diff is also where you catch the typo, the unused import, the file you committed by accident. It takes 60 seconds. The alternative is a public commit history that documents your fumbling. Choose the 60 seconds.

★

Notes in the margin.

closing

None of this is impressive to a senior engineer. That's the point. These twelve habits aren't ceiling — they're the floor. Build them in once and the platform stops being scary. Then you can pay attention to the actual work: the code, the design, the idea you're trying to ship.

I learned most of this from people who showed their work in public — Cal's open notebooks, Bailey's prototyping walkthroughs, Ashi's modular breakdowns, Dray's "AI Engineer" language. The pattern is always the same: someone shows you the exact command they typed, and the mystery evaporates.

So here's the same pact. The exact commands are above. Steal them. Try one tomorrow. Throw away the branch if it doesn't work — that's literally what branches are for.
