The Undo Book ↩

"oh no" → "oh phew" in one command

Twelve panics every beginner hits with Git, and the calm fix for each. The thing nobody tells you up front: Git almost never throws your work away. It just stops pointing at it. Once that clicks, most "I broke everything" moments turn into a one-line walk-back.

verified Open notebook · keep it bookmarked · every command adversarially verified

I used to treat Git like a tripwire. One wrong command and the work was gone — that was the story in my head. It took getting burned a few times to learn the opposite: a commit is just a snapshot plus a label, and labels are the cheapest thing in Git to move. "I lost my commits" almost always means "the label slid off them," not "they're deleted." The work is usually still on disk, waiting to be pointed at again.

So before the twelve scenarios, here are the two tools that make nearly everything on this page recoverable. When the panic hits, I reach for these first — they tell me what state I'm actually in before I touch anything.

🧭 The two-tool compass

git status

Where am I, what's changed, what's staged. The map. Run it before and after any fix — half of all panics evaporate the moment you can see the actual state instead of imagining the worst.

git reflog

Git's private logbook of every place HEAD has ever stood. This is the undo-for-the-undo. If a commit "vanished," its hash is almost certainly still written here — read it back and re-attach a label.

// the twelve panics
oh no

The garbage commit message you already hit enter on

Nothing's broken. A commit is a snapshot plus a message, and since this one hasn't been pushed, it lives only on this machine. The message isn't carved in stone — it's just metadata on the latest commit, and Git lets you rewrite the latest commit's message any time before it leaves your laptop.

fix the message — unpushed
$ git commit --amend -m "the message you actually meant"Replaces the last commit's message in one shot. Files stay exactly as they were. $ git commit --amendSame thing, but opens your editor for a longer message. Save and close to apply. $ git log -1 --onelineConfirms the new message stuck.

⚠ footgun--amend only rewrites the most recent commit, and only safely while it's unpushed. If it already went up, amending makes local history disagree with the remote and the next plain push gets rejected (that's card 08's territory). And if the bad message is two or three commits back, amend can't reach it.

oh no

The file you left out of the commit

A commit is a snapshot of whatever was staged the moment you ran it. The forgotten file wasn't staged, so Git didn't include it. Nothing's lost — the file is still in your folder, just not recorded in that snapshot yet. Stage it now and fold it into the same commit instead of making a second one.

fold the file into the last commit
$ git add path/to/forgotten-fileStage what you left out (or 'git add .' to grab everything that changed). $ git commit --amend --no-editRe-do the last commit with the file folded in. --no-edit keeps your original message.

⚠ footgunAmend gives the commit a brand-new ID — fine while it only lives on your machine. If you already pushed, a plain git push gets rejected and you'd need git push --force-with-lease, which can stomp a teammate's work. If it's already shared, just make a fresh second commit. No shame in two commits.

◆ claude codeSay "I forgot to include a file in my last commit" and it checks whether that commit was pushed before picking amend vs. a follow-up — so you never rewrite shared history by accident.

oh no

Undo the last commit, keep every change

A commit is a bookmark pointing at a snapshot — it isn't your files. git reset --soft HEAD~1 moves the bookmark back by one commit and leaves every edit exactly where it was, now staged and ready to re-commit. The commit disappears from the log; the work stays in git status. And the move itself is logged in the reflog, so even this undo is undoable.

un-commit, keep the work
$ git reset --soft HEAD~1Removes the last commit, keeps all its changes staged, ready to re-commit. $ git statusConfirms your work is still there — files show as staged, nothing lost.

⚠ footgunThe trap is reaching for --hard. git reset --hard HEAD~1 undoes the commit and wipes the changes — the exact opposite of what you want here. For this panic it's always --soft. Want the changes unstaged instead (back to plain edits)? Use --mixed. Both keep your work; only --hard destroys it.

◆ claude codeNot sure which reset flag you ran? Ask it to read git reflog — it shows every move HEAD made, so even an accidental commit can be pointed back to.

oh no

The edits you wish you never made

When you edit a file but haven't committed, Git still has a clean copy of the last committed version in its back pocket. Your ugly edits only live in the file on disk — Git hasn't recorded them. "Getting the file back" isn't undoing anything deep; it's telling Git to overwrite the mess with the copy it already saved. The lesson that dropped my panic: nothing's lost until you commit, and even after you save garbage, the good version is one command away.

snap a file back to its committed state
$ git statusIf the file shows as 'modified' (red), your edits were never committed — the clean copy is safe. $ git restore path/to/file.txtThrow away your edits, pull back the last committed version of that one file. $ git restore --staged path/to/file.txtOnly if you already 'git add'-ed it (shows green). Un-stages it, then run the line above.

⚠ footgungit restore deletes your current edits with no trash can — if there's any chance you want a scrap of what you typed, copy it somewhere first. And it only rescues files you never committed. Once the bad version is committed, restore won't reach back past it — that's a job for revert or reflog.

◆ claude codeSay "I hate my changes to this file, give me back the committed version" — it reads git status, spots whether the file is staged, and runs the right restore so you don't guess which path you're on.

oh no

Committed straight to main

Nothing is broken. A commit on main is just a labeled save point, and the main label is one of the cheapest things to move. The work is safe in that commit — all you're doing is copying the label onto a new branch, then sliding main back one step to where it was.

move the commit onto a branch where it belongs
$ git switch -c feature-branchNew branch right here — it points at your commit, so the work is safe. $ git switch mainHop back to main so you can rewind it. $ git reset --soft HEAD~1Move main back one commit. --soft keeps the changes; they're already safe on feature-branch. $ git switch feature-branchBack to your branch — keep working like you meant to all along.

⚠ footgunThis rewinds local history, so it's only safe before you've pushed main. If the commit already went up, don't reset — run git revert HEAD instead, which adds a fresh commit that cancels the change without rewriting what others pulled.

◆ claude codeI had it read my reflog and confirm the commit was still local before touching reset, so I knew the rewind was safe.

oh no

The commits that "vanished" after a bad reset

The first time a hard reset ate my work, I was sure it was gone. It wasn't. Git almost never throws commits away — reset just moved the branch pointer backward, leaving the old commits floating, still on disk, just unlabeled. The reflog remembers every place HEAD has stood, so "vanished" really means "no longer pointed at." Find the old position, point a branch back at it.

recover floating commits via the reflog
$ git reflogEvery recent HEAD position, newest first. The line just before your bad reset is the one you want — note its short hash. $ git show a1b2c3dPeek at that hash to confirm it's the work you thought you lost, before touching anything. $ git switch -c rescue a1b2c3dSafest move: bring it back on a NEW branch, leaving your current one untouched. $ git reset --hard a1b2c3dOr, if you're sure: snap the current branch back. Only with a clean working tree.

⚠ footgunRunning git reset --hard to recover while you have uncommitted edits open — the hard reset wipes the working tree too, trading one loss for another. Recover onto git switch -c rescue <hash> first, look at it, then decide. And don't wait forever: unreachable reflog entries get pruned eventually (weeks, not months), so the rescue window isn't open indefinitely.

◆ claude codePaste your git reflog output and it points at the exact line your good commit lives on — no squinting at a wall of SHAs guessing which hash to recover.

oh no the scary one

You committed your .env (or an API key)

Git did exactly what you told it — it photographed every staged file, .env included, and froze it into history. The file isn't so much "in" the repo as photographed by it: deleting the line now doesn't remove it from the old snapshot. That's the part that trips everyone up — undoing the commit and scrubbing the secret from history are two separate jobs. And the first question isn't a Git question at all: did this leave your machine yet?

un-commit + ignore — secret was NOT pushed
$ git log --oneline -1Confirm the bad commit is the most recent one. $ git reset --soft HEAD~1Undo just that commit — files stay on disk, still staged, nothing lost. $ echo ".env" >> .gitignoreTell Git to stop tracking .env from now on. $ git restore --staged .envUnstage the secret so the next commit won't grab it again. $ git commit -m "ignore .env" -- .gitignoreCommit ONLY the ignore rule (the '-- .gitignore' keeps unrelated staged work out of this commit).

where did my secret go?  Your .env is intentionally still on disk — just untracked now. That's correct; you want your local env file. It's only gone from Git's tracking, not from your folder.

⚠ footgunThe trap is thinking this is enough after you've pushed. The moment a secret hits a shared remote, treat it as leaked — bots scrape public commits for keys within minutes. reset --soft only rewrites local history; it can't claw back what GitHub already has. So if it pushed: rotate the key first (revoke, regenerate), then clean history. And if the secret is buried several commits back or already shared, the real scrub tool is git filter-repo (or the BFG) — not git rebase -i, which blindly rewrites shared history.

◆ claude codeIt can read your git log, tell you whether the bad commit actually pushed, and walk the exact reset-or-rotate path for your case instead of guessing.

oh no

I pushed a broken commit and people may have pulled it

Here's what unstuck me: once a commit is on the remote and someone might have pulled it, the history isn't mine alone anymore. Rewriting it (reset, force-push) would yank the ground out from under everyone else's clone. The clean move is to add a new commit that cancels the old one out. git revert builds the inverse of the bad commit and stacks it on top — the broken change is gone, the timeline stays honest, everyone's pull still lines up.

cancel a shared commit safely
$ git log --oneline -5Find the broken commit, copy its short hash from the list. $ git revert <hash>Builds a new commit that undoes that one. An editor opens for the message — save and close. $ git pushA plain push, no force — the fix goes out as a normal commit everyone pulls cleanly.

⚠ footgunThe reflex is git reset + git push --force to make the bad commit "never happen." On a shared branch that rewrites history out from under your teammates — their next pull conflicts or silently drops the fix. Force-push is for branches only you touch. The second anyone else has the commit, revert is the safe path.

oh no

The pull that started a fight

A pull is two moves stitched together: fetch the remote work, then merge it into yours. The merge is where it bit me. Git tried to fold their changes into mine, hit spots where both sides edited the same lines, and stopped cold rather than guess. Those CONFLICT lines aren't broken code or lost work — they're Git handing you both versions and saying "I won't pick for you." Nothing's committed yet, so there's always a clean way back out.

bail out, or resolve and finish
$ git merge --abortThe panic button — rewinds the pull, puts you back exactly where you were, conflicts gone. $ git statusAfter aborting, confirms you're clean. Or if you want to push through: lists every file still in conflict. $ git restore --ours path/to/fileKeep YOUR version of one file (or --theirs for the incoming one). The standard "I want this side" idiom. $ git add . && git commitOnce you've removed the conflict markers and kept the lines you want, this finishes the merge.

⚠ footgunThe reflex is to delete the whole repo and re-clone. Don't — your unpushed commits live only on this machine and a fresh clone wipes them. git merge --abort is the real undo. Also: the <<<<<<< / ======= / >>>>>>> lines are Git's markers, not your code — leaving even one ships a broken file. And restoring or editing a file alone doesn't end the merge; you still need to commit (or --abort) to close it out.

◆ claude codeDrop a conflicted file in and ask what each side was trying to do — it reads both branches' intent so you resolve by meaning, not by guessing which block to keep.

oh no

The stash that vanished days ago

Nothing got lost. A stash is just a saved bundle of changes Git set aside on a hidden shelf so your working tree could go back to clean. It doesn't expire on its own. The panic comes from forgetting the shelf exists, not from Git throwing the work away. Every stash you ever made is still in a list, newest first, waiting to come back.

find it, preview it, bring it back safely
$ git stash listEvery stash, newest first, labeled stash@{0}, stash@{1}, … $ git stash show -p stash@{0}Preview the actual diff so you confirm it's the one you want before touching anything. $ git stash apply stash@{0}Drops the changes back into your files but KEEPS the stash on the shelf as a safety copy. $ git stash drop stash@{0}Deletes that one stash — only after you've confirmed the changes landed safely.

⚠ footgunThe reflex is git stash pop, which applies and deletes in one move. Using apply first, then drop once the files look right, means there's always a copy on the shelf if something goes sideways mid-conflict. One more: a stash comes back onto whatever branch you're standing on now, not the one you made it on — check where you are with git status first.

◆ claude codePaste git stash list and it reads the diffs, tells you which stash holds which work, and walks you through applying the right one without nuking the others.

oh no

"HEAD detached" and you're lost in space

Nothing broke. Detached HEAD just means you checked out a specific commit directly instead of a branch, so you're standing on a snapshot with no branch name attached. Git's fine — it's warning you that any new commits made here won't belong to a branch, so they'd be easy to lose. The fix is just deciding where you actually want to be.

re-attach to a branch
$ git statusConfirms the detached state and shows the commit you're sitting on. $ git switch -If you just want OUT — jumps back to the branch you were on before. $ git switch mainOr land on a named branch directly (swap main for yours). $ git switch -c rescue-branchIf you made commits here and want to KEEP them — names this spot as a branch so nothing's lost.

⚠ footgunThe trap is making commits while detached, then running git switch main to leave — those commits aren't on any branch and look gone. The order that saves you: if you did work here, git switch -c a-new-branch first to anchor it, then switch away. Already left and panicking? git reflog still shows the hash so you can recover it. Detached HEAD isn't the danger — leaving without naming your work is.

◆ claude codePaste the full git status and it reads which commit you're parked on, then tells you whether you have unsaved commits to rescue before switching away.

oh no

The branch I swore I was done with

Here's what calmed me down: deleting a branch doesn't delete the work. A branch is just a sticky note pointing at a commit. I tore off the note, but the commit is still in Git's history. The reflog records every place HEAD has been, so the commit my branch pointed at is still written down — I just read it back and stick a new note on it.

rebuild a deleted branch from the reflog
$ git reflogScroll for the line naming your branch, like 'commit: work on feature'. The 7-char code at the start is the commit. $ git switch -c feature-thing b12505dRebuild the branch — swap in your real name and the code you found. Recreates it exactly where it was. $ git log --oneline -1Confirm your commits are back — the top line should be the work you thought you lost.

⚠ footgunThe thing that almost tripped me up: if the branch was already merged when I deleted it, none of this is needed — the commits live on the branch I merged into, so I just keep working there. The reflog rescue is for branches deleted with unmerged work on them. And the reflog is local-only and gets pruned over time, so this works on the machine where the branch lived — not a fresh clone, and not forever.

◆ claude codeI had it read my reflog and tell me which line was the branch I deleted — saved me squinting at a wall of SHAs guessing which one was mine.

The one habit underneath all twelve

Look at the cards again and the same shape repeats: git status to see where you are, git reflog when something "disappeared," and a strong bias toward recovering onto a new branch instead of resetting in place. Almost nothing on this page is actually destructive except reset --hard and push --force — so those are the only two commands worth slowing down for.

What changed things for me wasn't memorizing the fixes. It was believing the premise: the work is usually still there, just unlabeled. Once you stop assuming Git deleted your stuff, the panic drops and the right command gets obvious. Steal what's useful here, and the next time the terminal yells in red, you'll already know it's a "phew," not an "oh no."

commit small, push often, and let the reflog be your safety net.
