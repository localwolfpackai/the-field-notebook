The two dials — ten moves so your AI feature doesn't cost a fortune or make people wait.

Last entry put your feature on a rubric so it ships good. This one is about the two numbers nobody warns a beginner about: what each call costs, and how long it makes someone wait. Both are dials, not fixed facts — and most of the times they're stuck at "expensive" and "slow," it's a choice you didn't know you were making. Here's how to read them and turn them down. Both models, move for move.

My first AI feature worked beautifully in the demo and arrived with a $400 surprise at the end of the month. I'd wired every request — including "what's 2+2"-tier questions — to the biggest, smartest model, then stuffed the entire knowledge base into every prompt, fresh, every time. It was correct. It was also slow enough that people stopped using it, and costly enough that I almost killed it. Nothing was broken. I just had both dials cranked to the wall and couldn't see the dials.

That's the thing about cost and latency: they're invisible until they're a problem, and by then they feel like a property of "using AI" rather than choices you made. They're choices. Cost is mostly which model you picked and how many tokens you sent it. Latency is mostly how big the job is and whether the user stares at a spinner or watches words appear. Every move below turns one of those two dials down without making the output worse.

Ten moves, each with a number, a one-line claim, real code, and a try-it crumb. The panel under this intro is live — pick a model tier for a job and watch the two dials move in real time. Smart isn't always right; cheap isn't always wrong. The whole skill is matching the dial to the job.

01

Every call has a price tag — and it's printed on the response, you just never looked. money

You pay per token, in and out. Every model response hands back a usage object telling you exactly how many of each you spent — and most beginners never read it once. Multiply input tokens by the input price, output tokens by the (usually higher) output price, and you have the real cost of that one call. Do it once and the abstract bill becomes a number you can actually steer.

cost.ts — the number was on the response all along
// Both SDKs hand back token counts. Price them yourself.
const msg = await client.messages.create({ /* … */ });

console.log(msg.usage);
// { input_tokens: 1840, output_tokens: 215 }

// Claude Haiku 4.5 list price (per million tokens):
const IN = 1.00 / 1_000_000;   // $1.00 / Mtok in
const OUT = 5.00 / 1_000_000;  // $5.00 / Mtok out

const cost = msg.usage.input_tokens  * IN
           + msg.usage.output_tokens * OUT;
console.log(`this call: $${cost.toFixed(5)}`);
// this call: $0.00292  ← times a million requests, that's $2,920
heads up
Output tokens almost always cost more than input — often 4–5×. So a chatty model that pads every answer isn't just annoying, it's the expensive one. Move 05 turns that into a lever.
02

Don't send a genius to do a clerk's job — the smartest model is the wrong default. model

The instinct is to reach for the biggest model so quality is never the problem. But most of what an app does is clerical: classify this, extract that, reformat this, answer a FAQ. A small fast model does clerical work perfectly — and a frontier model on the same task is slower, pricier, and no more correct. Reaching for the top tier by default is like couriering every envelope by helicopter.

List every model call your app makes and write one word next to each: clerk or thinker. Every "clerk" pointed at a frontier model is free money on the table — drop it a tier and watch nothing get worse.
03

Route by difficulty, not by default — let a cheap model triage before a smart one swings. backend

Once jobs split into clerk and thinker, you can pick the model per request instead of per app. The pattern is a tiny route() function: cheap tier for the easy 80%, escalate to the heavy tier only when the input is genuinely hard. You can route on something dumb-but-effective (length, a keyword, a category) or let the cheap model itself flag "this one's above my pay grade" and hand it up.

route.ts — one function decides the tier
// The whole optimization is choosing the model on purpose.
type Tier = "cheap" | "heavy";

const MODELS = {
  cheap: "claude-haiku-4-5",    // fast clerk
  heavy: "claude-sonnet-4-6",   // bring it out only when needed
};

function route(task: Task): Tier {
  if (task.kind === "classify") return "cheap";     // clerical
  if (task.kind === "extract")  return "cheap";
  if (task.input.length < 600)      return "cheap";     // small = easy, usually
  return "heavy";                              // the genuinely hard 20%
}

const answer = await client.messages.create({
  model: MODELS[route(task)],   // ← the dial, set per request
  max_tokens: 400,
  messages: [{ role: "user", content: task.input }],
});
heads up
Routing has a failure mode: sending a hard job to the cheap tier and shipping a worse answer to save a cent. That's exactly what Vol. 24's eval harness catches — run both tiers against your golden cases and let the score tell you where "cheap" stops being safe.
04

Cache the part of the prompt that never changes — stop paying to re-read your own instructions. money

Most prompts are a big fixed chunk — system instructions, a style guide, a knowledge base, a few examples — followed by one small variable bit (the user's actual question). You're paying full input price to send that fixed chunk on every single call. Prompt caching lets the provider remember it: mark the stable prefix once, and repeat calls read it from cache at a fraction of the price and latency. The bigger and more repeated your prefix, the more this saves.

cache.ts — mark the stable prefix, pay once
// Claude: cache_control on the block that doesn't change.
await client.messages.create({
  model: "claude-sonnet-4-6",
  system: [
    {
      type: "text",
      text: BIG_KNOWLEDGE_BASE,           // 20k tokens, same every call
      cache_control: { type: "ephemeral" },  // ← cache this
    },
  ],
  messages: [{ role: "user", content: userQuestion }],  // the only fresh part
});
// first call: writes the cache (small surcharge).
// every call after: reads it ~10× cheaper + faster, within the TTL.

Claude

Explicit: add cache_control to the block. You decide what's cacheable and the usage reports cache_read vs cache_creation tokens so you can see it working.

Gemini

Context caching via a cached-content handle you create once and reference by name — same idea, you register the big stable context and reuse it across calls.

a 20k-token prefix re-sent 1,000 times is 20M tokens you bought twice. cache it and that bill nearly vanishes.

05

Cap the output — max_tokens is a cost lever, not just a safety net. backend

Output tokens are the expensive ones, and a model with no ceiling will happily write you an essay when you wanted a sentence. Set max_tokens to the real size of the answer you need, and tell the model to be brief in the prompt. You cut cost and latency at the same time — fewer tokens to generate means fewer tokens to pay for and fewer to wait on. Two dials, one knob.

brief.ts — size the answer to the need
// A 1-word category does not need 1,024 tokens of headroom.
await client.messages.create({
  model: "claude-haiku-4-5",
  max_tokens: 8,          // ← the answer is one of six words. cap it.
  system: "Reply with ONLY the category name. No preamble, no punctuation.",
  messages: [{ role: "user", content: email }],
});
// "billing"   ← 1 output token instead of 60 tokens of "Sure! This email is about…"
try it
Audit your prompts for the phrase the model loves — "Sure, here's…", "I'd be happy to…". Every one of those is output tokens you're paying for and a user is waiting on. Add "answer directly, no preamble" and shrink max_tokens to fit.
06

Latency is felt, not measured — stream the answer so the wait stops feeling like a wait. frontend

Here's the quiet trick: you often can't make the model finish faster, but you can make it feel instant by showing the first words the moment they exist. The number that matters to a human isn't total time — it's time to first token. A four-second answer that starts streaming at 400ms feels alive; the same answer behind a spinner feels broken. This is Vol. 22's whole move, pointed at the latency dial.

stream.ts — first token fast, rest as it arrives
const stream = await client.messages.stream({
  model: "claude-sonnet-4-6",
  max_tokens: 400,
  messages: [{ role: "user", content: prompt }],
});

stream.on("text", (chunk) => {
  process.stdout.write(chunk);   // paint each token the instant it lands
});                              // TTFT ~0.4s — the wait is over before it began
heads up
Streaming doesn't lower cost or true latency — it lowers perceived latency, which is the one your users actually rate. Pair it with Move 02: a cheap model that streams beats a smart model behind a spinner for almost every interactive surface.
07

Batch the work nobody is waiting on — offline jobs don't need real-time prices. money

Not every call has a human tapping their foot. Nightly summaries, bulk tagging, re-embedding a corpus, backfilling data — that work has no latency requirement at all, so don't pay the real-time premium for it. Both providers offer a batch mode that runs jobs asynchronously, within a window, at a steep discount (often ~50%). If nobody's waiting, latency is free to spend — trade it for cost.

batch.ts — async work, discounted
// 10,000 product descriptions to tag overnight? Not a chat. Batch it.
const batch = await client.messages.batches.create({
  requests: products.map((p) => ({
    custom_id: p.id,
    params: {
      model: "claude-haiku-4-5",   // cheap tier + batch = floor price
      max_tokens: 40,
      messages: [{ role: "user", content: tagPrompt(p) }],
    },
  })),
});
// poll batch.id until done. ~50% off, because you traded "now" for "by morning."

interactive? stream it. overnight? batch it. the dial you don't need is the dial you sell.

08

Log usage on every call — you can't tune a dial you can't see. backend

You optimize what you measure. Wrap every model call so it records the model, the token counts, the latency, and the computed cost — one row per request. Now "the AI is expensive" becomes "the summarizer is 80% of the bill and it's on the heavy tier for no reason." A thin logging wrapper is the single highest-leverage thing in this whole entry, because it turns every other move from a guess into a measurement.

meter.ts — wrap once, see everything
export async function metered(model: string, params: any) {
  const t0 = performance.now();
  const res = await client.messages.create({ model, ...params });
  const ms = performance.now() - t0;

  log.insert({
    model,
    in_tok:  res.usage.input_tokens,
    out_tok: res.usage.output_tokens,
    cached:  res.usage.cache_read_input_tokens ?? 0,
    cost:    price(model, res.usage),   // Move 01's math, reused
    latency_ms: Math.round(ms),
    route:   params._route,             // which tier the router picked
  });
  return res;
}
// one dashboard query later: cost by feature, p95 latency by model. now you can aim.
try it
Before you optimize anything, ship the logger and let it run for a day. Then sort by total cost descending. The top two rows are your entire optimization to-do list — the rest is rounding error.
09

Set a budget the code enforces — a cap nobody trips is a hope, not a limit. polish

The $400 surprise happens because nothing in the code knows about money. Fix that: give each feature (or user, or tenant) a spend ceiling, increment it from the same usage you're already logging, and refuse the call when it's blown. A runaway loop, a scraper hammering your endpoint, a prompt-injection that makes the model talk forever — all of them hit a wall instead of a credit card. Same shape as Vol. 24's CI gate: a number, a bar, a hard stop.

budget.ts — the wall that stops the surprise
const DAILY_CAP = 25.00;  // dollars, per feature, per day

async function guarded(model: string, params: any) {
  const spent = await today.spend(params.feature);
  if (spent >= DAILY_CAP) {
    throw new Error(`budget hit: ${params.feature} spent $${spent.toFixed(2)}`);
  }
  const res = await metered(model, params);      // Move 08's wrapper
  await today.add(params.feature, price(model, res.usage));
  return res;
}
// now the worst case is a blocked request + an alert — not a four-figure invoice.

a budget in a spreadsheet is a wish. a budget in an if statement is a guardrail.

10

The two-dial test — could this call be cheaper or faster without getting worse? polish

That's the whole entry in one question, asked of every call your app makes. Could a smaller model do this job just as well? Is the fixed part of this prompt cached? Is the output capped to the answer's real size? Does the user see the first token fast, or stare at a spinner? If the honest answer to any of those is "no," you've found a dial stuck at the wall — and turning it down costs you nothing but the minute it takes. The eval harness from last entry is your safety net: change a dial, re-run the cases, ship only if the score holds.
