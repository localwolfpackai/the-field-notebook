The agent loop — build your first tool-using AI from scratch.

Everyone keeps saying "agents" like it's a black box you have to buy. It isn't. An agent is a while loop that can call your functions. That's the whole secret. This notebook builds one from a single API call up to a streaming CLI — no framework, no magic, just the loop and the four moves that make it work.

—Lupo · The Mess is the Method
Read · ~16 min Stack · Python + Claude API Assumes · you can run a .py file Voice · open-notebook, casual

I avoided building agents for way too long because the word sounded like a thing you needed a degree for. Then I read the actual loop and felt a little robbed — it's about fifteen lines. The model talks, you notice it asked for a tool, you run the tool, you hand the result back, you let it talk again. Repeat until it stops asking. That loop is the agent.

So this is me re-teaching it the way I wish someone had taught me: smallest possible pieces, real code you can paste, and a local scratch script at every step so you can watch it work before you trust it. By the end you'll have a tiny agent that can read files, do math, and tell you what it did — and you'll know exactly where every decision happens.

Examples are Python with the Claude API because that's my daily driver, but the shape is identical in TypeScript or with any model that does tool calling. Steal the loop. The language is a detail.

The build order ↓

  1. The mental model: agent = loop + tools
  2. code Hello, model — your first call
  3. concept Define a tool the model can ask for
  4. the loop The loop — run the tool, hand it back
  5. the loop Let it chain — multi-step on its own
  6. concept Stop conditions — no runaway loops
  7. code Structured output you can trust
  8. concept The open notebook — a test harness
  9. code Stream it so it feels alive
  10. ship it Wrap it as a CLI & ship

Before any code: the picture in your head.

you send message a task + the list of tools
→
model replies text, or "use this tool"
→
you run the tool feed result back → loop
→
model done final answer, no tool ask

the dashed box is the only part you write. everything else is the API.

01

Hello, model — the one call everything is built on. code

Before tools, before loops, get one round-trip working. Install the SDK, set your key, send a message, print the reply. If this runs, you have everything you need — the rest is just wrapping this call in logic.

setup 
$ pip install anthropic
$ export ANTHROPIC_API_KEY=sk-ant-...   # keep this out of your code
hello.py 
import anthropic

client = anthropic.Anthropic()  # reads the env var automatically

resp = client.messages.create(
    model="claude-sonnet-4-6",   # fast + cheap; bump to opus for hard reasoning
    max_tokens=1024,
    messages=[
        {"role": "user", "content": "In one sentence: what is an agent?"},
    ],
)

print(resp.content[0].text)

Two things to notice that trip up newcomers. The reply is a list of content blocks, not a string — that's why it's resp.content[0].text. And the conversation is stateless: the API remembers nothing between calls. You carry the history. Hold that thought — it's the entire reason the loop in step 04 looks the way it does.

try it ↳
Run it. Then change the model to claude-opus-4-8 and ask something genuinely hard. Same code, different brain. That swap is most of "tuning" in practice.
02

Define a tool — teach the model what it's allowed to ask for. concept

A "tool" is just a function you've described in JSON so the model knows it exists. You're not giving the model your code — you're giving it a menu. It reads the description, decides if it's relevant, and asks you to run it with specific arguments. The schema is the contract.

tools.py 
# 1. the menu entry the model reads
TOOLS = [
    {
        "name": "calculate",
        "description": "Evaluate a basic arithmetic expression. "
                       "Use for any math the user asks for.",
        "input_schema": {
            "type": "object",
            "properties": {
                "expression": {"type": "string",
                               "description": "e.g. '42 * (3 + 1)'"},
            },
            "required": ["expression"],
        },
    },
]

# 2. the actual code that runs when the model picks it
def calculate(expression: str) -> str:
    return str(eval(expression, {"__builtins__": {}}))  # sandboxed-ish

# 3. a lookup so the loop can find the function by name
DISPATCH = {"calculate": calculate}

The description field is doing more work than it looks like. The model decides whether to call a tool based almost entirely on that sentence. Vague description, and it'll guess or skip it; sharp description with a "use this when…" hint, and it reaches for the right tool at the right time. Treat tool descriptions like prompt engineering, because they are.

heads up ↳
eval is fine for a toy. The instant a tool touches the real world — files, shell, HTTP — validate the input yourself before running it. The model proposes; your code disposes. Never run a tool argument you wouldn't run by hand.
03

The loop — run the tool, hand the result back. the loop

Here's the heart of it. You send the message with the tools attached. If the model just answers, you're done. If it asks for a tool, its reply comes back with stop_reason == "tool_use". You find the tool-use blocks, run them, and append the results as a new user message. Then you call again. That append-and-call-again is the loop.

agent.py — the core 
from tools import TOOLS, DISPATCH

messages = [{"role": "user", "content": "What is 18% of 250, plus 12?"}]

resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=1024,
    tools=TOOLS, messages=messages,
)

if resp.stop_reason == "tool_use":
    # 1. keep the model's turn in the history (required!)
    messages.append({"role": "assistant", "content": resp.content})

    # 2. run every tool it asked for, collect the results
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            output = DISPATCH[block.name](**block.input)
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,   # must match the request
                "content": str(output),
            })

    # 3. hand results back as a user turn, ask again
    messages.append({"role": "user", "content": results})
    resp = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=1024,
        tools=TOOLS, messages=messages,
    )

print(resp.content[0].text)
# → "18% of 250 is 45, plus 12 is 57."

Read step 1 again, because it's the bug everyone hits: you have to append the model's own tool-request turn to the history before you append your results. Skip it and the API rejects the next call — a tool_result has to answer a tool_use that's actually in the transcript. The tool_use_id is the thread that ties them together.

that's a working agent. one tool, one round-trip. everything after this is making it loop and behave.

04

Let it chain — turn the if into a while. the loop

Step 03 handled one tool call. Real tasks need several in a row — read a file, then count something, then answer. The fix is almost too simple: replace the if with a while. Keep calling and feeding results back until the model stops asking for tools. Now it can plan its own multi-step path.

agent.py — the real loop 
def run_agent(task: str) -> str:
    messages = [{"role": "user", "content": task}]

    while True:
        resp = client.messages.create(
            model="claude-sonnet-4-6", max_tokens=1024,
            tools=TOOLS, messages=messages,
        )

        # no tool requested → the model is done talking
        if resp.stop_reason != "tool_use":
            return resp.content[0].text

        messages.append({"role": "assistant", "content": resp.content})

        results = []
        for block in resp.content:
            if block.type == "tool_use":
                print(f"  🔧 {block.name}({block.input})")  # watch it think
                output = DISPATCH[block.name](**block.input)
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": str(output),
                })

        messages.append({"role": "user", "content": results})

That print line is doing a lot for fifty characters. Watching the tool calls scroll by is how you learn what the model is actually reasoning about — and it's the first thing you'll reach for when an agent does something weird. Cheap observability beats clever debugging.

try it ↳
Add a second tool — a read_file(path) — to your TOOLS list and DISPATCH. Then ask: "How many import lines are in agent.py?" Watch it read, then count. That two-step with zero extra orchestration is the whole point.
05

Stop conditions — because while True is a loaded gun. concept

An unbounded loop plus a model that can get confused equals a meter that spins forever. Three guardrails turn the toy into something you'd actually leave running: a hard step cap, a missing-tool guard so a typo'd tool name doesn't crash you, and a try/except so one broken tool becomes feedback instead of a stack trace.

guardrails 
def run_agent(task: str, max_steps: int = 10) -> str:
    messages = [{"role": "user", "content": task}]

    for step in range(max_steps):           # ← hard cap, not while True
        resp = client.messages.create(
            model="claude-sonnet-4-6", max_tokens=1024,
            tools=TOOLS, messages=messages,
        )
        if resp.stop_reason != "tool_use":
            return resp.content[0].text

        messages.append({"role": "assistant", "content": resp.content})
        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            try:
                fn = DISPATCH.get(block.name)
                if fn is None:
                    out = f"Error: no tool named {block.name}"
                else:
                    out = str(fn(**block.input))
            except Exception as e:
                out = f"Error: {e}"          # hand the error back as feedback
            results.append({"type": "tool_result",
                            "tool_use_id": block.id, "content": out})
        messages.append({"role": "user", "content": results})

    return "Hit the step limit without finishing."

The quietly clever bit: when a tool throws, you don't crash — you pass the error message back as the tool result. The model reads "Error: file not found" and adjusts, often retrying with a corrected path. Errors become part of the conversation. That single habit is what makes agents feel resilient instead of brittle.

06

Structured output — get JSON you can actually parse. code

Sometimes you don't want a chat — you want clean data. The reliable way isn't "please reply in JSON" and hope. It's to define a tool whose schema is your data shape, then force the model to call it with tool_choice. Now the SDK hands you a validated object every time, not a string you have to regex.

extract.py 
SCHEMA = [{
    "name": "save_contact",
    "description": "Record the structured contact details.",
    "input_schema": {
        "type": "object",
        "properties": {
            "name":  {"type": "string"},
            "email": {"type": "string"},
            "role":  {"type": "string"},
        },
        "required": ["name", "email"],
    },
}]

resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=512,
    tools=SCHEMA,
    tool_choice={"type": "tool", "name": "save_contact"},  # force it
    messages=[{"role": "user", "content":
        "Hi, I'm Dana Reyes, lead PM, dana@acme.co"}],
)

data = resp.content[0].input   # already a dict, schema-validated
print(data)
# → {'name': 'Dana Reyes', 'email': 'dana@acme.co', 'role': 'lead PM'}

This is the move that turns an LLM into a parser you can wire into real pipelines — messy email in, typed record out. Same trick scales to classification, data cleanup, pulling fields out of PDFs. Whenever you catch yourself about to write "respond only with JSON," reach for a forced tool instead.

07

The open notebook — a scratch harness you keep open. concept

This is the habit that made me actually fast: a tiny test file I run on every change, with a few fixed prompts and a clock. Not a unit-test suite — a notebook. It tells me at a glance whether a tweak to a tool description helped or quietly broke something. Cheap, ugly, indispensable.

scratch.py 
import time
from agent import run_agent

CASES = [
    ("What is 18% of 250, plus 12?",            "57"),
    ("How many import lines in agent.py?",        None),
    ("Read tools.py and list the tool names.",    "calculate"),
]

for prompt, expect in CASES:
    t = time.perf_counter()
    out = run_agent(prompt)
    dt = time.perf_counter() - t
    hit = "·" if expect is None else ("✓" if expect in out else "✗")
    print(f"{hit}  {dt:4.1f}s  {prompt[:38]:38}  → {out[:46]}")
$ python scratch.py 
✓   1.2s  What is 18% of 250, plus 12?            → 18% of 250 is 45, plus 12 is 57.
·   2.8s  How many import lines in agent.py?      → There are 2 import lines.
✓   3.1s  Read tools.py and list the tool names.  → The tools are: calculate, read_file.

Run this after every change. When a "tiny" edit to a tool description flips a ✓ to ✗, you'll catch it in seconds instead of in production. The timer column is a bonus — it's how you notice you accidentally put the slow model on the hot path. Keep the notebook open in a split pane and let it be your conscience.

heads up ↳
Models aren't perfectly deterministic, so an occasional flake is normal — don't chase a single ✗ on a fuzzy case. Watch the pattern across runs, and reserve hard assertions for the cases that genuinely should be stable (like the math).
08

Stream it — make the wait feel like thinking, not lag. code

A four-second silent pause feels broken. The same four seconds with text appearing word by word feels alive. Streaming is a one-line change to how you read the response — use messages.stream() and print the text deltas as they arrive.

streaming a reply 
with client.messages.stream(
    model="claude-sonnet-4-6", max_tokens=1024,
    messages=[{"role": "user", "content": "Explain the agent loop to a 12-year-old."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)   # tokens land as they come

final = stream.get_final_message()      # full object after, for the loop

For a tool-using agent you mostly stream the final answer — the one after the tools have run — while keeping the intermediate tool-handling exactly as before. get_final_message() hands you the same complete object the non-streaming call returned, so the loop logic from step 05 doesn't change at all. You're only changing how the last turn is rendered.

streaming is pure UX. the model isn't faster — it just stops feeling stuck.

09

Wrap it as a CLI — from script to thing you actually use. ship it

The last yard is making it runnable without editing the file. Forty lines of glue: a system prompt that sets the agent's job, an input loop, and a way to quit. This is the version that lives in my ~/bin and gets used on real Tuesdays.

cli.py 
import sys
from agent import run_agent

SYSTEM = (
    "You are a terse local assistant with file and math tools. "
    "Prefer using a tool over guessing. Show your final answer plainly."
)

def main():
    print("agent ready — Ctrl-C to quit\n")
    while True:
        try:
            task = input("you › ").strip()
        except (EOFError, KeyboardInterrupt):
            print("\nbye"); return
        if not task:
            continue
        answer = run_agent(task, system=SYSTEM)
        print(f"\nai  › {answer}\n")

if __name__ == "__main__":
    main()

Pass that system string into your messages.create calls via the system= parameter — it's the agent's job description and the cheapest lever you have on behavior. Then chmod +x, drop a shebang on top, symlink it into your path, and you've got a personal agent you built end to end and understand every line of.

heads up ↳
Once this is a habit, add prompt caching: mark your big static system prompt and tool definitions with "cache_control": {"type": "ephemeral"}. The model re-reads them every loop turn — caching makes that cheap and fast. It's the single highest-leverage optimization for a chatty agent.

One-page recap.

The whole agent, on a sticky note.

The mental model

  • agent= while loop + tools
  • youcarry the message history
  • tool= a JSON-described function
  • tool_usemodel asks; you run it
  • tool_resultyour answer, back to it
  • stop_reasonnot "tool_use" → done

The loop, in order

  • 1send task + tools
  • 2tool_use? append assistant turn
  • 3run tools, collect results
  • 4append results as user turn
  • 5call again — repeat
  • 6else: return the text

Don't-skip guardrails

  • max_stepscap the loop, never while True
  • try/excepterrors → feedback, not crash
  • .get(name)guard unknown tool names
  • validatecheck args before running
  • print 🔧log every tool call

Level-ups

  • tool_choiceforce structured JSON out
  • scratch.pya notebook you run every change
  • .stream()make waits feel alive
  • system=the agent's job description
  • cache_controlcache prompt + tools
