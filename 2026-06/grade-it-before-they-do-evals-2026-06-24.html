Grade it before they do — ten moves for putting your AI feature on a rubric.

Last entry got the model to hand you a clean object. This one asks the next question: is the object any good? If you don't have an answer, your users are running the eval for you — live, in production, one-star at a time. Here's the smallest harness that grades the model first: golden cases, a judge, a pass bar, and a gate that stops a bad release. Both models, move for move.

The most expensive bug I ever shipped looked perfect in the one example I tried. A support-reply generator — warm, helpful, fluent. I clicked "looks good," merged it, and went to bed. By morning it had confidently invented a refund policy that didn't exist, in three real conversations. The output read great. It was just wrong, and I had no way to have known, because my entire test suite was one happy click.

That's the gap an eval fills. A regular test asks "did the function return 4?" An eval asks "is this generated answer good enough to show a human?" — a fuzzier question with no single right string. The trick is to make it answerable anyway: write down what "good" means as a rubric, run the model against a handful of golden cases, and score each one. You're not chasing perfection. You're building a number that drops when you break something.

Below, ten moves get you from zero to a gate. Each has a number, a one-line claim, real code, and a try-it crumb. The panel under this intro is live — pick a model answer, hit Grade, and watch the rubric mark it pass or fail, one criterion at a time. That's the whole loop: output in, verdict out.

01

An eval is just a graded vibe-check — you already do it by hand, ten times a day, badly. model

Every time you read a model's output and think "yeah, ship it," you ran an eval. The problem isn't that you judge — it's that you judge once, on one example, from memory, with no record. Change the prompt next week and you have no idea whether you made it better or quietly broke the thing that worked.

An eval harness is that same judgment, written down and made repeatable. You fix the inputs (the cases), fix the standard (the rubric), and let a script produce a score you can compare across versions. Nothing exotic — it's a test suite for outputs that don't have one exact right answer.

heads up
Don't confuse this with a unit test. A unit test asserts sum(2,2) === 4. An eval asks "is this answer good?" — graded, not asserted. You'll use both: deterministic checks where you can, judged checks where you can't.
02

Write five golden cases, not five hundred — a tiny set you trust beats a huge one you don't. design

The blank-page fear is "I need a thousand examples." You don't. Start with five to ten golden cases — an input and a note on what a great answer looks like. Cover the boring happy path, then the two or three places you already know the model gets weird: the empty input, the hostile user, the question it should refuse. Those edges are where regressions hide.

cases.ts — the golden set is the spec
// Each case = an input + what "good" means for it.
// This file IS your definition of done. Grow it by hand.
export const cases = [
  {
    id: "happy-path",
    input: "Where is my order #4821?",
    expect: "Looks up the order, gives status, stays factual.",
  },
  {
    id: "no-such-policy",
    input: "Can I get a refund after 90 days?",
    expect: "Says it can't confirm; does NOT invent a policy.",  // my real bug
  },
  {
    id: "hostile",
    input: "your product is garbage, fix it now",
    expect: "Stays calm, offers a real next step, no grovelling.",
  },
  {
    id: "empty",
    input: "",
    expect: "Asks a clarifying question, doesn't hallucinate intent.",
  },
];
try it
Seed the file from your own worst moments. The fastest way to a useful eval set is to write down the three outputs that have already embarrassed you. Those are worth more than fifty synthetic prompts.
03

Turn "good" into a rubric — vague taste becomes a checklist a machine can run. design

"Is it good?" is unanswerable. "Does it cite a real order number? Does it avoid inventing policy? Is it under 120 words? Is the tone calm?" — those are four yes/no questions, and four yes/no questions are a rubric. The move is to decompose the fuzzy whole into specific, independent criteria. Grade each one on its own; never ask for a single holistic vibe-score, because that's just the original problem in a trench coat.

rubric.ts — one criterion, one question
export const rubric = [
  { key: "grounded",  ask: "Every fact is supported by the input — no invented policy or numbers." },
  { key: "on-task",   ask: "Answers what was actually asked, not a nearby question." },
  { key: "safe",      ask: "Refuses or defers when it should; no confident guessing." },
  { key: "tone",      ask: "Calm and professional, even to a hostile user." },
  { key: "concise",   ask: "Under ~120 words; no filler or restated question." },
];
// each one is independently true/false. that's the whole design.

one fuzzy score hides failures. five sharp ones expose exactly which one broke.

04

The cheap checks run first — half your rubric needs no model at all. backend

Before you spend a single token on a judge, run the criteria a plain function can answer. Length, format, banned phrases, "does it contain the order number that was in the input," valid JSON, no leaked system prompt — these are deterministic, instant, and free. Code-graded checks are faster and more reliable than any LLM judge, so push everything you can down to this layer.

checks.ts — deterministic first, judge second
// No model needed. Fast, free, never flaky.
export function codeChecks(answer: string, input: string) {
  return {
    concise:    answer.split(/\s+/).length <= 120,
    noFiller:   !/as an ai|i cannot stress|in today's world/i.test(answer),
    onOrder:    !/#\d+/.test(input) || answer.includes(input.match(/#\d+/)![0]),
    noLeak:     !answer.includes("system prompt"),
  };
}
// run these BEFORE the judge — if length already fails,
// you don't need to pay a model to tell you it's verbose.
try it
Sort your rubric into two piles: code-graded (length, format, contains-X) and judge-graded (grounded, on-task, tone). Anything that can be a regex should never be a model call.
05

Claude as judge — the model that wrote it can't grade it, so bring in a second one. claude

For the fuzzy criteria, you let a model grade the answer — "LLM-as-judge." The one rule that makes it work: separate the doer from the grader. A model will happily praise its own output even when it's mediocre, so the judge gets only the rubric and the answer, never the ego of having authored it. Force a structured verdict (one boolean per criterion) so you get data, not a paragraph. That's last entry's whole trick, pointed at quality control.

judge.ts — Claude, tool-forced verdict
import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();

export async function judge(answer: string, rubric: Crit[]) {
  const msg = await client.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 400,
    system: "You are a strict grader. Judge ONLY against the rubric. " +
            "You did not write this answer. Default to false if unsure.",
    tools: [{
      name: "verdict",
      description: "Return one boolean per rubric criterion, plus a reason.",
      input_schema: {
        type: "object",
        properties: Object.fromEntries(rubric.map(c => [
          c.key, { type: "object", properties: {
            pass:   { type: "boolean" },
            reason: { type: "string" },
          }, required: ["pass","reason"] },
        ])),
        required: rubric.map(c => c.key),
      },
    }],
    tool_choice: { type: "tool", name: "verdict" },  // no prose escape
    messages: [{ role: "user", content:
      `RUBRIC:\n` + rubric.map(c => `- ${c.key}: ${c.ask}`).join("\n") +
      `\n\nANSWER TO GRADE:\n${answer}` }],
  });
  return msg.content.find(b => b.type === "tool_use")!.input;  // typed verdict
}

"you did not write this answer" — one line that kills the self-praise problem.

06

Gemini as judge — same contract, and a flash model is cheap enough to grade the whole set. gemini

The judge doesn't have to be expensive. Grading is a smaller job than generating, so a fast, cheap model is usually the right call — you're running it across every case on every commit. Gemini takes the rubric the same way last entry's cards did: a responseSchema that forces one boolean per criterion, parsed once. Pick whichever judge you trust; the harness around it never changes.

judge.gemini.ts — responseSchema verdict
import { GoogleGenerativeAI, SchemaType } from "@google/generative-ai";
const genAI = new GoogleGenerativeAI(process.env.GEMINI_API_KEY);

const model = genAI.getGenerativeModel({
  model: "gemini-2.5-flash",            // cheap + fast = grade the whole set
  generationConfig: {
    responseMimeType: "application/json",
    responseSchema: {
      type: SchemaType.OBJECT,
      properties: {
        grounded: { type: SchemaType.BOOLEAN },
        onTask:   { type: SchemaType.BOOLEAN },
        safe:     { type: SchemaType.BOOLEAN },
        tone:     { type: SchemaType.BOOLEAN },
      },
      required: ["grounded","onTask","safe","tone"],
    },
  },
});

const res = await model.generateContent(prompt);
const verdict = JSON.parse(res.response.text());  // { grounded: true, ... }

Claude judge

Tool-forced verdict + a reason per criterion. Reach for it when the call is subtle — tone, nuance, "is this subtly wrong."

Gemini judge

Schema-forced booleans, flash-cheap. Reach for it for volume — grading hundreds of cases on every commit without a bill spike.

the harness doesn't care who judges. swap the model, keep the loop.

07

Score the set, set a pass bar — one number you can watch move. backend

Now roll it up. Run every case through the code checks and the judge, count the criteria that passed, divide by the total. That's your score. Pick a bar — say 90% — below which a build does not ship. The number itself matters less than the direction: when you change a prompt and the score drops, you just caught a regression before a user did. That's the entire payoff.

run-evals.ts — the whole harness, one loop
import { cases } from "./cases";
import { rubric } from "./rubric";
import { generate } from "../feature";   // the thing under test
import { judge }    from "./judge";

let pass = 0, total = 0;
for (const c of cases) {
  const answer  = await generate(c.input);   // run YOUR feature
  const verdict = await judge(answer, rubric); // grade it
  for (const { key } of rubric) {
    total++;
    if (verdict[key].pass) pass++;
    else console.log(`✗ ${c.id} / ${key}: ${verdict[key].reason}`);
  }
}

const score = pass / total;
console.log(`score: ${(score*100).toFixed(1)}%`);
if (score < 0.9) process.exit(1);   // ← the bar. fail the build.
heads up
Watch the per-criterion failures, not just the headline number. "Score dropped to 82%" is a shrug; "grounded failed on the refund case" is a bug report that tells you exactly what to fix.
08

Gate the release in CI — an eval nobody runs is a journal entry, not a guardrail. ci

The harness only protects you if it runs without you remembering to run it. Wire it into the same place your tests live — a GitHub Actions step on every pull request. Because run-evals exits non-zero below the bar, a regression turns the check red and blocks the merge. The eval stops being something you do and becomes something the repo enforces.

.github/workflows/evals.yml
name: evals
on: [pull_request]
jobs:
  grade:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx tsx evals/run-evals.ts   # non-zero below the bar → red ✗
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
try it
Add required status checks on your main branch so the eval job has to pass before anyone can merge. Now "the score went down" isn't a Slack message someone might miss — it's a wall.
09

Every prod bug becomes a new case — the set grows from reality, not imagination. polish

Here's the habit that compounds. When something slips through to a user — the invented refund policy, the weird tone, the truncated answer — don't just fix it. Add it to cases.ts first, watch the eval fail, then fix until it passes. Now that exact failure can never come back silently. Your golden set stops being a guess about what might break and becomes a memory of everything that already did.

cases.ts — a bug report, frozen into a test
// 2026-06-22: shipped. invented a "loyalty discount" that
// doesn't exist. caught by a customer, not by us. never again:
{
  id: "no-loyalty-discount",
  input: "Do I get a loyalty discount on this?",
  expect: "Says it can't confirm discounts; does not invent one.",
  regression: true,   // ← born from a real incident
},

this is the loop that makes the harness smarter than you are. let it.

10

The trust test — would you let this feature answer a real user without you reading it first? polish

That's the whole bar, same as last entry, pointed one level up. If your golden set covers the ways it fails, your rubric grades the things that matter, and the gate blocks a bad score from shipping — then yes, you can let it run unwatched, because the harness is watching. If you still feel the need to read every output by hand before it goes live, you've found the criterion your rubric is missing. Go add it as a case.
