Prompt → config → UI — let a model drive your frontend.

Most people bolt a chat box onto a finished app and call it "AI." There's a better seam. Have the model return structured JSON — a little blueprint of what the page should be — and let a plain renderer turn that into real React. The model decides what; your components decide how it looks. This notebook builds the whole loop in nine moves: schema first, endpoint second, renderer third, a scratch script at every stop, and a one-line swap between Claude and Gemini at the end.

—Lupo · The Mess is the Method
Read · ~17 min Stack · Next.js + Claude / Gemini Assumes · you can run npm run dev Voice · open-notebook, casual

The thing that finally made AI features click for me was realizing the model doesn't have to write your markup. It just has to fill in a form you designed. Give it a tight schema — "a page has a hero, some cards, and a CTA" — and ask for JSON that fits. You get back data, not HTML. And data is the friendliest thing a frontend can receive: you validate it, you render it, you style it with components you already trust.

That split is the whole trick. Last notebook (Vol. 11) was about directing Claude's taste inside Artifacts. This one is the engineering version: the model is a backend that returns a layout spec, and your job is the contract between them. Once that contract holds, you can swap models, cache responses, add fields, and never touch the render layer.

Code is TypeScript + Next.js because it's the path of least resistance for "model on the server, UI in the browser." But the pattern is language-agnostic. The schema is the product. Everything else is plumbing.

01

The pattern: treat the model like a JSON backend. concept

Here's the reframe that pays for the whole notebook. A chatbot answers in prose. A backend answers in a shape you defined. We want the second one. So instead of "write me a landing page," the real instruction to the model is: "fill out PageConfig for this request, and return only that."

Why this beats asking for HTML directly: HTML from a model is a liability. It can inject a class you don't have, an inline style that breaks your theme, a tag your sanitizer hates. JSON can't do any of that — it's inert data until your code decides what a "hero" block means. You keep the taste. The model brings the content and the arrangement.

Two ways to ask — same prompt, very different outcomes.

✗ "Write the page"

  • Model returns a wall of HTML/CSS
  • Off-brand spacing, random colors
  • You parse strings to fix it
  • Every model writes markup differently

✓ "Fill the config"

  • Model returns typed JSON
  • Your components own the look
  • You validate one object
  • Swap models, output stays the same shape
frame ↳
For the rest of this build, whenever you're tempted to ask a model for "the page," ask for the data that describes the page instead. That single habit is most of the battle.
02

The contract — design the schema before you touch a model. concept

The schema is the product. Spend your first twenty minutes here, not in the prompt. I write it as a Zod schema because Zod gives me three things at once: TypeScript types for the frontend, runtime validation for the response, and a JSON Schema I can hand to the model. One source of truth, three jobs.

lib/schema.ts 
import { z } from "zod";

// A block is one chunk of the page. Start with three.
const Hero = z.object({
  type:     z.literal("hero"),
  heading:  z.string().max(80),
  subhead:  z.string().max(160),
});

const Cards = z.object({
  type:  z.literal("cards"),
  items: z.array(z.object({
    label: z.string(),
    body:  z.string().max(120),
  })).min(2).max(4),
});

const Cta = z.object({
  type:  z.literal("cta"),
  label: z.string().max(32),
  href:  z.string(),
});

// The page is an ordered list of blocks. That's the contract.
export const PageConfig = z.object({
  title:  z.string(),
  blocks: z.array(z.discriminatedUnion("type", [Hero, Cards, Cta])),
});

export type PageConfig = z.infer<typeof PageConfig>;

Notice the constraints: max(80) on the heading, min(2).max(4) on the cards. Those aren't decoration — they're how you keep a model from handing you a 300-character headline that blows up your hero. The schema is also your design system's bouncer.

small schema first. you can always add a block type later — discriminated unions make it painless.
03

The endpoint — one route, one job. api

Now a single server route: take the user's prompt, ask the model to fill the config, return JSON. Keep it boring. No streaming yet, no model-swap yet — just prove the round trip. This is a Next.js App Router handler, but it's a plain function; the shape is identical in Express or a Cloudflare Worker.

app/api/generate/route.ts 
import Anthropic from "@anthropic-ai/sdk";
import { PageConfig } from "@/lib/schema";
import { SYSTEM, configTool } from "@/lib/prompt";

const anthropic = new Anthropic();

export async function POST(req: Request) {
  const { prompt } = await req.json();

  const msg = await anthropic.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 1200,
    system: SYSTEM,
    tools: [configTool],              // ← defined in step 4
    tool_choice: { type: "tool", name: "emit_page" },
    messages: [{ role: "user", content: prompt }],
  });

  // the model "called" our tool — the args ARE the config
  const block = msg.content.find((b) => b.type === "tool_use");
  const parsed = PageConfig.safeParse(block?.input);

  if (!parsed.success) {
    return Response.json({ error: "bad config" }, { status: 422 });
  }
  return Response.json(parsed.data);
}

Two design choices worth naming. One: the API key comes from the environment, never the client — the model call lives on the server so the secret stays there. Two: we safeParse before we trust anything. A 422 here is a feature, not a failure; it means the renderer will only ever see data that fits the contract.

heads up ↳
Set ANTHROPIC_API_KEY in .env.local and never commit it. The SDK reads it automatically — that's why new Anthropic() takes no args. Same story for Gemini's key in step 8.
04

Force valid JSON, every single time. api

The quiet hero of this whole pattern is tool use (a.k.a. function calling). Instead of begging the model in prose to "return JSON and nothing else," you hand it a tool whose input schema is your config. The model fills the tool's arguments. You get structured data by construction — no markdown fences to strip, no "Sure! Here's your JSON:" preamble to regex away.

lib/prompt.ts 
import { zodToJsonSchema } from "zod-to-json-schema";
import { PageConfig } from "./schema";

// the contract, restated as a tool the model can "call"
export const configTool = {
  name: "emit_page",
  description: "Return the page as a PageConfig object. Pick block "
    + "types that fit the request. Keep copy tight and concrete.",
  input_schema: zodToJsonSchema(PageConfig),
};

export const SYSTEM = `You are a layout author.
- Use ONLY the block types in the schema.
- Write specific copy, never lorem ipsum.
- Order blocks: hero first, cta last.
- If the request is vague, make one tasteful choice and commit.`;

The zodToJsonSchema call means your tool definition can never drift from your validator — they're generated from the same Zod object. Change a max() in step 2 and both the model's instructions and your runtime check update together. That's the kind of coupling you actually want.

why ↳
tool_choice: { type: "tool", name: "emit_page" } from step 3 forces the call. The model can't wander off into chat — its only move is to fill your form. That one line removes a whole class of "the JSON had a paragraph glued to the front" bugs.
05

The renderer — map config to components. frontend

This is the part that feels like magic but is the most boring code in the repo — and that's the point. A lookup table from block.type to a component. Each block type is a small, dumb, well-styled component you already know how to build. Add a new block type? Write one component, add one line to the registry. Nothing else changes.

components/page-renderer.tsx 
import type { PageConfig } from "@/lib/schema";
import { Hero, Cards, Cta } from "./blocks";

// the whole "engine": one map, type → component
const registry = {
  hero:  Hero,
  cards: Cards,
  cta:   Cta,
} as const;

export function PageRenderer({ config }: { config: PageConfig }) {
  return (
    <main>
      {config.blocks.map((block, i) => {
        const Block = registry[block.type];
        // @ts-expect-error — discriminated union narrows per type
        return <Block key={i} {...block} />;
      })}
    </main>
  );
}

The blocks themselves are just components with your tokens baked in — the model supplies heading and items, you supply the spacing, type scale, and color. Here's roughly what the dog-café prompt renders into once the config flows through:

localhost:3000
Bark & Brew

Cold brew for you, a water bowl for them. Open 7–3, daily.

cardPatio seating
cardHouse oat-milk
cardPup menu
Reserve a table →
one config object → this. styled by your components, not the model.

the registry is your real moat. taste lives in the blocks; the model just fills them.

06

Wire the prompt box to the route. frontend

Now the front door: a text box, a button, and a fetch. Type a request, POST it to /api/generate, drop the returned config into state, render it. This is the smallest possible client — loading and error states get real attention in step 9; here we just close the loop so you can see it move.

app/page.tsx 
"use client";
import { useState } from "react";
import { PageRenderer } from "@/components/page-renderer";
import type { PageConfig } from "@/lib/schema";

export default function Home() {
  const [prompt, setPrompt] = useState("");
  const [config, setConfig] = useState<PageConfig | null>(null);
  const [busy, setBusy] = useState(false);

  async function generate() {
    setBusy(true);
    const res = await fetch("/api/generate", {
      method: "POST",
      body: JSON.stringify({ prompt }),
    });
    setConfig(await res.json());
    setBusy(false);
  }

  return (
    <>
      <input value={prompt} onChange={(e) => setPrompt(e.target.value)} />
      <button onClick={generate} disabled={busy}>
        {busy ? "thinking…" : "build it"}
      </button>
      {config && <PageRenderer config={config} />}
    </>
  );
}

That's the entire user-facing app. Box in, page out. Everything interesting already happened on the server and in the renderer — which is exactly the separation you want. The client stays thin enough to rewrite in an afternoon.

07

The open notebook — a scratch tester you run locally. local

Before I trust any of this in the browser, I poke at it from a throwaway script. It's faster than clicking, it shows me the raw config, and it's where I catch a schema that's too loose or a prompt that's too vague. Keep a scratch/ folder. This file lives there and never ships.

scratch/try.ts — run with: npx tsx scratch/try.ts 
import { PageConfig } from "../lib/schema";

const prompts = [
  "landing page for a dog café in San Diego",
  "signup page for a budgeting app, friendly tone",
  "",                          // ← edge case: empty prompt
  "a;lksdjf zzz 9999",           // ← edge case: garbage
];

for (const prompt of prompts) {
  const res = await fetch("http://localhost:3000/api/generate", {
    method: "POST",
    body: JSON.stringify({ prompt }),
  });
  const data = await res.json();

  // re-validate client-side so the test is honest
  const ok = PageConfig.safeParse(data).success;
  console.log(
    `[${ok ? "PASS" : "FAIL"}] "${prompt.slice(0, 28)}"`,
    `→ ${data.blocks?.length ?? 0} blocks`,
  );
}
output 
[PASS] "landing page for a dog café"  → 3 blocks
[PASS] "signup page for a budgeting"  → 3 blocks
[PASS] ""                             → 2 blocks  # model still picked something sane
[FAIL] "a;lksdjf zzz 9999"            → 0 blocks  # 422 — caught it

That last line is the whole reason to write the script. Garbage in didn't crash the app or render a broken page — it tripped the validator and came back as a clean 422. Now I know the failure mode before a real user finds it. The notebook isn't a test suite; it's a place to be curious on purpose.

try it ↳
Add a prompt that should break your schema — ask for "twelve cards" when you capped it at four. Watch the model either trim to four or the validator reject it. Either way, you learn where your contract actually holds.
08

Swap the engine — Claude ↔ Gemini behind one interface. api

Here's the payoff for keeping the config as the only thing that crosses the boundary: the model becomes a swappable part. Wrap each provider in a tiny adapter that takes a prompt and returns a PageConfig. The route doesn't care which one it called. Neither does the renderer.

lib/engines.ts 
import Anthropic from "@anthropic-ai/sdk";
import { GoogleGenAI } from "@google/genai";
import { PageConfig } from "./schema";
import { SYSTEM, jsonSchema } from "./prompt";

type Engine = (prompt: string) => Promise<unknown>;

const claude: Engine = async (prompt) => {
  const a = new Anthropic();
  const m = await a.messages.create({
    model: "claude-sonnet-4-6", max_tokens: 1200, system: SYSTEM,
    tools: [{ name: "emit_page", input_schema: jsonSchema }],
    tool_choice: { type: "tool", name: "emit_page" },
    messages: [{ role: "user", content: prompt }],
  });
  return m.content.find((b) => b.type === "tool_use")?.input;
};

const gemini: Engine = async (prompt) => {
  const g = new GoogleGenAI({});
  const r = await g.models.generateContent({
    model: "gemini-2.5-flash",
    contents: `${SYSTEM}\n\nRequest: ${prompt}`,
    config: {
      responseMimeType: "application/json",   // ← Gemini's JSON mode
      responseSchema: jsonSchema,
    },
  });
  return JSON.parse(r.text);
};

const engines = { claude, gemini } as const;

export async function buildConfig(prompt: string, which: keyof typeof engines) {
  const raw = await engines[which](prompt);
  return PageConfig.parse(raw);   // same validator for both
}

Same prompt, same schema, same validator — two engines. Both providers have a structured-output mode (Claude via forced tool use, Gemini via responseSchema), and because you re-validate with one Zod object, their slightly different outputs land in the exact same shape. Now you can A/B them on cost, latency, and taste without rewriting a line of UI.

Claude — forced tool use

  • Tightest contract — tool_choice guarantees the call
  • Strong at tasteful, restrained copy
  • Great when the schema is nested or strict

Gemini — responseSchema

  • Fast + cheap on Flash, good for high volume
  • Native JSON mode, no tool wrapper needed
  • Handy when you want raw throughput over nuance
heads up ↳
The adapters are where provider quirks go to die. If Gemini ever returns a stray field or Claude nests differently, you fix it in one function — the route and renderer never learn the difference. That's the entire value of the boundary.
09

Guardrails & the ship-day checklist. ship

The demo works. Shipping it means handling the three things demos skip: the model fails, the model is slow, and the model occasionally returns something almost-but-not-quite valid. None of these are exotic. All of them have one-line answers if you planned for them.

the route, hardened 
export async function POST(req: Request) {
  const { prompt, engine = "claude" } = await req.json();

  // 1. cap input — don't pay for a novel
  if (!prompt || prompt.length > 500) {
    return Response.json({ error: "bad prompt" }, { status: 400 });
  }

  try {
    const config = await buildConfig(prompt, engine);
    return Response.json(config);
  } catch (err) {
    // 2. one retry on a validation miss — models wobble
    try {
      const config = await buildConfig(prompt, engine);
      return Response.json(config);
    } catch {
      // 3. fall back to a safe default page, never a white screen
      return Response.json(FALLBACK_PAGE, { status: 200 });
    }
  }
}

On the client, the same discipline: show a skeleton while busy is true, show a friendly retry button on error, and render the fallback page if the config is the default. The user never sees a stack trace or a spinner that spins forever. A model-driven UI feels broken the instant it stalls — loading states aren't polish here, they're the product.

checklist ↳
Validate on the server, always. Retry once on a parse miss. Fall back to a static config instead of crashing. Cap the input length and the max_tokens. Cache identical prompts so you stop paying twice. Five lines each, and it stops feeling like a demo.

That's the loop, end to end: a schema you designed, a model that fills it, a renderer that owns the look, and enough guardrails that a bad response is a non-event. The model drives the content. You still own the car.
