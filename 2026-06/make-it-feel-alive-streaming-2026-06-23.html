Make it feel alive — nine moves for streaming an AI response into a real UI.

The spinner is a lie. It tells the user "wait" while the model has been talking for two seconds already. This notebook is the move that flips that — tokens straight from Claude or Gemini into the DOM, character by character, so your app stops loading and starts breathing. One contract, one reader loop, one tasteful typewriter. Mostly frontend. Both models, side by side.

—Lupo · The Mess is the Method
Read · ~13 min Surface · a frontend + one API route Assumes · you've called a model once before Voice · open-notebook, casual

Here's the thing nobody tells you when you build your first AI feature: the model already streams. The tokens come out one at a time, the moment they're generated. The default tutorial throws all of that away — it awaits the whole answer, then drops a finished wall of text in front of a spinner. You paid for a live performance and showed your user a recording.

The fix is small. It's not a framework, it's not a library, it's a reader loop and a few lines of state. But the effect is the single biggest jump in perceived quality I know — the difference between a class project and a product. People feel it before they can name it.

Below: each move gets a number, a one-line claim, the actual code, and a try-it crumb. The reader at the top of this page is real — it's the typewriter from move 04, running on a canned response so you can feel the target before we build it.

01

Kill the spinner — streaming isn't a feature, it's the default the model already gives you. model

When you call a chat model, the response is generated left to right, one token at a time. A non-streaming call just buffers all of those tokens server-side and hands you the finished string. You're not saving work by waiting — you're adding a wait. The first token is usually ready in a few hundred milliseconds; the full answer might take eight seconds. Streaming shows the user something at 300ms. Buffering shows them a spinner for eight seconds.

Buffered (the tutorial)

User clicks → spinner → 8s of nothing → wall of text appears. Feels broken even when it works.

"is it frozen?"

Streamed (this notebook)

User clicks → first words at 300ms → text grows as they read. Feels like a conversation.

"oh, it's thinking out loud."

That's the entire pitch. Same model, same prompt, same cost. The only change is when you show the bytes. Everything below is how to wire that up without it turning into a mess.

02

The stream contract — one tiny server route both models can fill. backend

You never call the model from the browser — your API key would be sitting in the page source. So there's always one server route in the middle. Its job is dead simple: take the prompt, open a stream to the model, and forward each chunk to the browser as it arrives. The web has a built-in format for exactly this: Server-Sent Events. It's just a long-lived response where you write data: ...\n\n over and over.

app/api/stream/route.ts · Next.js, runs on the server 
export async function POST(req: Request) {
  const { prompt } = await req.json()

  // ask the model for a stream, not a string
  const modelStream = await callModel(prompt)   // move 05 fills this in

  // hand the browser a readable stream of SSE chunks
  const stream = new ReadableStream({
    async start(controller) {
      const enc = new TextEncoder()
      for await (const token of modelStream) {
        controller.enqueue(enc.encode(`data: ${JSON.stringify({ token })}\n\n`))
      }
      controller.enqueue(enc.encode("data: [DONE]\n\n"))
      controller.close()
    },
  })

  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache",
      "Connection": "keep-alive",
    },
  })
}

That's the whole server. Notice it doesn't care which model callModel talks to — Claude, Gemini, whatever. The contract is "for-await over tokens, write SSE lines." Keep that boundary clean and you can swap models without touching the frontend.

heads up ↳
On Vercel, add export const runtime = "edge" for true streaming — the default Node serverless runtime will sometimes buffer the whole response before flushing, which silently undoes everything you just built. Edge runtime streams for real.
03

The reader loop — eleven lines that are the entire trick. frontend

This is the heart of it, and it's smaller than people expect. The browser fetch gives you a response.body that is itself a stream. You grab a reader, loop until it's done, decode each chunk, and append the text to a piece of state. React (or anything reactive) re-renders on each append — and that re-render is the live typing effect.

the reader loop · runs in the browser 
async function streamPrompt(prompt: string, onToken: (t: string) => void) {
  const res = await fetch("/api/stream", {
    method: "POST",
    body: JSON.stringify({ prompt }),
  })

  const reader = res.body.getReader()
  const dec = new TextDecoder()

  while (true) {
    const { value, done } = await reader.read()
    if (done) break
    for (const line of dec.decode(value).split("\n\n")) {
      if (!line.startsWith("data: ")) continue
      const payload = line.slice(6)
      if (payload === "[DONE]") return
      onToken(JSON.parse(payload).token)   // ← append & re-render
    }
  }
}

Wire it to state and you're done. In React: streamPrompt(p, (t) => setText((prev) => prev + t)). Every token that arrives bumps the state, every bump paints. That's the whole reactive loop — no websocket library, no polling, no magic.

the model is the engine. this loop is the throttle cable.
04

The typewriter, done with taste — tokens arrive in bursts; smooth them out. polish

Raw token streams are lumpy. The model sends three words, pauses, sends a whole sentence, pauses again. If you paint each chunk the instant it lands, the text stutters — it looks janky, not alive. The fix is a tiny render queue: buffer incoming tokens, and drain them to the screen at a steady, slightly-faster-than-reading pace. That's the demo at the top of this page.

smooth-drain typewriter · the trick behind the live demo 
// incoming tokens pile into a queue; a timer drains chars evenly
function makeTypewriter(paint: (s: string) => void, cps = 90) {
  let queue = "", shown = "", timer: any

  function tick() {
    if (!queue) { timer = null; return }
    shown += queue[0]
    queue = queue.slice(1)
    paint(shown)
    timer = setTimeout(tick, 1000 / cps)   // even cadence
  }

  return {
    push(token: string) {
      queue += token
      if (!timer) tick()
    },
  }
}

Now the buffer absorbs the lumps. When the model dumps a sentence, it goes into queue and drains out at a calm ~90 characters a second. When the model stalls, the queue empties and the caret just blinks — which reads as "thinking," not "frozen." Tune cps to taste: slower feels deliberate, faster feels snappy.

05

Claude vs Gemini — same idea, two SDKs, one swappable function. model

Remember callModel from move 02? Here's both versions. They're almost identical — both expose an async iterable of text deltas. Pick one, drop it into the route, and the rest of the stack never knows the difference. This is the move the design-blog crowd loves to compare, so here they are honestly, next to each other.

Claude · @anthropic-ai/sdk

import Anthropic from "@anthropic-ai/sdk"
const a = new Anthropic()

async function* callModel(p) {
  const s = a.messages.stream({
    model: "claude-opus-4-8",
    max_tokens: 1024,
    messages: [{ role: "user", content: p }],
  })
  for await (const e of s) {
    if (e.type === "content_block_delta")
      yield e.delta.text
  }
}

warm prose, holds structure under long answers

Gemini · @google/generative-ai

import { GoogleGenerativeAI } from "@google/generative-ai"
const g = new GoogleGenerativeAI(key)

async function* callModel(p) {
  const m = g.getGenerativeModel({
    model: "gemini-2.5-flash",
  })
  const r = await m.generateContentStream(p)
  for await (const c of r.stream) {
    yield c.text()
  }
}

fast first-token, great for data-shaped output

Both are generator functions (function*) that yield strings. The route's for await loop doesn't care which one it got. That's the payoff of keeping the contract thin in move 02 — model choice becomes a one-import decision, not a rewrite.

heads up ↳
Default to the latest, most capable model for the job and check the SDK's current model IDs before you ship — they rev often. The shape of the streaming API (an async iterable of text deltas) is the stable part; the exact id string is not.
06

The stop button — let users cancel, and actually stop billing. frontend

A streaming UI without a stop button is a trap. The user asks a question, realizes it was wrong, and has to sit through 800 tokens they don't want — tokens you're paying for. An AbortController fixes both: it kills the fetch and propagates upstream so the model call winds down too.

abortable stream 
const ctrl = new AbortController()

// pass the signal into fetch...
const res = await fetch("/api/stream", {
  method: "POST",
  body: JSON.stringify({ prompt }),
  signal: ctrl.signal,   // ← this line is the whole feature
})

// ...and the Stop button just calls:
onClick={() => ctrl.abort()}

// wrap the read loop so an abort exits cleanly, not as a crash
try { /* reader loop from move 03 */ }
catch (e) {
  if (e.name !== "AbortError") throw e   // expected on stop
}

One controller per request. New prompt → new controller. Keep a ref to the current one so the Stop button always aborts the live stream, not a stale one. Small detail, huge "this feels like a real app" payoff.

07

Stream straight into Markdown — render as it arrives, not after. design

Models love Markdown — headings, bold, lists, code fences. If you wait for the stream to finish before parsing it, you've reintroduced the buffer you worked to kill. Instead, re-parse the accumulated text on every token and render the partial Markdown live. It handles half-finished syntax gracefully — a **bold with no closing stars just renders as plain text until the second ** lands, then snaps bold.

live markdown · React + a streaming-md renderer 
import Markdown from "react-markdown"

function Answer({ text }) {
  // `text` grows every token; react-markdown re-parses
  // the partial string and renders what's valid so far.
  return (
    <div className="prose">
      <Markdown>{text}</Markdown>
      {streaming && <span className="caret" />}
    </div>
  )
}

One catch worth knowing: re-parsing the full string every token is fine for chat-length answers but gets expensive for very long ones. If you're streaming a 5,000-word document, memoize the parse or only re-render on sentence boundaries. For 99% of features, naive re-parse is perfectly fast.

this is the move that makes code blocks appear with real syntax highlighting, live.
08

The graceful fail — streams break mid-sentence; plan for it. backend

A buffered call fails cleanly: you get an error, you show a message, done. A stream can die halfway — the user is watching the answer type out and the connection drops on word forty. If you don't handle it, the text just... stops, mid-thought, with no signal. That's worse than a plain error because it looks like a real (bad) answer.

fail without lying to the user 
let got = 0
try {
  while (true) {
    const { value, done } = await reader.read()
    if (done) break
    got++
    /* ...append token... */
  }
} catch (e) {
  if (e.name === "AbortError") return          // user hit stop, fine
  setError(got > 0
    ? "Connection dropped mid-answer — retry?"   // partial
    : "Couldn't reach the model — retry?")      // never started
} finally {
  setStreaming(false)   // always stop the caret blinking
}

Two things make this feel handled instead of broken: the finally that always clears the streaming flag (so the caret stops, signalling "this is over"), and an error message that distinguishes "never started" from "died partway." A retry button on a partial answer is the difference between "buggy" and "robust."

heads up ↳
Keep the partial text on screen when a stream drops — don't blank it. A half-answer plus a retry button is useful. An answer that vanishes the moment it fails just makes the user re-type their prompt.
09

The feel test — nine checks that separate "alive" from "almost." polish

Streaming is one of those things that's either right or uncanny, and the gap is all small stuff. Before you call a streaming UI done, run it past this. If any row fails, the user won't be able to name why it feels off — but they'll feel it.

✓First token under ~500ms. If the spinner is up longer than that, your route is buffering. Check the edge runtime.
✓The caret blinks during stalls. A pause with a blinking caret reads as thinking. A pause with nothing reads as frozen.
✓Cadence is steady, not bursty. The typewriter queue (move 04) absorbs lumpy chunks into a calm, readable pace.
✓Auto-scroll follows the text — but stops the moment the user scrolls up. Hijacking their scroll is rage-inducing.
✓The stop button works instantly and leaves the partial answer on screen.
✕Don't re-layout on every token (no jumping heights). Reserve space or animate height; never let the page jolt.
✕Don't show raw **markdown** asterisks while it types. Render live (move 07) or strip until done.
✕Don't let a dropped stream vanish the text. Partial + retry beats blank every time.
✓Respects prefers-reduced-motion. Some users want the text to just appear. Honor it — it's two lines of CSS.

Pass all nine and you've got the thing the polished AI apps have and the weekend projects don't. It's not one big feature — it's nine small ones stacked, and the user reads the stack as "this feels real."
