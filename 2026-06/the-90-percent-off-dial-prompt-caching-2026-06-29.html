The 90%-off dial — the day your bill stops scaling with how often you repeat yourself.

Every call, you re-send the same system prompt, the same docs, the same few-shot examples — and you pay full freight to make the model re-read them from scratch. Prompt caching is one marker that says remember this part. The stable prefix gets read once and replayed for pennies; only the new bit at the end pays full price. Ten moves to mark it, order it, read the hit, and watch cost and latency fall off a cliff. The ledger below is live — flip cold to warm and watch the bars collapse.

—Lupo · The Mess is the Method

The first time I watched a token bill for an agent that re-sent a 6,000-token system prompt on every single turn, I felt physically ill. The agent was good. It was also paying to re-read its own instructions, its own tool list, and a wall of documentation — word for word — a hundred times an hour. None of that changed between turns. I was buying the same book over and over because I kept forgetting I owned it.

Prompt caching is the fix, and it's almost embarrassingly simple. You tell the provider: this chunk is stable, store it. The next call that starts with the exact same chunk gets a cache hit — the model skips re-reading it and you pay roughly a tenth of the price for those tokens. Only the genuinely new part, the user's latest message, pays full freight.

It is not a new endpoint and not a new model. It's one marker — cache_control on Claude, a cached-content handle on Gemini — plus one discipline: put the stable stuff first, the volatile stuff last. Get the order right and the cache lands. Get it wrong and you quietly pay full price forever. Ten moves below to land it on purpose.

01

Mark the stable prefix — it's one marker on a block you already send. setup

No new endpoint, no special model. You take the chunk that doesn't change between calls — the system prompt, usually — and hang a cache_control marker on it. That tells the provider: store everything up to and including this block. The next request that opens with the exact same bytes gets to skip re-reading them.

cache.py — one marker on the stable system prompt
import anthropic
client = anthropic.Anthropic()

BIG_SYSTEM = open("system_prompt.md").read()   # long & stable

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=[{
        "type": "text",
        "text": BIG_SYSTEM,
        "cache_control": {"type": "ephemeral"},  # <-- the marker
    }],
    messages=[{"role": "user", "content":
        "Summarize the last meeting in three bullets."}],
)
try it
Run that exact call twice in a row. The first one writes the cache; the second one hits it. Then print response.usage on both and watch cache_read_input_tokens jump from 0 to the size of your system prompt. That number is the dial moving.
02

Read the shape — you pay a little to write, almost nothing to read. read

Caching has two prices, and they're the whole mental model. The first call that stores a chunk pays a small premium on those tokens — a cache write, slightly more than normal. Every call after that reuses it pays a cache read — roughly a tenth of the normal token price. So the trade is: pay a hair more once, pay almost nothing forever after. The break-even lands fast (Move 9 does the math).

write

The first call — a small premium. The provider reads your big chunk and stores it. You pay normal price plus a little — the one-time cost of putting the book on the shelf.

read

Every call after — about 10% of normal. Same chunk, recognized, replayed. The model doesn't re-read it from scratch — which is also why it answers faster, not just cheaper.

cheaper AND faster — caching buys back latency too, not just dollars.

03

Order it: stable first, volatile last — this is the whole game. cache

The cache matches on the prefix — it works left to right and stops the instant something differs. So one rule governs everything: put what never changes at the front, what changes every call at the back. System prompt, then tool schemas, then session documents, then — last — the user's new message. Slip one volatile token (a timestamp, a request ID) up near the top and you've poisoned the prefix: nothing after it can ever hit.

front

Cache this — system prompt → tools → stable docs. Byte-for-byte identical across calls. This is the prefix the cache stores and replays.

put the cache breakpoint here
back

Always fresh — the user's latest turn. Different every call by definition. It pays full price — but it's tiny next to the prefix you just stopped re-paying for.

heads up
The killer is a moving token near the top. A "current time: 14:32:07" line in the system prompt, a per-request trace_id, a freshly-shuffled examples list — any of them changes the prefix and the cache misses every single time. If it has to be there, push it below the breakpoint.
04

Read the hit — four counters tell you the whole story. read

You don't guess whether caching worked — the response tells you. Every reply carries a usage block with four token counters. Two are new and they're the ones that matter: cache_creation_input_tokens (what you just wrote) and cache_read_input_tokens (what you got for cheap). On a cold call the read is 0. On a warm call your whole prefix should show up in the read.

usage.py — the same call, run twice
# --- call 1 (cold): writes the cache ---
input_tokens:                 40
cache_creation_input_tokens:  7400   # paid a premium, once
cache_read_input_tokens:      0

# --- call 2 (warm): hits the cache ---
input_tokens:                 40
cache_creation_input_tokens:  0
cache_read_input_tokens:      7400   # ~10% of full price ✓
try it
Compute a one-line hit ratio and print it: read / (read + fresh + creation). Anything north of ~0.8 on a steady workload means the cache is doing its job. If it's stuck near 0, you have a moving token in your prefix — go re-read Move 3.
05

Cache the system prompt and the tool list — the agent tax. cache

Agents are the textbook win. A real agent (Vol. 10) loops dozens of times per task, and on every loop it re-sends the same fat system prompt and the same wall of tool schemas (Vol. 19 — MCP tool defs are big). That's the part that never changes within a run. Mark the end of the tools block and the entire instruction-plus-tools preamble caches as one prefix.

agent_cache.py — cache the preamble, not the conversation
response = client.messages.create(
    model="claude-sonnet-4-6",
    system=[{"type": "text", "text": SYSTEM,
             "cache_control": {"type": "ephemeral"}}],
    tools=[
        tool_a, tool_b, ...,
        {**tool_z, "cache_control": {"type": "ephemeral"}},  # mark the LAST tool
    ],
    messages=conversation,   # the only part that grows
)
# everything up to the last tool is now one cached prefix.
try it
Marking the last tool caches all the tools before it too — the breakpoint stores everything up to that point. On a 20-turn agent run, this is the difference between paying for your tool schemas once versus twenty times. It's the single biggest line-item you can delete.
06

Cache a big document, then ask it ten questions. cache

The other classic: you have one large thing — a contract, a transcript, a codebase dump, the retrieved chunks from Vol. 26 — and you want to interrogate it from a dozen angles. Don't re-send the document on every question. Put it in the prefix, cache it once, and let each new question be the only thing that pays full price.

interrogate.py — load the doc once, ask many times
DOC = open("50_page_contract.txt").read()   # ~40k tokens

def ask(question):
    return client.messages.create(
        model="claude-sonnet-4-6", max_tokens=512,
        messages=[{"role": "user", "content": [
            {"type": "text", "text": DOC,
             "cache_control": {"type": "ephemeral"}},  # doc cached
            {"type": "text", "text": question},        # only this is fresh
        ]}],
    )

ask("What's the termination clause?")   # writes cache
ask("Any auto-renewal traps?")         # hits cache
ask("Summarize the payment terms.")    # hits cache
heads up
Caching has a minimum size — the cacheable chunk has to clear a token floor (roughly a thousand-ish, model-dependent) or the provider won't bother storing it. Tiny prompts aren't worth caching and the API will quietly ignore the marker. This move only pays off on genuinely big, reused context.
07

Mind the TTL — the cache is a fridge, not a freezer. gotcha

A cache entry doesn't live forever. The default lifetime is short — on the order of a few minutes — and every hit refreshes the timer. So a busy endpoint keeps its cache warm just by being busy, while a quiet one lets it go cold and the next call pays the write premium again. If you need it to survive longer gaps, some providers offer a longer TTL tier for a bigger write premium.

SituationWhat the cache doesMove
Steady trafficstays warm — each hit resets the clockjust cache it
Bursty, then idlegoes cold between bursts; re-writes on returnconsider a longer TTL
One call, then neverwrites, never reads — pure premiumdon't cache

a hit resets the timer. keep it busy and it stays warm for free.

08

Don't cache the thing that always changes — you'll lose money. gotcha

Caching is not free to write. If you hang a marker on a chunk that's different every call, you pay the write premium every time and never collect a single read — strictly worse than not caching at all. The skill is sorting your prompt into "stable" and "volatile" honestly, and only marking the stable part. When in doubt, look at the cache_read counter: if it never climbs, you cached the wrong thing.

BlockCache it?Why
System promptyesstable across the whole app
Tool / function schemasyesfixed for the session
Retrieved docs (this session)yesreused across the turn's questions
The user's latest messagenonew every call — leave it fresh
A live timestamp / request idnopoisons the prefix; never repeats
09

The break-even — when caching has paid for itself. cost

Here's the back-of-napkin that makes it obvious. The write costs you a small premium once; each read saves you roughly 90% of that chunk's price. So the cache pays for its own write premium after just a handful of hits — and everything after that is pure savings. For anything you call more than two or three times with the same prefix, caching is a no-brainer.

napkin.txt — a 7,400-token prefix, called 100×/hour
# WITHOUT caching
100 calls × 7,400 tokens at full price ........ 740,000 tok

# WITH caching (1 write + 99 reads)
  1 write  × 7,400  (slight premium) ............   ~9,250 tok-equiv
 99 reads  × 7,400  at ~10% ....................   ~73,260 tok-equiv
total ......................................... ~82,510 tok-equiv

# ≈ 89% fewer prefix tokens billed. the dial, turned.
try it
Plug your numbers into that napkin before you optimize anything else. The biggest prefix you re-send the most often is where the money is — usually the agent system prompt. Cache that one block and you've likely captured 80% of the available savings in five minutes of work.
10

Verify the hit — log the ratio, gate on it. ship

Caching fails silently. Someone adds a timestamp to the system prompt, refactors the tool order, tweaks one byte of the preamble — and your hit ratio quietly drops to zero while the bill creeps back up. Nothing errors. So treat it like any other metric from Vol. 25: log cache_read on every call, watch the ratio, and let your Vol. 24 harness fail the build if it regresses.

guard.py — a test that fails when the cache breaks
def hit_ratio(usage):
    read  = usage.cache_read_input_tokens
    total = read + usage.input_tokens + usage.cache_creation_input_tokens
    return read / total if total else 0.0

# warm it once, then assert the second call hits
ask("warmup")
u = ask("real question").usage
assert hit_ratio(u) > 0.8, "cache regressed — check the prefix!"
try it
Add that one assert to CI. The day someone slips a moving token into the system prompt, the test goes red before the bill does. A cache you don't monitor is a cache that's already broken — you just don't know it yet.
