The prompt that stops the agent from guessing.

I pulled 874 of my own prompts out of Cursor's database to see what I actually type when an agent is doing the work. The pattern was loud: the prompts that worked weren't longer or cleverer — they front-loaded constraints and took away the agent's room to improvise. This is that playbook, eight moves deep.

—Lupo · The Mess is the Method
Read · ~12 min Surface · Cursor · Claude Code · any coding agent Assumes · you've let an agent build one thing Voice · open-notebook, casual

Here's the thing nobody told me when I started letting agents write code for me: the model is almost never the problem. The prompt is. When an agent rebuilds a component you didn't ask it to touch, or "improves" a brief into something generic, or confidently describes a file it never opened — that's not the model being dumb. That's the model filling a gap you left open.

So I went looking at my own evidence. Cursor keeps every prompt you've ever typed in a little SQLite file. I exported mine: 874 prompts, 759 unique. The single most-repeated one — 33 times — wasn't a request at all. It was a set of rules. "Implement the plan. Don't edit the plan file. Don't stop until every to-do is done."

That's the whole lesson in one line. The best prompt I own is mostly a list of things the agent is not allowed to do. Below are the eight moves that came out of reading the rest. Top to bottom, roughly most-used first.

01

Front-load the dealbreakers — before the ask, not after. constraint

The friction that showed up the most across every usage report I kept was the same one: "wrong approach." The agent picks a direction, commits to it, and you're now arguing it back out of a decision it already made. The fix is stupidly simple and I resisted it for months: say the 2–3 things that would make the result wrong first, before you describe the task.

guessable 
build me a pricing page

# agent invents a stack, a
# layout, a color system, 3
# tiers you didn't ask for...
constrained 
# dealbreakers first:
Tailwind v4, light mode,
mobile-first, two tiers only,
no new dependencies.

Now build a pricing page.

Same request. The second one can't drift, because the expensive decisions are already made. I think of it as spending three sentences to save three rounds of "no, not like that."

try it ↳
Take any task you'd normally one-line. Before you send it, write the sentence: "This is wrong if it ______." Fill the blank twice. Paste those two answers above your request. That's the whole move.
02

The plan-execution lock — my single most-typed prompt. flow

This is the one I typed 33 times without realizing it had become a template. The shape: you make a plan with the agent in one step, then in a fresh step you tell it to execute that plan with its hands tied. The lock is the second half — it stops the agent from re-litigating the plan it just agreed to.

the lock — copy this verbatim 
Implement the plan as specified, it is attached for
your reference.

Do NOT edit the plan file itself.
The to-dos already exist — do not recreate them.
Mark each in_progress as you work, starting with #1.
Don't stop until every to-do is complete.

Why it works: "plan" and "execute" are different jobs, and agents are worst at the seam between them — that's where they wander. Splitting them into two prompts with an explicit "don't touch the plan" rule keeps the thinking and the doing from contaminating each other.

two prompts beat one. the seam is where agents wander off.
03

Negative constraints — the "do NOT" list is the steering wheel. constraint

Most prompt advice is about what to ask for. The leverage is in what to forbid. A coding agent has a thousand reasonable-looking moves available at every step; you don't steer by listing the one you want, you steer by fencing off the ones that quietly cause damage. My real prompts are full of these — and they're never clever, just specific.

do-not lines, lifted from real sessions 
Don't overlap or break any other setups.
Don't add anything unnecessary — tighten, don't expand.
Don't overload the context window with files you don't need.
Don't delete — archive to a dated folder instead.
Don't touch the Pictures folder. # burned by this once

That last one is real and it's there because an agent once chewed through a giant media folder it had no business reading. A "do NOT" line is cheap insurance — one sentence that prevents one specific disaster you've already lived through.

heads up ↳
Negative constraints are most powerful as standing rules, not per-prompt ones. The "archive, never delete" rule earned a permanent home in my config after the agent assumed 128 files were duplicates and removed them. Some "do NOT"s should outlive the session.
04

Audit first, edit never — until you explicitly say go. flow

The strongest sessions I've ever run all started the same way: the agent looked before it touched. Read-only first. You'd be amazed how much drift disappears when the agent isn't allowed to change anything on the first pass — it has to understand the system before it can break it.

the two-pass open 
# pass 1 — read only
Analyze this folder and offer a plan. Make NO
changes yet. Tell me what you found and what
you'd do, then wait.

# pass 2 — only after you've read pass 1
Good. Proceed with steps 1–3 only. Stop and
report before step 4.

The reason this matters beyond safety: an agent that has to describe its plan before acting can't quietly invent. The classic failure — confidently telling you what a script does without reading it — only happens when nothing forced it to look first.

try it ↳
Next messy folder or unfamiliar repo: open with "analyze and offer a plan, make no changes, then wait." Read the plan. Then let it move. You'll catch the wrong approach while it's still words, not commits.
05

"Ask me 3 questions before you touch anything." mindset

A tiny phrase that punches way above its weight, and it shows up in my extraction more than once: "ask 3 questions you need from me before making changes." It flips the default. Instead of the agent guessing to fill the gaps in your brief, it surfaces the gaps and hands them back to you.

gap-surfacing open 
Before you write any code, ask me the 3 questions
whose answers would most change your approach.

# the agent now tells you what it was
# about to assume — which is exactly the
# stuff that produces "wrong approach"

The number matters. "Any questions?" gets you nothing or twenty. "The 3 that would most change your approach" forces a ranking — you get the load-bearing unknowns, not the trivia. It's the cheapest insurance against a confidently-wrong first draft I know of.

06

Name the file, kill the guess. constraint

Half of "wrong approach" is the agent editing the wrong thing because it guessed where the code lived. The fix doesn't require a clever prompt — it requires you to do five seconds of pointing. Paste the path. Paste the DOM selector. Name the function. Specificity isn't a tone, it's coordinates.

guessable 
fix the broken nav

# which nav? which file?
# the agent goes hunting,
# touches three components
pointed 
# coordinates, not vibes
In src/components/nav.tsx,
the mobile menu at line 40
doesn't close on route change.
Fix only that. Touch nothing else.

When I'm in the browser I'll grab the exact selector from the inspector and paste it in. When I'm in the repo I'll name the file and line. The agent stops being a detective and starts being a surgeon — and surgeons don't redecorate the room.

specificity is the entire game. coordinates > adjectives.
07

Demand the status check — "report, then verify." flow

Another phrase that earned its keep through sheer repetition in my logs: "Provide current status update. If finished, return final summary and verification results." The verification clause is the part that matters. An agent left to its own devices will tell you it's done. It will not, by default, tell you whether done actually works.

the close-out 
Status update. If finished:
  — one-line summary per to-do
  — the command you ran to verify each
  — the actual output, not "it should work"

# "should work" is where the bugs hide

The discipline here mirrors the one I hold myself to: verify, never guess. If the agent can't show you the lint output or the passing test or the screenshot, the task isn't done — it's claimed. Asking for the evidence in the same breath as the summary makes the difference impossible to skip.

08

Protect the danger zones — out loud, every time. mindset

The most expensive lessons I have aren't about getting better output — they're about not losing work. Early on, agents broke my environment more than they helped it: deleted files they assumed were duplicates, wiped editor profiles, went after gigabytes of bundles. Every one of those was a missing sentence in a prompt.

the guardrail line 
Off-limits, do not read or modify:
  ~/Pictures, anything with a numbered backup
  name (v2-backup, step-1), .env / credentials,
  any dir over a few hundred MB.

When in doubt, archive to a dated folder.
Never delete. Confirm before anything destructive.

Two things made these stick. First, the destructive ones belong in a hook or a standing rule — a guarantee, not a hope, because "please don't" is a preference and a preference can be forgotten mid-session. Second, the numbered-name instinct: anything called step-1 or v2-backup means "I might want this back." Archive it, don't trust the agent's read on whether it's junk.

heads up ↳
There's a real line between a preference and a guarantee. "Use light mode" is fine in a prompt. "Never delete without confirming" should live somewhere the agent cannot skip — a hook, a config rule — because the cost of it being forgotten once is hours, not seconds.

Say this, not that — the same nine asks, sharpened.

The whole notebook collapses into a single habit: trade the adjective for the coordinate, the wish for the constraint. Here's the swap in nine everyday lines.

make it look better

clean up this folder

fix the bug
