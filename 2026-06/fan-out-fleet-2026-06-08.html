Fan out the fleet — stop running one agent at a time.

For months I ran AI the way everyone starts: one chat, one task, wait, repeat. Then I watched my own usage report and saw the leap I'd missed — the month I stopped operating a single agent and started directing a fleet of them. This is that shift, broken into the moves that actually made it work, plus the one rule that keeps it from turning into expensive theater.

—Lupo · The Mess is the Method
Read · ~12 min Surface · Claude Code + sub-agents Assumes · you've run a few solo agent sessions Voice · open-notebook, casual

Here's the number that reframed everything for me. Three usage reports, stacked: Phase 1 was 39 sessions of survival — long, interrupted, one thing at a time. Phase 2 was system-building. Phase 3 was 100 sessions, 979 messages, and a daily volume that doubled. What changed wasn't the model. It was that I'd quietly stopped being the one doing the work and become the one handing it out.

The official name for this is "sub-agents" or "multi-agent orchestration," which sounds like something you need a platform team for. It isn't. The core idea is small: instead of asking one agent to do six things in a row, you spawn six agents that each do one thing at the same time, and you read the conclusions instead of the work. The slow loop — ask, wait, ask, wait — is where my hours used to die.

Below: the mental model, the pattern that makes it concrete, and an honest section on when not to do this — because the failure mode here isn't "it breaks," it's "it feels impressive and produces nothing." Each move gets a claim, a real example, and a try-it crumb.

The shape ↓

YOU — the director (one context)
agent 1audit repo A
agent 2audit repo B
agent 3draft README
agent 4find dead links

They run in parallel. Each returns a conclusion, not a transcript. You keep the summary, not the noise.

01

Notice which loop you're stuck in. mindset

Before any tooling, the diagnosis. The single-agent loop has a tell: you're sitting there waiting. You ask, it works, you read, you ask the next thing. Each step is fine on its own. The waste is the gaps between them — you idling while one agent grinds through work that has nothing to do with the next thing you'll ask.

The reframe is dumb-simple: are these steps actually dependent, or did I just line them up because that's how I think? "Audit these four folders" is four independent jobs wearing a trench coat. "Fix the bug, then write the test for the fix" is genuinely sequential. The first one should fan out. The second one shouldn't.

fan out ✓
Independent + repeated. Same job across many targets — audit 40 repos, summarize 12 docs, check links on 8 pages.
fan out ✓
Different angles, one thing. Three agents review the same PR for bugs / security / clarity, then you merge their verdicts.
keep serial ✗
Each step needs the last one's output. Design → build → test on the same file. A fleet here just collides with itself.

if you're waiting more than you're reading, you're in the wrong loop.

02

Spawn workers that hand back a conclusion, not a diary. pattern

The thing that makes a fleet worth running is what comes back. A sub-agent gets its own fresh context window, does its job in private, and returns one message to you. That return is the whole point: you want the verdict, not the forty tool calls it took to get there. Done right, the director's context stays clean while the messy work happens off-screen.

In practice you describe the fleet in one breath and let the orchestrator dispatch it. The trick is writing each task so the agent knows exactly what to report — "tell me the conclusion" beats "go look around."

one prompt → four workers 
# the director prompt — note the shape:
# N independent jobs, each told what to RETURN

> Spin up four agents in parallel, one per folder in
  ~/Agents/{brand,tools,ai-insights,audit}.
  Each one: scan for broken internal links and stale dates.
  Return ONLY a short list: file · issue · fix.
  Don't edit anything. I'll decide what to touch.

agent-1 (brand)      → 2 stale dates, 0 broken links
agent-2 (tools)      → clean
agent-3 (ai-insights)→ 1 dead path in synthesis-map.md
agent-4 (audit)      → 3 broken links in map.md

# four reports. one context. zero waiting between them.

The phrase doing the heavy lifting is return ONLY. Without it, each agent dumps its full reasoning back into your window and you've recreated the exact noise problem the fleet was supposed to solve. Tell them what to bring home.

try it ↳
Pick any folder with 3+ sub-projects. Ask for one agent per sub-project to summarize what it does in two sentences and return only that. You'll get a map of your own work in the time it used to take to read one folder.
03

Use the panel trick — same target, different lenses. pattern

Fan-out isn't only for "many targets." The sharper move is one target, many perspectives. Instead of asking a single agent "is this PR good?" — a question so broad it gets a mushy answer — you run a small panel. One agent hunts correctness bugs. One reads it for security. One asks "would a tired teammate understand this at 5pm?" Then you read three focused verdicts instead of one averaged shrug.

This works because narrow questions get sharp answers. A reviewer told to only find security holes finds more of them than a generalist trying to cover everything at once. The same logic powers the "adversarial verify" pattern — spawn skeptics whose entire job is to try to refute a finding before you trust it.

the review panel 
> Review this diff with three agents, each one lens only:
    1. correctness — logic bugs, edge cases, off-by-ones
    2. security    — input handling, secrets, auth gaps
    3. clarity     — naming, would a teammate follow it
  Return one verdict each: SHIP / FIX / BLOCK + why.

correctness → FIX  · null case in line 42 unhandled
security    → SHIP · no untrusted input reaches the query
clarity     → FIX  · "data2" / "tmp" — rename before merge

# 2× FIX, 0× BLOCK → you know exactly what to do next

a vague question gets averaged. a narrow one gets answered.

04

Give parallel writers their own room. guardrail

Reading in parallel is free. Writing in parallel is where people get burned. If four agents all edit files in the same folder at the same time, they trample each other — two of them "fix" the same line, a third reverts a change it never saw. The result looks like work and is actually a merge conflict you have to untangle by hand.

The fix is isolation. When agents mutate files concurrently, each one gets its own working copy (a git worktree) so their edits can't collide. They do their thing in separate rooms; you review the diffs and decide what comes back. It's a little more setup, so I only reach for it when agents are genuinely writing — not when they're just reading and reporting.

heads up ↳
The rule I burned myself on: read-only fleets can be big and casual; write fleets must be isolated and small. A dozen agents auditing in parallel is fine. A dozen agents editing the same repo in parallel is a Saturday you won't get back.

Same energy as the old "archive, never delete" lesson — the cost of a wrong parallel write is way higher than the cost of one extra setup step. Default to read-heavy fleets that propose, and let yourself be the one who applies.

05

Earn the complexity — don't cosplay it. mindset

Now the honest part, because my own notes argue with each other on this one and the argument is the lesson. One side of my strategy docs says build the big stack: multi-agent orchestration, layered memory, the whole authority ladder. The other side warns against "speculative infrastructure" and "building before observing" — earn complexity gradually.

Both are right, and the way to hold them together is a ladder. Start at the bottom. Only climb a rung when the friction you're actually hitting justifies it. A fleet of twelve agents is genuinely impressive and genuinely useless if the job was a five-minute single-agent ask. The tell that you've over-built: it feels like a lot is happening and the output is thin.

rung 1
Just ask. One agent, one question. Most days end here.
rung 2
A saved skill. The same ask, twice — encode it so you stop retyping.
rung 3
Fan out. Independent work × many targets — the move this whole notebook is about.
rung 4
A real workflow. Fan-out + verify + synthesize, run as one repeatable pipeline.
rung 5
Full architecture. Memory, hooks, orchestration as a system — only when observed friction demands it.

I live on rungs 1–3 most weeks and visit 4 when a task is big enough to repeat. Rung 5 is a destination you arrive at by being forced there, not a place you start. The harness compounds — but only the parts of it you actually had a reason to build.

try it ↳
Next time you reach for a fleet, say the rung out loud first. "This is a rung 3 because it's four independent audits." If you can't name why it's not a rung 1, it's probably a rung 1.
