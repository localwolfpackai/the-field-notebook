Prompt to product — ten moves for building real frontends with Claude & Gemini.

The GitHub notebooks were about the tools. This one is about the loop — how a single sentence becomes a designed, working AI app. Artifacts as a canvas, the design knobs that make Claude output feel warm, Gemini turning a prompt into a React panel, and the wiring + eval habits that keep the thing honest once it leaves the chat window. Learned hands-on, written down so the next person skips the flailing.

—Lupo · The Mess is the Method
Read · ~16 min Surface · Claude · Gemini · the AI SDK Assumes · you can read JS, not write models Voice · open-notebook, casual

I am not a developer. I orchestrate. So everything in here is written from the seat of someone who describes what they want, watches a model build it, and then learns just enough to wire it together and ship. Turns out that seat is a great place to build from in 2026 — the gap between “I have an idea” and “it’s on the internet” has never been thinner.

The trick nobody tells you: building with an AI model is a different skill than prompting one for an answer. It’s a loop. Describe → look → adjust one thing → look again. The people who are fast at it aren’t smarter — they just have the loop wired into muscle memory.

Format below mirrors the last few notebooks: each move gets a number, a one-line claim, a real demo, and a crumb you can try in the next ten minutes. Top of the list is where you start; bottom is where you ship.

01

Pick your partner — warmth vs. density. design

Before any code, one decision saves you an hour of fighting the output: which model are you handing the wheel? They have personalities. After a few dozen builds you start reaching for them like different pens. This is the breakdown I’d give a friend over coffee, not a benchmark table.

Reach for Claude when

  • You want it to look designed — padding, warmth, editorial type
  • The surface is an Artifact, a landing page, a polished component
  • You care about taste defaults more than raw data plumbing
  • You’re iterating on feel: “softer,” “more whitespace,” “less corporate”

Reach for Gemini when

  • You’re building data-dense UI — dashboards, tables, multi-panel
  • You want structured output: JSON configs, schemas, typed arrays
  • You need a giant context window or native image/video in the loop
  • The job is “turn this spec into scaffolding” more than “make it pretty”

This isn’t loyalty, it’s casting. I’ll draft a layout in Claude because its default spacing and type already feel human, then hand the data wiring to Gemini when there’s a wall of structured records to model. Same project, two pens.

Luis P’s whole beat is this: Claude manages warmth & grid; Gemini wins on data structure. Watch one comparison and you’ll feel it.

02

Write the prompt like a spec, not a wish. claude

The single biggest upgrade to my output wasn’t a better model — it was writing the ask like a brief. “Make me a dashboard” gets you a generic dashboard. A model can only be as specific as you are. So I front-load four things: what it is, who it’s for, the constraints, and the vibe. Then I let it build.

the spec-prompt skeleton 
# WHAT
Build a single-file React component: a habit tracker.

# WHO / JOB
For someone checking off 5 daily habits on their phone.
Mobile-first. Glanceable in under 2 seconds.

# CONSTRAINTS
- No external libraries except React.
- State in useState, no backend. Persist to localStorage.
- Tap a habit to toggle. Long streaks get a subtle flame.

# VIBE
Warm, calm, light mode. Generous whitespace. Rounded.
Think paper journal, not SaaS dashboard. One accent color.

Notice there’s zero code in that prompt. I’m describing the destination, not the route. The model is better than me at the route. My job is to be unmistakably clear about where we’re going — especially the vibe line, which is the part most people skip and then wonder why everything looks like a default Bootstrap template.

try it ↳
Take any “build me X” idea in your head and force it through those four headers before you hit enter. WHAT / WHO / CONSTRAINTS / VIBE. The first build will land 80% closer. That’s the whole game.
03

Artifacts as a live canvas — iterate in the panel, not the codebase. claude

When Claude builds you something in an Artifact, it renders live in a side panel next to the chat. That panel is the whole point. You’re not copying code into an editor and refreshing — you’re looking at the running thing and talking to it. The loop tightens to seconds.

The mistake beginners make is asking for the whole app to be rebuilt every turn. Don’t. Change one thing and let it surgically edit. The model keeps the Artifact in context, so “make the cards 20% bigger and the streak flame orange” updates exactly that and nothing else.

an iteration session, abridged 
you › build the habit tracker from the spec above
       → renders in the panel. close, but cramped.

you › more vertical breathing room between habits,
        and round the corners more
       → edits spacing + radius only. better.

you › the checked state is too loud. make it a soft
        fill, not a hard green
       → one visual tweak. now it feels calm.

you › add a tiny streak counter under each habit name
       → adds the feature, keeps everything else.

Four turns, four small asks, and the thing is real. Each one is a sentence. You are art-directing, not coding. When it’s right, the “copy code” button hands you the whole file — which is where moves 6 through 10 pick up.

heads up ↳
One concept per turn. If you batch “bigger cards, dark mode, add a calendar view, and fix the font” into one message, you lose the ability to tell which change broke the thing you liked. Slow is smooth; smooth is fast.
04

The design knobs that make it feel made, not generated. design

“Make it look better” is a wish. These are the actual dials. When something feels AI-generated, it’s almost always one of these knobs left on default. I keep this list next to me and turn them one at a time.

whitespace The #1 tell. Ask for “more breathing room” — generous padding reads as intentional. Cramped reads as a template.
type scale One display face, one body face, real size jumps. “Editorial typography” is a phrase models understand — use it.
one accent Pick a single accent color and let everything else be ink + paper. Three accent colors = it looks like a draft.
grid as anchor Ask it to align everything to a visible or implied grid. Off-grid elements are what make a page feel sloppy.
radius + shadow Consistent corner radius, soft single-direction shadows. Mixed radii are a dead giveaway.
warmth Pure #fff / #000 feels cold. Ask for off-white paper and near-black ink. This alone is half of “why does Claude’s output feel nicer.”

The vocabulary matters. Models respond to the words designers use: warmth, padding, editorial, grid, hierarchy, restraint. If you say “more professional” you get more corporate. If you say “more editorial, one accent, generous whitespace” you get something with taste.

this page is the demo. Off-white paper, ink not black, one warm accent, everything on a 32px ruled grid.

05

Gemini: prompt → PageConfig → styled Next.js. gemini

When the job is data-shaped, I flip to a different pattern: don’t ask for a component, ask for a config. Have the model emit structured JSON that describes the page, then render that config with code you control. You get AI flexibility on content and deterministic control on layout. This is Roma Armstrong’s whole move and it scales beautifully.

ask for the shape, then render it 
// 1. Gemini returns a typed config, not markup
type PageConfig = {
  title: string
  sections: { kind: 'hero' | 'grid' | 'cta'; props: Record<string, unknown> }[]
}

// 2. You own a tiny renderer — one switch, fully styled by you
function Page({ config }: { config: PageConfig }) {
  return config.sections.map((s, i) => {
    switch (s.kind) {
      case 'hero': return <Hero key={i} {...s.props} />
      case 'grid': return <CardGrid key={i} {...s.props} />
      case 'cta':  return <CallToAction key={i} {...s.props} />
    }
  })
}

The win: the model never touches your CSS. It decides what goes on the page; your components decide how it looks. Dark mode, brand tokens, responsive rules — all baked into the renderer once. The AI just fills the slots. Regenerate the config a hundred times and every result is on-brand.

try it ↳
Next build, instead of “make me a pricing page,” ask for “a JSON array of pricing tiers with name, price, features[], highlighted.” Then write the <Tier> component yourself. You’ll never go back to asking for raw markup.
06

Wire the model in — streaming, the part that feels like magic. engineer

Eventually the app needs to talk to a model at runtime, not just be built by one. This is where most no-code folks stall — and where it’s genuinely easier than it looks. The Vercel AI SDK gives you one hook on the frontend and one function on the backend. Streaming, loading states, and message history come free. Swap the provider import to switch between Claude and Gemini.

app/api/chat/route.ts — the backend 
import { streamText } from 'ai'
import { anthropic } from '@ai-sdk/anthropic'
// swap line above for: import { google } from '@ai-sdk/google'

export async function POST(req: Request) {
  const { messages } = await req.json()
  const result = streamText({
    model: anthropic('claude-sonnet-4-6'),
    system: 'You are a calm, concise habit coach.',
    messages,
  })
  return result.toUIMessageStreamResponse()
}
the frontend — one hook 
'use client'
import { useChat } from '@ai-sdk/react'

export default function Coach() {
  const { messages, sendMessage, status } = useChat()
  return (
    <div>
      {messages.map(m => <p key={m.id}><b>{m.role}</b>: {m.parts.map(p => p.type === 'text' ? p.text : '')}</p>)}
      {status === 'streaming' && <span>…thinking</span>}
    </div>
  )
}

That’s a working chat app. The streaming text, the role labels, the in-flight state — all handled. Dray’s framing is the one that stuck with me: “an AI engineer is just a regular engineer who’s comfortable with one non-deterministic function call.” This is that call. Everything around it is the boring, knowable web you already understand.

heads up ↳
Your API key lives in .env.local as ANTHROPIC_API_KEY (or GOOGLE_GENERATIVE_AI_API_KEY), and it stays server-side — in the route.ts, never the client component. Ship a key to the browser and it’s scraped within the hour.
07

The open notebook — a throwaway script to feel the model out. engineer

Before I wire a model into a UI, I sit with it in a plain script. No frontend, no framework — just a file I run from the terminal and read the output. This is Cal’s open-notebook habit and it’s the most underrated move in here. You learn how the model actually behaves on your task before you build anything around it.

try.ts — run it, read it, tweak it 
import Anthropic from '@anthropic-ai/sdk'
const client = new Anthropic()  // reads ANTHROPIC_API_KEY from env

const prompts = [
  'Summarize this in one calm sentence: ...',
  'Now do it for a 9-year-old.',
  'Now as a haiku.',
]

for (const p of prompts) {
  const msg = await client.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 300,
    messages: [{ role: 'user', content: p }],
  })
  console.log('\n— ' + p)
  console.log(msg.content[0].text)
}
run it 
$ npx tsx try.ts
— Summarize this in one calm sentence: ...
A quiet recap, one breath long.

— Now do it for a 9-year-old.
Here's the short version, easy words only.

— Now as a haiku.
five seven five, done.

Fifteen lines, zero ceremony. I keep a scratch/ folder full of these — one per experiment, dated, never cleaned up. They’re a logbook. When a build later misbehaves, half the time the fix is something I already learned in one of these tiny scripts and forgot. The notebook remembers.

Cal’s rule, paraphrased: write the dumb script first. You can’t design a system around a model you’ve never actually watched answer.

08

Iterate by screenshot — the diary-style design pass. design

Here’s a move that feels illegal the first time: when a layout is almost right but you can’t name what’s off, screenshot it and paste the image back to the model. “Here’s the current state. The spacing feels uneven and the header competes with the hero — fix it.” It can see what you see. This is Sébastien Castiel’s diary loop: build, screenshot, critique, repeat — and you keep the screenshots as a visual changelog.

the visual iteration loop 
# the cycle, written out
1. build / render the current version
2. screenshot it  (Cmd+Shift+4 on mac → drag)
3. paste image back: "what's visually off here?"
4. apply the ONE most important fix it names
5. screenshot again → keep both, side by side
6. repeat until you stop finding things

# after 4–5 passes you have a filmstrip of the design
# evolving. that filmstrip IS the story you post.

Two things this unlocks. First, you fix problems you couldn’t articulate — the model names them for you, which teaches you the vocabulary from move 4. Second, the screenshot trail is content. A before/after filmstrip of a layout finding its form is one of the most-shared things you can post, because it shows the work, not just the result.

try it ↳
Take a screenshot of any page you half-like and paste it with one question: “What are the three biggest visual problems here, ranked?” Fix only #1. Screenshot again. You’ll learn more about design in five loops than in five articles.
09

The eval loop — the AI engineer’s habit that keeps you honest. engineer

Here’s the move that separates a demo from a product. A model’s output is non-deterministic, so “it worked when I tried it” is not the same as “it works.” Before you ship anything that runs a prompt for real users, write a handful of checks — inputs you know the answer to — and run them every time you change the prompt. This is the whole discipline behind “AI engineering,” demystified.

evals.ts — five lines of insurance 
const cases = [
  { input: 'I ran 3 miles today',      expect: 'exercise' },
  { input: 'skipped breakfast again',    expect: 'nutrition' },
  { input: 'in bed by 10, finally',      expect: 'sleep' },
]

let pass = 0
for (const c of cases) {
  const got = await classify(c.input)   // your prompt, wrapped in a fn
  const ok = got === c.expect
  console.log(ok ? '✓' : '✗', c.input, '→', got)
  if (ok) pass++
}
console.log(`\n${pass}/${cases.length} passing`)

That’s it. Ten cases is plenty to start. Now when you “improve” the prompt and three checks start failing, you catch it before your users do. I’ve shipped prompt changes that felt better and quietly broke a category — this loop is the only reason I noticed. Treat the prompt like code, because it is code now.

heads up ↳
You don’t need a framework for this on day one. A loop and a counter beat an elaborate eval harness you never run. Add the fancy tooling when ten cases stops being enough, not before.
10

Ship the thing — the last mile is the shortest now. ship

The hardest part used to be deployment. It’s now the easiest. A Next.js app with the AI SDK goes live in one command, with your env keys set in the dashboard. The bottleneck is no longer infrastructure — it’s your willingness to put a v1 in front of someone. So ship the embarrassing version. The screenshots from move 8 are your launch post.

prompt → product, the last step 
$ npm i -g vercel
$ vercel            # preview deploy, gives you a URL
$ vercel --prod     # promote it to production

# set your keys once, in the dashboard:
#   Settings → Environment Variables
#   ANTHROPIC_API_KEY / GOOGLE_GENERATIVE_AI_API_KEY

✓ Production: https://your-habit-coach.vercel.app

That URL is the finish line for the loop we started ten moves ago: a sentence became a spec, the spec became an Artifact, the Artifact became a wired-up app with checks, and the app is now a link you can text to a friend. None of it required being a developer. It required being clear, iterating in small steps, and shipping before it felt ready.

every L is a W if you ship it and write down what broke. The notebook is the real product.
