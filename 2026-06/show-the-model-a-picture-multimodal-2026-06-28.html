Show the model a picture — the day you stop describing the screenshot and just hand it over.

You've been typing paragraphs to explain a UI the model could see in one attachment. Multimodal is the move: drop an image into the same messages call you already make, then — the part most people miss — ask for a typed list of findings instead of a wall of prose. For the longest time I narrated screens to the model like a radio play: "there's a hero, the CTA is amber, the spacing feels off in the third card." It was slow and it was lossy — I was re-encoding pixels into prose and hoping the model decoded them back. Then I just attached the screenshot. The narration disappeared and the answers got sharper, because the model was finally looking at the same thing I was.

Multimodal isn't a different API. It's one new kind of content block on the message you already send — an image sitting right next to your text. Send a screenshot, a photo, a chart, a receipt, a whiteboard. The model reads it and answers in the same turn.

The unlock isn't the attachment, though — it's what you ask for. A vague "what's wrong with this?" gets you a vague paragraph. Ask for a schema-shaped list of findings (this is Vol. 23 wearing sunglasses) and you get back something your code can render, sort, and act on. Ten moves below: attach it, shape the answer, point at a region, tune resolution for cost, and turn a picture of a UI into a build spec.

01

Attach the image — it's one new block on the message you already send. setup

No new endpoint, no special model. The content of a message can be a list of blocks instead of a plain string — so you put an image block and a text block side by side in the same user turn. The image carries the pixels; the text carries the question. The model reads both together.

see.py — an image block next to a text block
import anthropic, base64, pathlib
client = anthropic.Anthropic()

img = base64.standard_b64encode(
    pathlib.Path("screenshot.png").read_bytes()
).decode()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[{"role": "user", "content": [
        {"type": "image", "source": {   # <-- the new block
            "type": "base64",
            "media_type": "image/png",
            "data": img,
        }},
        {"type": "text", "text":
            "What's the single biggest UX problem on this screen?"},
    ]}],
)
try it
Screenshot any app you use daily — ⌘⇧4 on a Mac — and run exactly that. Then do the thing you used to do: write a paragraph describing the same screen and ask cold. The attached-image answer is more specific every time, because it isn't guessing at your description.
02

Read the shape — image goes in, ordinary text comes out. read

The request got a new block type, but the response doesn't. Vision is input-only: the model can't draw you a picture back, it answers in words (or, if you ask, in JSON). So response.content is the same text you're used to — the image just made that text smarter. Order matters a little: put the image before the question so the model has looked before it's asked.

content[0].type == "image"

The pixels. A base64 PNG or a URL. The model sees the layout, the colors, the text rendered in the screenshot, the spacing — everything you'd see glancing at it.

content[1].type == "text"

The question. "What's wrong here?" / "Extract the line items." / "Return findings as JSON." This is the steering — the same image answers very differently depending on the ask.

image first, then the text. it reads top-to-bottom like you do.

03

Ask for findings, not a paragraph — this is the whole game. see

A bare "what do you think?" gets you a polite essay where the real bug is sentence four of paragraph two. Don't accept prose. Hand the model a schema and demand a list — each item a title, a severity, a region, a fix. Now the answer is sortable, renderable, and rankable. This is Vol. 23 pointed at an image: structured output is what turns "looks fine to me" into a punch-list.

findings.py — a tool schema turns the critique into data
tools = [{
    "name": "report_findings",
    "description": "Structured UX review of the screenshot.",
    "input_schema": {"type": "object", "properties": {
        "findings": {"type": "array", "items": {
            "type": "object", "properties": {
                "title":    {"type": "string"},
                "severity": {"enum": ["high","med","low"]},
                "region":   {"type": "string"},   # "hero / right"
                "fix":      {"type": "string"},
            }, "required": ["title","severity","fix"]},
        }},
    }, "required": ["findings"]},
}]
# force the schema: tool_choice = report_findings
# -> response.content[0].input["findings"] is now sortable data
try it
Sort the returned list by severity and render the high ones in red at the top — exactly like the live panel above. A reviewer who sees a ranked punch-list trusts it more than a paragraph, and your code can act on it: open a ticket per finding, diff two screens, gate a deploy.
04

Point at one region — crop the question before you ask it. see

When you only care about the nav bar, don't send the whole 4K page and write "look at the top." Two better moves: crop the image to the region before you attach it, or annotate it — draw a red box, add a number — and reference the marker in your prompt. Less to look at means a tighter, cheaper, more accurate answer. Models read marked-up images well; a literal red arrow is a legitimate prompt.

heads up
Don't ask for pixel-perfect coordinates — "the bug is at x=412, y=88." Vision models reason about regions and relationships ("the right half of the hero"), not exact pixel math. Ask for a named region or a crop, not a bounding box you'll trust to the pixel. Crop first; let the frame be the coordinate.
05

Send many images — and label which is which. see

You can stack several image blocks in one turn — perfect for before/after diffs, a flow across three screens, or "which of these mockups is strongest?" The catch: the model can't read your variable names. Put a text label before each image so it can refer back to them, then ask the comparison question last.

compare.py — label each image so the answer can cite it
content = [
    {"type": "text", "text": "Image A — current design:"},
    {"type": "image", "source": a_src},
    {"type": "text", "text": "Image B — proposed redesign:"},
    {"type": "image", "source": b_src},
    {"type": "text", "text":
        "What did B improve, and what did it quietly break?"},
]
# the model can now answer "in Image B, the CTA..." by name
try it
This is the Vol. 27 trick made literal: generate the same screen with Claude and with Gemini, screenshot both, send them labeled A and B, and ask the model to critique its own and its rival's output. The self-review is often where the best fix hides.
06

Tune resolution — remember that pixels are tokens. cost

An image isn't free; it's billed as input tokens, and the count scales with the image's area. A giant retina screenshot can quietly cost more than the prompt around it. The providers resize very large images down anyway, so you gain nothing by sending a monster — you just pay for pixels they throw away. Resize to roughly what the model needs to read the content, and your bill drops without hurting the answer.

resize.py — cap the long edge before you send
from PIL import Image

im = Image.open("screenshot.png")
im.thumbnail((1568, 1568))   # cap the long edge ~1568px
im.save("small.png")        # readable, far fewer tokens

# rough rule of thumb for token cost:
#   tokens ≈ (width_px × height_px) / 750
# a 1568×1568 image ≈ ~1,600 input tokens. budget per image.
heads up
This is the through-line to Vol. 25: every image is a recurring line item. One screenshot in a chat is nothing; a screenshot per frame of a video, or per item in a batch, adds up fast. Resize at the edge, send the smallest image that still reads, and measure it like you measure tokens.
07

URL or base64 — pick the intake that fits where the image lives. setup

Two ways to hand over the pixels. Base64 inlines the bytes right in the request — best for a local file or something you generated on the fly. A URL source lets the provider fetch a publicly reachable image — best when it already lives on the web and you don't want to ship the bytes yourself. Same image block, different source.type.

intake.py — same block, two source types
# A) local / generated bytes → base64
{"type": "image", "source": {
    "type": "base64",
    "media_type": "image/png",
    "data": b64_string,
}}

# B) already on the public web → url
{"type": "image", "source": {
    "type": "url",
    "url": "https://example.com/hero.png",
}}
heads up
Stick to the common formats — PNG, JPEG, GIF, WebP. Set the media_type to match the actual bytes; mislabel a JPEG as PNG and you'll get a decode error that reads like a mystery. The URL path needs a link the provider can actually reach — a localhost or auth-walled URL won't work.
08

Know what it can't see — the honest limits beat a confident wrong answer. gotcha

Vision is strong, not magic. It reads UI, charts, diagrams, documents, and handwriting well. It gets shaky on tiny text, exact pixel measurements, precise counts in a crowded image, rotated or low-contrast scans, and anything where a small visual detail flips the meaning. The failure mode is the dangerous one: it answers confidently anyway. So build the escape hatch into your prompt.

AskVision?Why
Read the text on this screenstrongOCR-grade on legible type
Critique this layoutstrongreasons about hierarchy & balance
Extract a table / receiptstrongstructure + values together
"Exactly how many pixels…?"shakyno precise pixel math
Count 80 dots in a chartshakydense counting drifts
Read 6px greeked textshakybelow legibility — it'll guess

add "say 'unclear' if you can't read it" — calibrated beats confident-wrong.

09

Turn a screen into a build spec — the move that closes the design loop. ship

Here's where it pays off. Screenshot a design you admire (or your own mockup) and ask the model to return a PageConfig — the same structured layout JSON from Vol. 12 — describing what it sees: sections, hierarchy, the rough token palette. Now you've gone pixels → spec → code without typing a word of description. The image is the brief.

spec.py — a screenshot becomes a layout config
prompt = (
    "Describe this screen as a PageConfig: an ordered list of "
    "sections, each with a type, the key copy, and the dominant "
    "colors as hex. Don't invent content you can't see."
)
# content = [ image_block, {"type":"text","text": prompt} ]

# -> {"sections": [
#      {"type":"hero","headline":"...","bg":["#7C5CFC","#3B6BF4"]},
#      {"type":"feature_grid","cols":3, ...},
#      {"type":"cta","label":"Sign up","style":"amber"} ]}

# feed that config into your renderer from Vol. 12 → live UI
try it
Add the guardrail "don't invent content you can't see" to the prompt — it's the single most useful line. Without it the model helpfully hallucinates a pricing section that was never in the screenshot. With it, the spec stays honest to the pixels, and honest specs build the right thing.
10

Verify with the same eval harness — pictures get graded too. ship

Don't trust a vision feature on vibes any more than a text one. The harness from Vol. 24 works unchanged: a golden set of images, each with the answer you expect, and a judge that scores the model's output against it. This is how you catch the silent regressions — the resize that made small text unreadable, the model update that changed how it ranks severity. The image is just another input to grade.

eval_vision.py — golden images, expected findings
golden = [
    {"img": "low_contrast_hero.png",
     "must_flag": "contrast"},
    {"img": "clean_layout.png",
     "must_flag": None},   # should find nothing — no false alarms
]
for case in golden:
    out = review(case["img"])             # the move-3 findings call
    ok = flagged(out, case["must_flag"])
    print(case["img"], "✓" if ok else "✗")

# low_contrast_hero.png ✓   # caught the real bug
# clean_layout.png       ✓   # didn't cry wolf on a fine screen
try it
Put a clean screenshot with nothing wrong in your golden set. A vision reviewer that invents problems on a perfect screen is worse than useless — testing the no-findings case keeps it from crying wolf. Grade both the catches and the restraint.
