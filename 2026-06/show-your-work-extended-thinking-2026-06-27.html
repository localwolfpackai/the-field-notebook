For a year I treated the model like a vending machine: prompt in, answer out, and if the answer was wrong I just shook the machine harder. Extended thinking changed that. It's one field — thinking: { type: "enabled", budget_tokens: N } — and it tells the model to think before it speaks, on a scratchpad you actually get to read.

What comes back isn't one block of text anymore. It's two: a thinking block where the model works the problem out in the open, then the normal answer block built on top of that work. On a gnarly puzzle the difference is night and day — the same model that confidently flubbed it cold gets it right when it's allowed to show its steps first.

But it isn't free and it isn't always right. Those thinking tokens are billed as output, they eat your context window, and on a "what's the capital of France" they're pure waste. Ten moves below: enable it, budget it, stream it, preserve it across tools, and — the move most guides skip — turn it off when the task doesn't earn it. The panel under this intro is live: drag the budget and watch where your tokens go.

01

Flip the one switch — it's a single field on the request. setup

There's no new endpoint, no special model name, no SDK upgrade dance. You take the messages.create call you already make and add one object: thinking. Set its type to enabled and give it a budget_tokens ceiling. That's the whole on-ramp. The model now reasons on a private scratchpad and hands you the work back alongside the answer.

basic.py — the entire diff is the thinking block
import anthropic
client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=4000,
    thinking={                       # <-- the only new thing
        "type": "enabled",
        "budget_tokens": 2000,
    },
    messages=[{"role": "user", "content":
        "Three guests pay $30 for a $25 room. The bellboy "
        "pockets $2 and returns $1 each. Where's the missing $1?"}],
)
try it
Run that classic missing-dollar riddle twice — once with the thinking block, once without it. Cold, the model often parrots the trick's wrong framing. With a scratchpad, it catches that you're adding the $2 when you should be subtracting it. Same model, one field, a correct answer.
02

Read the new shape — the response is two blocks now, not one. read

Before, response.content was basically one text block. Turn on thinking and it becomes a list: a thinking block first, then the text block with the actual answer. If your code grabbed content[0].text and called it a day, it will now reach into the scratchpad by mistake. Loop the blocks and branch on block.type — show the thinking in a collapsible drawer, render the text as the reply.

block.type == "thinking"

Let me reframe. The guests paid $27 total. Of that, $25 is the room and $2 is the bellboy. Adding the $2 to the $27 double-counts it — the right move is $27 − $2 = $25. There is no missing dollar; the question mis-groups the math.

block.type == "text"

There's no missing dollar. The $27 the guests paid already includes the bellboy's $2; the question wrongly adds it again instead of subtracting. $27 − $2 = $25, the room.

render.py — branch on the block type
for block in response.content:
    if block.type == "thinking":
        show_drawer(block.thinking)   # the visible scratchpad
    elif block.type == "text":
        render_answer(block.text)     # the reply users see

the thinking block carries a `signature` too — you'll need it in move 07.

03

Set a budget that fits the task — start at the floor, climb on purpose. budget

budget_tokens is a ceiling on how much the model may think before it must answer. The floor is 1,024; ask for less and the API rejects it. The official advice is the disciplined one: start at the minimum and raise incrementally until answers stop improving. Don't open with 16k "to be safe" — you'll pay for reasoning the task never needed. Match the dial to the job.

lean budgets — 1k–2k
logic checks classification safety gates tool picking quick math
deep budgets — 8k–16k+
multi-step proofs debugging agent planning untangle constraints long-form reasoning
heads up
budget_tokens must be less than max_tokens — thinking and the answer share that ceiling. If you set a 16k budget under a 4k max_tokens, the model has no room left to answer. Raise max_tokens above the budget, always.
04

Watch it work — stream the thinking token by token. think

Deep thinking adds latency, and a frozen UI for ten seconds feels broken (that's the whole point of Vol. 22). The fix is the same here: stream. With thinking on, the stream emits the scratchpad first — thinking_delta events — then switches to text_delta for the answer. Pipe the thinking into a live "thinking…" drawer so the user watches the model reason instead of staring at a spinner.

stream.py — route deltas by their event type
with client.messages.stream(
    model="claude-sonnet-4-6", max_tokens=4000,
    thinking={"type": "enabled", "budget_tokens": 2000},
    messages=[{"role": "user", "content": prompt}],
) as stream:
    for event in stream:
        if event.type == "content_block_delta":
            d = event.delta
            if d.type == "thinking_delta":
                drawer.write(d.thinking)   # scratchpad, live
            elif d.type == "text_delta":
                answer.write(d.text)       # the reply, live
try it
Render the thinking drawer in a dimmer, smaller, monospace style and the answer in your normal body type. The visual demotion reads exactly right: "here's me working, here's my answer." Users trust the answer more because they saw the work.
05

Count the tokens — thinking is billed as output, and it adds up. budget

Here's the part that surprises people: thinking tokens are output tokens. They bill at the output rate, they count against your rate limits, and they sit inside the context window right alongside the answer. A 16k thinking budget on every call is a real line item, not a rounding error. Read response.usage after a few representative calls and you'll see precisely what your reasoning costs.

usage.py — what the scratchpad actually cost
print(response.usage)
# Usage(
#   input_tokens=84,
#   output_tokens=1736,   # <-- thinking + answer, together
# )

# thinking lives *inside* output. budget it like you budget
# max_tokens — every call, multiplied by your traffic.
heads up
This is the through-line back to Vol. 25: extended thinking trades tokens and latency for quality. That's a great trade on a hard problem and a terrible one on an easy lookup. Measure the trade per task type — don't leave a fat budget on globally and call it a day.
06

Drop the knobs it can't use anymore — thinking changes the rules. gotcha

Turning thinking on quietly disables a few things you may be used to reaching for. You can't set temperature, top_p, or top_k while thinking is enabled, and you can't pre-fill the assistant's response. The reasoning process needs its own sampling, so those levers go away. Leave them out and the call is clean; leave them in and you'll get an error that reads like a mystery until you know this rule.

LeverWith thinking on?Do this instead
temperaturenot allowedomit it — the model self-samples
top_p / top_knot allowedomit them
response pre-fillnot allowedsteer via the prompt, not a primer
budget < 1,024rejected1,024 is the floor — start there
budget ≥ max_tokensno room to answerraise max_tokens above the budget

most "thinking won't enable" bugs are just one of these five. check them first.

07

Keep the blocks alive across tool calls — pass them back untouched. tools

This is the move people get wrong when they wire thinking into an agent. When the model thinks, then calls a tool, you run the tool and send the result back — and you must send the original thinking block back with it, signature and all. That block is the model's memory of why it reached for the tool. Strip it out and the model loses the thread; pass it back verbatim and it picks up exactly where it left off. It won't emit a fresh thinking block until the next non-tool_result turn.

agent_loop.py — thinking block rides along with the tool result
# 1. model thinks, then asks for a tool. keep its WHOLE turn:
messages.append({"role": "assistant", "content": response.content})
#   ^ response.content still holds the thinking block + signature

# 2. hand back the tool result as the next user turn:
messages.append({"role": "user", "content": [{
    "type": "tool_result",
    "tool_use_id": tool_use.id,
    "content": run_tool(tool_use),
}]})

# 3. continue — the model resumes with its reasoning intact
response = client.messages.create(model=MODEL, max_tokens=4000,
    thinking={"type": "enabled", "budget_tokens": 2000},
    tools=tools, messages=messages)
heads up
Don't hand-edit or "clean up" the thinking block before sending it back. The signature is how the API verifies the block is genuine and unaltered. Mutate the text and you'll break the signature — pass the object through exactly as you got it. Pairs cleanly with the agent loop in Vol. 19.
08

Don't panic at a redacted block — it's still load-bearing. gotcha

Once in a while a thinking block comes back as redacted_thinking instead of plain text — the internal reasoning got flagged by safety systems and returned encrypted. Your instinct will be to drop it. Don't. Pass it back exactly like a normal thinking block; the API decrypts it on its side so the model keeps its context. You just can't read that one. Handle it by type, render a neutral placeholder, move on.

redacted.py — treat it as opaque, keep it in the history
for block in response.content:
    if block.type == "thinking":
        drawer.write(block.thinking)
    elif block.type == "redacted_thinking":
        drawer.write("[reasoning hidden — kept for context]")
        # still append it to messages on the next turn!
    elif block.type == "text":
        render_answer(block.text)
try it
You don't have to wait for one in the wild to test your handling. The docs ship a magic trigger string that deterministically returns a redacted block — send it once, confirm your UI shows the placeholder and your agent still threads the block through. Test the rare path on purpose so it never surprises you in production.
09

Know when NOT to think — the move every hype post skips. read

Extended thinking is a power tool, and power tools are wrong for most jobs. If the task is a lookup, a format conversion, a short rewrite, or anything the model nails cold, thinking just adds latency and cost for no quality gain. Reserve it for problems with real steps — logic, math, debugging, planning, untangling constraints — where reasoning in the open is what flips a wrong answer to a right one. The honest default is off, switched on deliberately.

TaskThink?Why
"Capital of France?"noknown cold — pure waste
Reformat JSON → CSVnomechanical, no reasoning
Summarize a paragraphnoone-pass, low stakes
Multi-step word problemyessteps are the whole game
Debug from a stack traceyesneeds to reason about cause
Plan an agent's next 5 movesyestradeoffs worth thinking through

route it: cheap fast model with no thinking for easy calls, thinking on only for the hard ones.

10

Pair it with an eval — prove the budget actually bought you accuracy. think

Don't trust the vibe that "thinking makes it smarter." Measure it. Take the golden test set from Vol. 24 and run it three ways: thinking off, a lean budget, a deep budget. Now you have a number, not a hunch — the exact accuracy each setting buys and the exact tokens each one costs. Often a 2k budget captures most of the win and a 16k budget barely moves the needle. The eval tells you where to stop paying.

sweep.py — grade accuracy against budget, pick the knee
for budget in [None, 2000, 8000, 16000]:
    cfg = {} if budget is None \
          else {"type": "enabled", "budget_tokens": budget}
    score, out_tokens = run_eval(golden_set, thinking=cfg)
    print(f"budget={budget}: {score:.0%} acc, {out_tokens} out-tok")

# budget=None:  71% acc,   180 out-tok   # fast, cheap, weakest
# budget=2000:  94% acc,  1900 out-tok   # <-- the knee. ship this.
# budget=8000:  95% acc,  6400 out-tok   # +1% for 3x the tokens
# budget=16000: 95% acc, 12800 out-tok   # pure waste past the knee
try it
Plot accuracy vs. budget and look for the knee — the point where the curve flattens. That's your production setting: the smallest budget that captures the accuracy. Re-run the sweep whenever the task changes. The eval, not the hype, picks your number.
