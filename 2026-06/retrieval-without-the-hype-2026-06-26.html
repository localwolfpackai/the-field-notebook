Retrieval without the hype — nine moves to give your AI a memory without drowning it.

Last entry tuned the two dials so your feature ships cheap and fast. This one fixes the reason it was guessing in the first place: it didn't know your stuff. "RAG" is the scary acronym for a plain idea — let the model look something up before it answers. Here's how to wire that without a vector-database PhD or a $400 prompt. Both models, move for move.

I built a support bot for a client and it confidently invented a refund policy that didn't exist. Not maliciously — it just had no idea what their actual policy was, so it filled the gap with a plausible-sounding one. The fix wasn't a smarter model or a longer prompt. It was letting the bot read the real policy doc before it spoke. That's the whole of retrieval, stripped of the acronyms: find the relevant page, hand it to the model, ask the question on top of it.

Everyone reaches for the wrong fix first. You can't fine-tune your way out of "the model doesn't know your private docs" without a research budget. You can't paste your whole knowledge base into every prompt — it's slow, expensive (see Vol. 25), and past a certain size the model loses the thread anyway. Retrieval is the middle path: store your knowledge once, and at question-time fetch only the few paragraphs that matter.

Nine moves, each with a number, a one-line claim, real code, and a try-it crumb. The panel under this intro is live — ask it a question and watch it pull the matching chunks out of a tiny knowledge base by meaning, not keywords. No build step, no database required to see the idea click.

01

First, check if you even need a database — most "RAG" problems are a paste-the-doc problem. data

Retrieval has a real cost: another pipeline to build, embed, store, and keep fresh. Before you take it on, ask the cheap question — does the whole knowledge fit comfortably in one prompt? If your "knowledge base" is a 4-page policy doc, you don't need vectors. Paste it into the system prompt, cache it (Vol. 25, Move 04), and you're done. Retrieval earns its keep when the corpus is too big to send every time, or changes too often to hard-code.

One doc, fits in a prompt paste it + cache the prefix no
Hundreds of docs, a few relevant per question embed + retrieve the top few yes
Knowledge changes daily (prices, tickets, stock) retrieve fresh, never bake it in yes
You want it to learn a new skill, not facts that's fine-tuning, not retrieval no
try it
Count the tokens in your entire knowledge base. Under ~50k and mostly static? Skip this whole entry — paste and cache beats a vector store you have to babysit. Retrieval is for when "paste it all" stops being an option.
02

Chunk your docs — cut them into pieces small enough to each be one idea. backend

You don't store whole documents; you store chunks. The reason is simple: when someone asks about refunds, you want to hand the model the refund paragraph, not the entire 40-page handbook it's buried in. So slice each doc into bite-sized pieces — a few hundred tokens each, ideally split on natural seams (headings, paragraphs) so a chunk is one coherent thought. Add a little overlap so an idea straddling two chunks isn't sliced in half.

chunk.ts — split on seams, keep a little overlap
// Aim for ~300–500 tokens per chunk. Split on paragraphs, not mid-sentence.
function chunk(doc: string, size = 1600, overlap = 200): string[] {
  const paras = doc.split(/\n\s*\n/);   // natural seams first
  const out: string[] = [];
  let buf = "";

  for (const p of paras) {
    if ((buf + p).length > size) {
      out.push(buf.trim());
      buf = buf.slice(-overlap);     // carry a tail so ideas don't get cut
    }
    buf += "\n\n" + p;
  }
  if (buf.trim()) out.push(buf.trim());
  return out;   // each item = one searchable, self-contained idea
}
heads up
Chunk too big and every search drags in noise the model has to wade through. Too small and you shred the context — a chunk that says "it's 30 days" is useless if "the refund window" lives in the chunk before it. When unsure, lean slightly larger and let the overlap save you.
03

Embed each chunk — turn its meaning into a list of numbers. model

Here's the one genuinely new idea, and it's less mystical than it sounds. An embedding is a function that reads a piece of text and spits out a long list of numbers — a vector — that captures its meaning. Two chunks about the same thing land near each other in that number-space, even if they share no words. "Money back within 30 days" and "Can I get a refund?" end up as neighbors. That closeness is the entire trick: search becomes "find the chunks nearest to the question."

embed.ts — text in, a vector of meaning out
// You run this ONCE per chunk, ahead of time, and store the result.
async function embed(text: string): Promise<number[]> {
  const res = await google.embedContent({
    model: "text-embedding-004",
    content: text,
  });
  return res.embedding.values;   // e.g. [0.013, -0.21, 0.08, … ] × 768
}

// Embed the whole knowledge base, once:
const index = await Promise.all(
  chunks.map(async (text) => ({ text, vector: await embed(text) }))
);
// `index` is now your searchable memory. Save it (Move 04).

04

Store the vectors where you can actually search them — a JSON file scales, until it doesn't. data

For a prototype, your index is just an array in memory or a JSON file on disk — genuinely fine for a few thousand chunks. When that gets slow, you don't need an exotic "vector database"; you need Postgres with the pgvector extension, which adds a vector column and a similarity operator to the database you probably already have. Same SQL you know, plus the ability to ask "nearest neighbors."

store.sql — your existing Postgres, now with vectors
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id     bigserial PRIMARY KEY,
  doc    text,
  body   text,                 -- the chunk's words (you'll send these to the model)
  embedding vector(768)        -- the chunk's meaning, as 768 numbers
);

-- an index so nearest-neighbor search stays fast at scale
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
try it
Don't reach for a new managed vector DB on day one. If your app already has Postgres (Supabase, Neon — see the stack notes), turn on pgvector and keep your vectors next to your real data. One database, one backup, one thing to reason about.
05

Search by meaning — embed the question too, then find its nearest chunks. backend

Retrieval at question-time is symmetric with indexing: you embed the user's question with the same model, then ask for the stored chunks whose vectors sit closest to it. "Closest" is usually cosine similarity — a single number from -1 to 1 measuring how aligned two vectors are. Higher means more similar in meaning. Pull the top k (3–6 is a sane start) and you've got the relevant context, ranked.

search.sql — one query returns the top matches
-- <=> is pgvector's cosine-distance operator. Smaller distance = closer.
SELECT body, 1 - (embedding <=> $1) AS similarity
FROM   chunks
ORDER BY embedding <=> $1     -- $1 = the question's embedding
LIMIT  5;                     -- the 5 most relevant chunks, best first

-- No vectors yet? The same idea in 6 lines of JS:
const dot = (a,b) => a.reduce((s,x,i) => s + x*b[i], 0);
const mag = (a) => Math.sqrt(dot(a,a));
const cosine = (a,b) => dot(a,b) / (mag(a)*mag(b));   // 1 = identical meaning
heads up
This is exactly what the live panel above is doing — embeddings are precomputed, but the cosine ranking runs in your browser on click. Notice the founder question returns low scores across the board: nothing in the docs is close, which is the signal Move 07 turns into an honest "I don't know."
06

Stuff the top chunks into the prompt — the "generation" half is almost anticlimactic. model

Here's the punchline nobody warns you about: once you have the right chunks, the rest is a normal prompt. You paste the retrieved text in as context, put the user's question underneath, and call the model exactly like always. That's the G in RAG — generation — and it's the part you already know. The intelligence was never in the model "knowing" your data; it's in handing it the right page at the right moment.

answer.ts — retrieve, then ask on top of it
const hits = await search(question, { k: 5 });   // Move 05
const context = hits.map((h) => h.body).join("\n\n---\n\n");

const answer = await client.messages.create({
  model: "claude-sonnet-4-6",
  max_tokens: 500,
  system: "Answer using ONLY the context below. " +
          "If it isn't there, say you don't know.",
  messages: [{
    role: "user",
    content: `Context:\n${context}\n\nQuestion: ${question}`,
  }],
});
// Grounded answer — drawn from your docs, not the model's imagination.

retrieve → stuff → ask. that's the whole loop. everything else is making each step less dumb.

07

Make the model cite its sources — and let it say "I don't know." model

A grounded answer with no receipts is still asking for trust. Tell the model to attach the source of each claim, and — just as important — to refuse when the retrieved context doesn't contain the answer. The "I don't know" is the feature: it's the difference between my refund-policy bot inventing a number and admitting the doc is silent. Pair this with typed output (Vol. 23) and you get answers and citations your UI can render as real links.

cite.ts — grounded answer + where it came from
// Tag each chunk with its source, then ask for citations back.
const context = hits
  .map((h, i) => `[${i + 1}] (${h.doc})\n${h.body}`)
  .join("\n\n");

const system = `Answer ONLY from the context. Cite sources as [1], [2].
If the context doesn't answer it, reply exactly: "I don't have that in my docs."`;

// → "Refunds are available within 30 days of purchase [1]."
// → "I don't have that in my docs."   ← when nothing relevant came back
try it
Add a floor on the top score: if even your best chunk's similarity is below, say, 0.4, don't bother calling the model — just return "I don't have that." Cheaper, faster, and it kills the most embarrassing hallucinations before they happen.
08

Re-rank when the top hit isn't the best hit — embeddings get you close, not perfect. backend

Pure vector search is fast but a little blunt: it ranks by overall similarity, which occasionally floats a vaguely-related chunk above the one that truly answers the question. The fix is a second, sharper pass. Retrieve a generous k (say 20), then re-rank those few with a model that reads question-and-chunk together and scores true relevance. You spend a little more on 20 candidates to make sure the top 3 you actually send are the right 3.

heads up
Don't add re-ranking until plain search visibly fails — it's a Move-08 problem, not a Move-01 one. Most small knowledge bases are fine with top-k alone. Reach for it when you can see the right chunk sitting at rank 4 instead of rank 1.
09

Keep the index fresh — a confident answer from a stale doc is the worst kind. data

The day your docs change, your index is wrong — and a retrieval bot will cite the outdated chunk with total confidence. So treat indexing as a pipeline, not a one-time script: when a source doc is created or edited, re-chunk and re-embed just that doc and upsert its chunks. Batch the re-embed overnight if nothing's waiting on it (Vol. 25, Move 07 — embeddings are perfect batch work). The goal is simple: what the model retrieves is always what's true today.
