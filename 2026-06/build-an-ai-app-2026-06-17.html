Field Notebook • Vol. 17 • 2026 · 06 · 17 build ai-app

Build an AI app in an afternoon — frontend + model, the non-dev way.

Past notebooks were about the model in a chat box. This one is about the model behind glass — wired into a real interface that streams, renders, and looks like you meant it. Nine steps from a one-line idea to a styled, working app. No CS degree. A model that does the heavy lifting, and a contract that keeps it honest.

—Lupo · The Mess is the Method
Read · ~15 min Stack · Next.js + Tailwind + a model API Assumes · you can run npm Voice · open-notebook, casual

The thing nobody tells you when you're not a developer: the model is the easy part. The model has been trained to write your function. What it can't read your mind about is the shape of what comes back, and where on the page it lands. So that's where I learned to spend my effort — not on the AI, on the contract around it.

I built three of these before it clicked. Every time I tried to design the screen first and bolt the model on later, I'd end up with a beautiful box that received an unpredictable blob of text. The flip — decide the data shape first, make the model promise to fill it, then design around that shape — is the whole trick. Roma Armstrong calls the shape a PageConfig. I just call it the contract.

Here's the order I follow now. Steal the steps that fit; the closer to the top, the more it matters if you skip it.

04–06The wiring — server route, the stream, render the shape

01

Say it in one sentence — then cut it in half. scope

Every app I've actually finished started as a sentence I could say out loud. "A page where I paste a job description and it spits back three resume bullet points." Notice what that sentence does: it names one input, one model call, and one shaped output. That's an afternoon.

The version that never ships sounds like "a career platform with profiles and saved history and a dashboard." Same idea, fifty times the surface. The cut is the skill. For a first build, if your sentence has the word "and" twice, delete one.

scoping out loud 
# too big — three apps wearing a trenchcoat
"a tool that writes posts AND schedules them AND tracks analytics"

# right size — one input, one call, one output
input    → a rough idea + a platform (X / LinkedIn)
call     → one model request
output   → 3 drafts in that platform's voice
try it ↳
Write your idea as input → call → output on one line. If you can't, you don't have an app yet — you have a category. Narrow until it fits.
02

Decide the output shape before you design anything. contract

This is the step I skipped for months and the one that changed everything. Before I touch a single pixel, I write down the exact JSON the model has to return. Not the prose — the structure. Once that shape exists, the UI almost designs itself, because every field is a thing on the screen.

Roma's PageConfig idea is just this taken seriously: the model doesn't return text, it returns a typed object, and your frontend is a renderer for that object. The model becomes a content database that thinks.

the-shape.ts 
// the contract. write this first, by hand.
type Draft = {
  platform: "x" | "linkedin";
  drafts: {
    hook: string;       // the first line
    body: string;
    charCount: number;   // so the UI can warn on limits
  }[];
}

Notice charCount is in there even though the model doesn't strictly need it. I put it in because the screen needs it — I want a little "248 / 280" counter under each draft. Designing the shape is designing the app. You just don't know it yet.

if a field isn't going to show up on screen, ask why the model is returning it.

03

Write the prompt that fills the shape, not one that "writes posts." model

Now the prompt has an easy job. It isn't being asked to be creative in a vacuum — it's being asked to fill in a form you already drew. I give the model the schema, one good example, and a hard rule: return only the JSON. Both Claude and Gemini have a real JSON mode for this; turn it on and half your parsing bugs disappear.

the prompt 
// system
You turn a rough idea into 3 social drafts.
Return ONLY valid JSON matching this shape:
{ platform, drafts: [{ hook, body, charCount }] }

// rules that save you later
- charCount must be the real length of body
- hook is one line, no hashtags
- if the idea is empty, return drafts: []   ← defines the edge case now

That last rule is doing a lot of quiet work. By telling the model what to do with bad input in the prompt, I've defined my empty state before I ever build it (see step 8). The prompt and the contract are the same document seen from two sides.

heads up ↳
Ask for JSON and you'll still get a model that occasionally wraps it in ```json fences or a "Sure! Here you go:". Strip fences and JSON.parse inside a try/catch. Never trust the first token to be {.
04

Put the API key on a server route — never in the browser. wiring

The one rule that isn't optional. Your model API key is a password to your credit card. If it ships to the browser, anyone who opens DevTools can read it and spend your money. So the call happens on a server route; the browser talks to your route, your route talks to the model.

In Next.js that's one file. The key lives in .env.local, which never leaves your machine and never gets committed.

app/api/draft/route.ts 
import { NextRequest } from "next/server";

export async function POST(req: NextRequest) {
  const { idea, platform } = await req.json();

  const res = await fetch("https://api.anthropic.com/v1/messages", {
    method: "POST",
    headers: {
      "x-api-key": process.env.ANTHROPIC_API_KEY!,  // stays server-side
      "anthropic-version": "2023-06-01",
      "content-type": "application/json",
    },
    body: JSON.stringify({ model: "claude-...", max_tokens: 1024, messages: [...] }),
  });

  return new Response(res.body);  // hand the stream straight back
}
heads up ↳
Add .env.local to .gitignore before your first commit, not after. A leaked key in git history is leaked forever, even if you delete the file in the next commit. Rotate it immediately if it slips.
05

Stream the response — the wait is what makes it feel cheap. wiring

A model call takes a few seconds. If your app shows a dead spinner the whole time, it feels broken even when it's working. The fix is streaming: the model sends tokens as it writes them, and you paint them as they arrive. Same total time, completely different feeling — the difference between "is this thing on?" and "oh, it's thinking."

the browser side — read the stream 
const res = await fetch("/api/draft", {
  method: "POST",
  body: JSON.stringify({ idea, platform }),
});

const reader = res.body!.getReader();
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value);
  setRawText(buffer);   // paint partial output live
}

For a structured-JSON app there's a wrinkle: half-streamed JSON isn't valid JSON yet. So while it streams I show the raw text in a "thinking" panel, and only parse into the real shape once done is true. Cal's open-notebook move here is to just console.log(buffer) on every chunk the first time, watch it fill in your terminal, and then decide how to display it. See the machine work before you dress it up.

try it ↳
Before building any UI, log each chunk to the console and just watch the text assemble itself. It's weirdly satisfying, and it tells you exactly what your render code has to handle.
06

Render the shape into panels — one field, one element. render

Because you wrote the contract in step 2, this part is almost boring — in the good way. You .map() over drafts and each field becomes a thing you can see. The hook is a heading, the body is a paragraph, the charCount is the little counter you planned for. No surprises, because you decided the shape before the model ever ran.

draft-list.tsx 
{data.drafts.map((d, i) => (
  <article key={i} className="rounded-xl border p-5">
    <h3 className="font-semibold">{d.hook}</h3>
    <p className="mt-2 text-neutral-700">{d.body}</p>
    <span className={d.charCount > limit ? "text-red-600" : "text-neutral-400"}>
      {d.charCount} / {limit}
    </span>
  </article>
))}

That's the whole render. The contract did the architecture; the JSX is just reading it out loud. This is the moment the "model is the easy part" claim from the intro pays off — you're not wrestling text, you're displaying a known object.

07

The design pass — and why Claude and Gemini feel different here. design

Now it works and looks like a homework assignment. The design pass is where you hand the model your bare component and ask it to make it feel made. This is also where the two big models show their personalities — and knowing the difference saves you a lot of nudging.

Claude leans warm + editorial

Reaches for generous padding, softer neutrals, real type hierarchy, and restraint. Ask for "a clean tool" and you tend to get whitespace and calm. Great default for anything content-shaped.

Nudge it with: "denser, more data per screen" when it gets too airy.

Gemini leans dense + structural

Reaches for data-rich layouts — tables, multi-panel grids, tight rows, dashboard energy. Strong when your app is genuinely information- heavy. Can feel cramped for a simple tool.

Nudge it with: "more breathing room, fewer elements" to loosen it up.

Whichever you use, give it the same guardrails I keep in my own design notes so the output is consistent instead of vibes: a 4px spacing grid (8 / 16 / 32 / 64), a 1200px max content width, body text contrast at 4.5:1, and 44px touch targets. Hand those numbers to the model and "make it nicer" stops being a coin flip.

the design-pass prompt 
Restyle this component. Constraints, not suggestions:
- spacing on a 4px grid (8 / 16 / 32 / 64 only)
- max content width 1200px, centered
- text contrast >= 4.5:1, interactive targets >= 44px
- one accent color, light mode, mobile-first
Keep the markup and props identical. Style only.

"keep the markup identical, style only" stops the model from quietly rewriting your working logic.

08

Build the unglamorous states — empty, loading, broken. render

This is the gap between a demo and a thing people can actually use. A demo handles the happy path. An app handles the moment the model returns nothing, times out, or sends back garbage. The good news: you defined two of these back in step 3, so you're just building what the contract already promised.

the three states you owe the user 
// 1. empty — they haven't run it yet
if (!data && !loading)  → "Paste an idea above to get started."

// 2. loading — the stream is mid-flight
if (loading)           → show the partial text + a soft pulse

// 3. broken — parse failed or the API errored
catch (e)              → "That didn't come back clean. Try again?"
                          + a retry button, not a stack trace

The error message is a copy decision, not just an engineering one. "That didn't come back clean. Try again?" tells a real person what to do. Error: SyntaxError unexpected token < tells them your app is broken and they should leave. Same failure, opposite outcome.

heads up ↳
Test the broken path on purpose: unplug your wifi mid-request, or feed the model an empty idea. If your app explodes, your users found the bug before you did. Break it yourself first.
09

Ship it free, get the link, send it to one person. ship

The last 10% that never happens for most people. A project on your laptop isn't real until someone else can open it. Push to GitHub, point Vercel at the repo, paste your key into their environment variables UI (not the repo), and you get a live URL in about two minutes.

ship it 
$ git init && git add . && git commit -m "first draft"
$ gh repo create my-draft-tool --public --source=. --push

# then on vercel.com:
#   New Project → import the repo → add ANTHROPIC_API_KEY
#   in Settings → Environment Variables → Deploy

✓ https://my-draft-tool.vercel.app  — live, shareable, free tier

Then do the part that actually matters: send the link to one person who fits the use case and watch them use it without explaining anything. Every place they hesitate is your real next step — not the feature you imagined, the friction they hit. That's how an afternoon project becomes a second one.

try it ↳
Set the key in Vercel's environment variables, never in the code. Same rule as step 4, one layer up: the platform holds the secret, the repo stays clean enough to make public.
