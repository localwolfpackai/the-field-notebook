Context before code — how I stopped re-prompting and started directing.

The recent notebooks were about getting the model to build things. This one is about getting it to build the right thing the first time. Nine moves for setting up context so the AI shows up already knowing the brief — the shift from operating it like a tool to directing it like a teammate. Learned the slow way, over five months of session logs.

—Lupo · The Mess is the Method
Read · ~13 min Surface · any agent (Claude Code, Cursor, Gemini) Assumes · you've prompted a model into a corner once Voice · open-notebook, casual

For my first few months with these tools I treated the model like a vending machine. Type a prompt, get a result, the result is wrong, type a better prompt. Repeat until tired. It worked, kind of, the way pushing a stalled car works — it moves, but you're the engine.

The thing that actually changed my output wasn't a smarter prompt. It was realizing the prompt was the wrong unit. The model wasn't missing instructions — it was missing context. What I'm building, who it's for, what stack, what's already decided. I'd been re-explaining the project from scratch every single session like a goldfish with a keyboard.

Context-Driven Development is the fix, and the name is bigger than the idea. It's just this: write down the durable stuff once, in files the model reads automatically, and spend your prompts on the work instead of the recap. Below are the nine moves that got me there. Top of the list is where I'd start if I were doing it again from zero.

01

Context precedes code — define what & why before how. mindset

This is the whole philosophy in one line, so I'll put it first. Before you ask a model to write a single function, the model should be able to answer: what are we building, who is it for, and what have we already decided? If it can't, you're going to spend your session re-deciding things you already settled — out loud, in chat, where they evaporate the moment the window closes.

The vending-machine loop

"build me a login page" → it picks a stack → wrong stack → "no, use Next" → it picks a style → wrong style → "match my brand" → what brand? → you paste tokens → next session, all forgotten.

The context loop

stack + brand + goals live in a file the model reads first → "build the login page" → it already knows Next, your tokens, your conventions → you review, not re-explain.

the prompt was never the unit. the project is.

02

The three context files — WHAT, HOW, WITH-WHAT. context

You don't need a documentation framework. You need three short files that answer three questions, dropped where your agent looks automatically (CLAUDE.md, AGENTS.md, .cursor/rules, a repo README — whatever your tool reads on its own). Keep each one under a page. Concrete beats complete.

the three files 
product.md      # WHAT & WHY — vision, users, core features, success metric
guidelines.md   # HOW we talk — voice, terminology, copy + error conventions
tech-stack.md   # WITH WHAT — languages, deps + versions, deploy target, test setup

The trick that makes this real instead of busywork: each file has an "update when" rule at the bottom. tech-stack.md updates when you add a dependency. product.md updates when the goal shifts. That one line is what keeps them from rotting into lies.

try it ↳
Open the project you're in right now. Write the tech-stack.md in five minutes — just list what you're actually using and the versions. Next session, watch the model stop guessing your framework. That's the cheapest win in this whole notebook.
03

Write a spec, not a prompt — requirements + acceptance criteria. context

A prompt says "build the thing." A spec says "build the thing, here's done." The difference is acceptance criteria — the checklist that lets the model (and you) know when to stop. Without it, the model guesses what "done" means, and its guess and yours rarely match.

spec-for-a-work-unit.md 
# Feature: email capture on the landing page

## Requirement
Visitors can submit an email; it persists; they see confirmation.

## Acceptance criteria
- [ ] Empty / malformed email shows an inline error, no submit
- [ ] Valid email writes to the store and clears the field
- [ ] Success state is announced to screen readers
- [ ] Duplicate email is a friendly message, not a 500

## Out of scope
- double opt-in, analytics events (next unit)

The out of scope block does as much work as the criteria. It's how you stop the model from helpfully building four features when you asked for one. Scope creep is just unstated boundaries — so state them.

heads up ↳
Keep specs to one work unit. A spec that covers "the whole app" is a product doc, and the model will treat it like wallpaper. Small spec, clear done, ship, next spec.
04

Plan in phases the model can check off. context

Once the spec exists, ask the model to turn it into a phased plan before writing code — then make it work the plan, one phase at a time, pausing for your nod between phases. This is the single biggest quality lever I found. A model that plans first writes code that fits together; a model that dives straight in writes code you refactor later.

Phase 0 Context files exist & current
→
Phase 1 Spec reqs + acceptance
→
Phase 2 Plan phased tasks
→
Phase 3 Implement one phase, then pause

The literal prompt I use: "Don't write code yet. Read the spec, then give me a phased plan with a checkbox per task. I'll approve, then you do phase one and stop." Costs one extra round-trip. Saves three.

05

Make context a living artifact, not a launch ritual. mindset

The failure mode isn't skipping the context files — it's writing them once, feeling productive, and never touching them again. Three weeks later they describe a project that no longer exists, and now they're worse than nothing because the model trusts them.

The fix is a habit, not a tool: when a decision changes, change the file in the same breath. Switched from Postgres to SQLite for the prototype? That's a one-line edit to tech-stack.md right now, not "later." Treat context like code — it gets committed, it gets reviewed, it drifts if you let it.

try it ↳
Add one rule to your agent's instructions: "When we make a stack or product decision in chat, update the relevant context file before moving on." Now the upkeep rides along with the work instead of becoming a chore you'll never do.
06

Greenfield vs. brownfield — two different context jobs. context

Starting fresh and inheriting a codebase need opposite first moves, and mixing them up is where a lot of frustration comes from.

Greenfield

You're inventing the context. Write product.md first — decide what and why before the model talks you into a stack. The risk here is the model deciding for you.

Brownfield

The context already exists in the code — you just have to extract it. Ask the model to read the repo and draft the three files for you, then correct them. The risk here is assuming, not reading.
brownfield bootstrap 
# let the model do the archaeology, then you edit
> Read this repo. Draft tech-stack.md from what you actually find —
  real deps and versions from the lockfile, not what you'd expect.
  Flag anything you're unsure about instead of guessing.

That "from the lockfile, not what you'd expect" clause matters. Left alone, a model will confidently document the stack it assumes a project like yours uses. Point it at the evidence.

07

Operating → directing — the shift the whole thing is for. mindset

Here's the part that took me five months to feel. Early on, I was operating the model — hands on the keyboard, steering every turn, the bottleneck in my own loop. The context files quietly changed the job. Once the model knew the project, I stopped steering and started directing: setting intent, reviewing output, sending it off again.

Concretely, that looked like going from one careful conversation at a time to handing off whole work units — "here's the spec, here's the plan, go" — and spending my attention on judgment instead of typing. Same tool. The difference was entirely in how much it already knew before I asked.

Operating

You explain the project every session · you catch every wrong assumption live · output quality tracks your patience that day · you are the engine.

Directing

The project explains itself · assumptions are caught by the files · output quality tracks the context, not your mood · you are the editor.

you don't get faster by typing faster. you get faster by repeating yourself less.

08

The daily experiment habit — one small test, written down. mindset

None of the above arrived as a theory. It came from doing one small thing with these tools nearly every day and keeping notes on what stuck. A throwaway script, a tiny local test, a "what happens if I phrase it this way" — cheap, low-stakes, documented. The notes are the point. A trick you discovered and didn't write down is a trick you'll rediscover from scratch next month.

~/notes/2026-06-05.md 
# today's experiment
Tried: phased-plan-then-pause prompt on the email-capture unit.
Result: model stopped after phase 1 cleanly, asked before phase 2. Good.
Keep: "do phase one and stop" is the magic phrase.
Drop: asking for the whole plan AND code in one message — it ignores the pause.

# tomorrow: try the same pattern with a brownfield repo

Four lines. Tried / result / keep / drop. Do that daily for a month and you have a personal playbook nobody could have written for you, because it's calibrated to exactly how you work.

try it ↳
Start the file today, even if today's experiment is just reading this notebook and trying move #2. Tried / Result / Keep / Drop. That's the entire format. Future-you will thank present-you.
09

Archive, never delete — the guardrail I earned the hard way. safety

I'll close on the least glamorous one, because it's the one that cost me real work before it became a rule. Give a capable model a cleanup task and it will be helpful — sometimes by deleting files it decided were duplicates, or wiping a directory it judged stale. Helpful and wrong is the worst combination, because it moves fast.

What I let happen once

"clean up the duplicates" → the model found ~128 files it was sure were redundant → deleted them → several weren't. Recovery: not fun.

The rule now

Destructive ops move to _archive/, never rm. Anything with a numbered name gets archived before it's touched. Confirm before anything irreversible.

This belongs in your context files too. One line in the instructions — "prefer archive over delete; confirm before any destructive action" — and the model inherits the lesson so you don't have to relearn it. The best context isn't just what to build. It's also what never to do.

heads up ↳
For the hard guarantees — "never delete X," "never touch credentials" — a sentence in a context file is a preference, not a lock. If it must always happen, enforce it at the tool layer (a hook, a permission rule), not in prose the model can reason its way around.
