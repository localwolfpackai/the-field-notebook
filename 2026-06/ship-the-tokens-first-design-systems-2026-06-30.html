Ship the tokens first — author the design system before you let the model touch a single component.

You ask for a “nice, modern landing page” and get AI slop — because the model is inventing a padding value, a blue, a font size per div, and none of them agree. The fix is boring and it works: make it write the tokens first — one small JSON contract of color scale, type ramp, spacing, radius, motion — then build every component against that contract. Ten moves to a UI that looks made, not auto-spat. The knob below is live — drag it and watch every component in the card move together.

The tell of an AI-generated UI isn't ugliness — it's disagreement. One card has a 16px radius, the next has 8. The hero blue is #3B82F6; the button blue is #2563EB; the link blue is something else again. Padding is 12px here, 20px there, 14px for no reason at all. Nothing is wrong, exactly — it's that nothing was decided. The model made a fresh style choice for every element and never checked its own earlier choices.

Designers solved this decades ago with a design system: decide the values once — the color scale, the type ramp, the spacing steps, the corner radii — and then every component just references them. A button doesn't invent a blue; it reaches for --accent. A card doesn't guess a gap; it uses --space-4. The model is fully capable of working this way. It just won't unless you make the system the first thing it produces.

So flip the order. Don't say “build me a landing page.” Say “first, author the design tokens as JSON; show me only that.” Approve the contract, then ask for components. Every div now snaps to the same grid, because the grid existed before the div did. Ten moves below to run it on purpose — on Claude Artifacts, on Gemini, or in Claude Code.

01

Name the slop — it's disagreement, not ugliness. read

Before you can prompt your way out of AI slop you have to see it correctly. It's rarely that a single element looks bad. It's that the elements don't agree: three shades of the “same” blue, four unrelated radii, spacing that lands on 11px and 19px and 26px like it was scattered. The eye reads that incoherence as cheap long before it can name why.

Luis P (Vol. 27 is the companion read) puts it well when he lines Claude and Gemini layouts side by side: the models that feel “designed” are the ones being consistent about warmth, padding, and grid. Consistency is the whole trick, and consistency comes from a shared source of values — not from asking nicely for “polish.”

slop

Decided per-div — every element picks its own values. Button blue ≠ hero blue. Card radius 16, input radius 8. Gaps at 12 / 14 / 20 with no rule. Looks “fine” in isolation, incoherent as a set.

system

Decided once — every element references the same tokens. One --accent, one radius scale, one spacing step. Nothing invents; everything reaches. The set reads as one hand made it.

02

Make tokens the first deliverable — not the page. setup

This is the entire move, and it's an ordering trick. Instead of asking for the artifact, ask for the system that the artifact will be built from — and ask for only that. You want the model to stop and hand you a small JSON object before it has written one line of markup. Approving that object is you doing the one job that's actually yours: taste.

prompt — the tokens-first opener (paste into Claude or Gemini)
# DON'T say this:
"Build me a modern landing page for a productivity app."

# Say this instead — stage 1, tokens only:
"Before writing any UI, author a design token contract as JSON:
  - a color scale (accent + neutrals, light + dark)
  - a type ramp (5 steps from a base and a ratio)
  - a spacing scale (an 8pt grid, 6 steps)
  - a radius scale (3 steps)
  - motion (one duration, one easing)
Output ONLY the JSON. No components yet. Wait for my approval."
try it
The magic words are “output only the JSON” and “wait for my approval.” They stop the model's reflex to helpfully build the whole page in one shot — the exact reflex that produces slop. You've turned one big vague ask into two small precise ones.
03

The five tokens that carry the load. design

You don't need the 400-variable enterprise system. Five families do ~90% of the work, and every component you'll ever ask for reads from them. Get these five decided and coherent and the UI has a spine.

tokens.json — the contract the model returns in stage 1
{
  "color": {
    "accent":  "oklch(0.55 0.16 264)",   # one hue, one truth
    "ink":     "oklch(0.20 0.01 60)",
    "paper":   "oklch(0.98 0.01 85)"
  },
  "type":   { "base": 16, "ratio": 1.32 },  # a ramp, not sizes
  "space":  { "unit": 8, "steps": [4,8,16,24,40,64] },
  "radius": { "sm": 6, "md": 12, "lg": 18 },
  "motion": { "dur": "0.2s", "ease": "cubic-bezier(.22,1,.36,1)" }
}
try it
Ask for the colors in OKLCH, not hex. OKLCH is perceptually uniform, so “same lightness, different hue” actually looks the same — which is exactly how you build a scale that doesn't have one muddy step. It's the format this whole notebook is written in.
04

Build a scale, not one color. system

The single most common slop tell is a lonely accent color with no relatives. Real systems have a scale — the same hue at a run of lightness steps — so a hover state, a wash background, a border, and a pressed state are all obviously the same color, dimmed or lifted. Ask for the scale explicitly or the model gives you one blue and then improvises the rest.

prompt — turn one hue into a usable scale
"From the accent hue, generate a 6-step scale by varying ONLY
 lightness in OKLCH — keep chroma and hue locked. Label them
 50 / 100 / 300 / 500 / 700 / 900. 500 is the base accent.
 Use 100 for washes, 700 for hover, 900 for pressed text."

# you get back a coherent family, e.g.:
accent-100: oklch(0.93 0.05 264)   # wash / chip bg
accent-500: oklch(0.55 0.16 264)   # the button
accent-700: oklch(0.42 0.16 264)   # hover / link ink
heads up
If you let it vary chroma and hue too, the “scale” drifts — step 300 leans teal, step 700 leans indigo, and you're back to three blues that don't agree. Lock hue, lock chroma, move only lightness. That one constraint is what makes it a scale instead of a mood board.
05

Ramp the type, step the space — on an 8pt grid. system

Font sizes should come from a ratio, not vibes. Pick a base (16px) and a ratio (1.25 “major third” is safe; 1.33 is punchier) and every heading is base × ration. Spacing works the same way: pick an 8pt unit and only ever use multiples of it. Now every gap and every heading is a derived value, and derived values can't disagree.

ramp

Base 16 × 1.32 — 16 → 21 → 28 → 37 → 49. Five steps, one ratio. The relationship between any two sizes is constant, so headings feel like a family instead of five arbitrary numbers.

spacing

8pt grid — 4 · 8 · 16 · 24 · 40 · 64. Every margin, gap, and pad snaps to a step. No 11px, no 19px. The rhythm is what makes a layout feel engineered rather than nudged-by-hand.

no magic numbers — if a value isn't on the grid or the ramp, it's a bug.

06

Approve the contract before any component exists. design

This is where you earn your keep. The model just handed you a small JSON object — that's the entire design of the product, compressed. Read it. Nudge it in plain language: “accent's too cold, warm it 20 degrees,” “bump the ratio to 1.4, I want more drama in the headings,” “tighten radius to 8, this should feel sharper.” Iterate on the contract, which is cheap, not on rendered pages, which is slow.

the approval loop — plain-language nudges on the JSON
you  ▸ warmer accent, tighter corners, one notch more spacing.
ai   ▸ updated: accent hue 264 → 40, radius md 12 → 8, unit 8 → 8 (steps up one).
you  ▸ perfect. lock it. NOW build the hero + pricing cards
        using ONLY these tokens. No new colors, no off-grid spacing.
try it
Say “lock it” explicitly, then “using ONLY these tokens.” You're converting an approved spec into a hard constraint for stage 2. The model now has a rubric to build against instead of a blank canvas to improvise on — and improvisation was the slop.
07

Ban magic numbers — reference a token or don't ship it. system

Stage 2 is where discipline slips: the model builds three clean components off the tokens, then quietly drops a margin-top: 13px or a #eee border because it felt right in the moment. That one raw value is the crack that spreads. Put the rule in the prompt as a hard negative constraint, the way you'd constrain a coding agent (Vol. 18).

CSS — every value points back at the contract
:root {
  --accent: oklch(0.55 0.16 264);
  --radius-md: 12px;
  --space-3: 16px;  --space-4: 24px;
}
.card {
  border-radius: var(--radius-md);      # not 12px
  padding: var(--space-4);            # not 24px
}
.card .btn {
  background: var(--accent);          # not #6d5ef0
  margin-top: var(--space-3);
}
# the point: change the token, the whole UI follows. that's a system.
heads up
Watch for the sneaky ones: a box-shadow with a hand-picked blur, a line-height: 1.45, a one-off gap. Shadows, line-heights, and durations are tokens too. If it's a number that affects how it looks, it belongs in the contract.
08

Give it a soul — the vibe words that steer the tokens. design

A coherent system can still be generic. Coherence kills slop; character is what's left to add. The lever is the adjectives you feed stage 1 — and, per Vol. 27, Claude and Gemini lean different directions, so the same words land differently. A few that reliably move tokens in a real direction:

Say thisWhat it moves in the tokensResult
“editorial, warm”serif display, low chroma, generous line-height, cream papercalm, human
“dense, technical”tight spacing steps, small ramp ratio, mono accents, cooler neutralsdata-forward
“punchy, product”high-chroma accent, bigger ratio, larger radius, bold weightsenergetic
“quiet, premium”near-neutral accent, wide spacing, subtle shadows, restraintexpensive
“modern & clean”nothing — it's a null instruction the model averages awayslop

"modern and clean" means nothing — give it a direction with an edge.

09

Reuse the tokens across screens — one contract, many pages. system

The payoff compounds the moment you build a second screen. Because the design lives in one small object, the settings page, the dashboard, and the marketing site all read from the same tokens — so they look like one product instead of three freelancers. Paste the approved tokens.json back in as the header of every new request. It's the same stable-prefix discipline as prompt caching (Vol. 30): the system is the part that doesn't change.

prompt — carry the contract into every new screen
"Here is the approved design contract (do not change it):
<paste tokens.json>

Now build the DASHBOARD using only these tokens. Same accent
scale, same 8pt spacing, same radius set, same type ramp.
Match the visual language of the landing page exactly."
try it
Keep tokens.json in a file you own, not just in a chat. It's the single most reusable asset in the whole project — the thing that makes screen #7 as coherent as screen #1 without you re-deciding anything. This is exactly the DESIGN.md habit, in machine form.
10

Verify — grep for the raw hex. ship

Don't trust that the model held the line — check it, the way you'd verify any output on a rubric (Vol. 24). The test is mechanical and brutal: search the generated code for raw color literals and off-grid numbers. A clean token-based UI has almost none outside the :root block. Every hex or rando-pixel you find in a component is a place the system leaked.

verify.sh — hunt raw values outside the token block
# any hex colors hiding in components?
$ grep -nE '#[0-9a-fA-F]{3,6}' app.css | grep -v ':root'
(no output = every color came from a token ✓)

# any spacing that isn't a multiple of 8 or 4?
$ grep -oE '[0-9]+px' app.css | sort -u
4px  8px  12px  16px  24px  40px  64px   # all on-grid ✓
13px                                    # <-- the one leak. fix it.
try it
Found a leak? Don't hand-fix the 13px. Feed the grep output back to the model: “these values violate the token contract — replace each with the nearest token.” You're closing the loop the same way an eval gate does — the machine made it, the machine fixes it, you just hold the standard.
