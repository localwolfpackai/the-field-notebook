Give the agent hands — eleven moves for wiring MCP into your real tools.

We taught the agent to plan without guessing and to build a frontend in an afternoon. But a model that can only talk about your Gmail, your repos, your Figma file is still a very smart person locked in a room. MCP is the door. This notebook is the part nobody explains: the mental model, the setup, and the guardrails — learned by actually running a dozen connectors at once.

—Lupo · The Mess is the Method
Read · ~13 min Surface · Claude / Cursor + MCP Assumes · you've talked to an agent before Voice · open-notebook, casual

For months I treated my AI like a brilliant intern with no badge. I'd ask it to draft a reply, then copy-paste from Gmail. Ask it to check a PR, then alt-tab to GitHub and read the diff back to it like a bedtime story. The thinking was great. The reaching was all me. I was the agent's hands.

MCP — the Model Context Protocol — is the thing that ends that. It's a small, boring standard with a huge payoff: one common plug so an agent can reach into a real tool, read what's there, and act. Think USB-C for AI. Once a connector is plugged in, the model stops asking you to fetch things and just… fetches them.

This isn't theory for me. As I write this, the agent on the other side of the screen has live connectors into GitHub, Figma, Sanity, Gmail, Calendar, Vercel, Box, and my actual Mac. That's the material below. Eleven moves, from "what even is this" to "don't let it email your boss by accident." The closer to the top, the sooner you'll feel it.

How a request actually travels.

you "Draft a reply to the latest invoice email."
→
the agent decides it needs Gmail picks the right tool
→
mcp server Gmail connector reads the thread, returns it

The agent never touches Gmail directly. It speaks one standard language to an MCP server — a tiny program that knows how to talk to Gmail on its behalf. Swap "Gmail" for "GitHub," "Figma," or "your filesystem" and the picture is identical. That's the whole idea: the model learns one protocol, and every connector that speaks it just works. No custom glue per app.

01

The mental model: MCP is USB-C for your AI. concept

Before USB-C, every device had its own cable. Your camera, your phone, your mouse — a drawer full of incompatible plugs. USB-C made one shape work for everything. MCP is that, for AI tools.

Without it, every "let my AI use tool X" integration was a custom, brittle, one-off. With it, anyone can ship a connector once, and any MCP-aware agent — Claude, Cursor, VS Code, whatever comes next — can use it. The protocol is open. That's why the ecosystem went from a handful of servers to thousands in about a year.

You don't need to understand the wire format any more than you need to understand USB-C's pin layout to charge your laptop. You need exactly one sentence: an MCP server exposes a tool's abilities; your agent calls them. Hold that and the rest is plumbing.

try it ↳
Next time your agent says "I can't access that, please paste it" — don't paste. Ask: "is there an MCP connector for this?" Half the time the answer is yes and you've been doing manual labor for nothing.
02

Three words to know: tools, resources, prompts. concept

Every MCP server can offer three kinds of things, and knowing which is which saves a lot of confusion the first week.

tools
Verbs the agent can do. create_issue, send_email, query_documents. This is the action layer — the part with consequences.
resources
Nouns the agent can read. A file, a calendar, a doc. Context it pulls in, no side effects.
prompts
Canned workflows the server suggests. Pre-baked recipes like "review this PR" you can trigger by name.

The line that matters: resources are safe, tools have teeth. Reading your calendar can't hurt you. A tool named delete_event can. We come back to this hard in moves 6 and 7 — it's the difference between a connector that helps and one that surprises you.

03

Your first connector: the click-to-connect path. setup

Forget the terminal for your first one. The big tools now ship hosted ("remote") MCP servers you connect with an OAuth click — same flow as "Sign in with Google." No install, no token files, no JSON. Inside Claude or Cursor you open the connectors panel, pick the service, approve the login, done.

This is the path I'd start anyone on. GitHub, Figma, Notion, Vercel, Linear, Sentry — most have an official hosted server now. The hosted ones also handle their own auth refresh, so you're not babysitting expired tokens.

the click path (no terminal) 
# in Claude / Cursor / your agent app:
Settings → Connectors → Browse
  → pick "GitHub"
  → "Connect" → approve OAuth in browser
  → done. the agent now sees github tools.

# verify it took:
you › "list my 3 most recently updated repos"
→ agent calls search_repositories, returns them
heads up ↳
Hosted servers are easiest but they route through someone else's infrastructure. For anything sensitive (a private client repo, internal docs) check who hosts it — prefer the official vendor server over a random community proxy. Move 8 has the rule.
04

claude mcp add — local servers, one line. setup

When you want the agent to touch your machine — the filesystem, a local Postgres, a script — you run a local ("stdio") server. The CLI makes this a one-liner. No editing JSON if you don't want to.

terminal · claude mcp 
# add the filesystem server, scoped to one folder
$ claude mcp add files -- \
    npx -y @modelcontextprotocol/server-filesystem ~/Agents

# add one with a secret, passed as an env var (don't hardcode)
$ claude mcp add github --env GITHUB_TOKEN=$GH_TOKEN -- \
    npx -y @modelcontextprotocol/server-github

# see what's wired up + whether it's connecting
$ claude mcp list
files    ✓ connected
github   ✓ connected

# inspect or remove one
$ claude mcp get github
$ claude mcp remove github

The -- separator matters: everything after it is the command that launches the server. npx -y means "fetch and run without a global install," which is why most quick-starts use it.

scope the filesystem server to a folder, never your whole home dir. you'll thank yourself.

05

The config file, demystified. setup

Under the click-paths and one-liners, it all lands in a plain JSON file. Knowing its shape means you can read, debug, and copy-paste a setup someone shares without it being magic. Every MCP-aware app uses the same skeleton.

mcp config (the shape is universal) 
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "~/Agents"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}

That's the entire vocabulary: a name, a command to launch it, its args, and optional env for secrets. Remote servers swap command for a url + auth. When a tutorial hands you a JSON blob, this is what you're pasting into — and now you can read it instead of trusting it blind.

heads up ↳
Write secrets as ${GITHUB_TOKEN} referencing an environment variable — never paste the raw token into a config you might commit or share. A leaked token in a screenshot is the classic day-one mistake.
06

Read-only first. Earn the write access. safety

The single habit that's saved me the most grief: when you add a new connector, use it read-only for a few days before you let it write anything. Let it list your issues, read your calendar, summarize a thread. Watch how it picks tools. Build trust before you hand it a pen.

Most servers expose far more than you need on day one. The filesystem server can be added in read-only mode. GitHub doesn't need merge_pull_request just to help you triage. Start with the nouns (resources), graduate to the safe verbs, and only then the consequential ones.

day 1 · read
list, get, search, read. Zero side effects. Just looking.
week 1 · soft write
create_draft, create_issue, create_branch. Reversible, visible, low blast radius.
earned · hard write
send, merge, delete, deploy. Only once you trust the tool selection.

a draft you review beats an email you can't un-send. always.

07

The "write" actions that actually bite. safety

Here's the lesson the hard way so you don't have to live it. The dangerous tools aren't the obviously scary ones — you're already careful with delete. The bites come from the helpful-sounding ones the agent reaches for a little too eagerly.

send_email
Reaches a human instantly and can't be recalled. Prefer create_draft and review.
merge_pull_request
Changes shared state. One confident-but-wrong merge can ruin an afternoon for a team.
deploy_to_vercel
Pushes to a URL real people hit. Great when intended, rough when assumed.
create_event / respond_to_event
Pings other people's calendars. Outward-facing the moment it fires.

The rule I keep taped up: anything outward-facing or hard to reverse gets a confirm-first leash. Most agent apps let you set tools to "ask every time" instead of auto-run. Do that for the four above on day one. The friction is two seconds; the alternative is an email to a client that starts with "Hi {{first_name}}."

heads up ↳
A connector with both read and write to the same account is a real attack surface: a poisoned doc the agent reads can contain instructions that trigger a write. This is "prompt injection," and it's why read-only-by-default isn't paranoia — it's the seatbelt.
08

Scope the keys, not the vibes. safety

When a connector wants a token, your instinct is to grab the easiest one — the all-powerful personal access token that does everything. Resist it. The whole game is least privilege: give the connector exactly the access the job needs and not one scope more.

scoping a github token, the right way 
# BAD — classic token, every scope, never expires
[x] repo   [x] admin:org   [x] delete_repo   [x] workflow ...

# GOOD — fine-grained token, one repo, read + issues only
Repository access:  only "humanlup-site"
Permissions:        Contents (read)  ·  Issues (read/write)
Expiration:         90 days

Three habits that compound: fine-grained over classic tokens, one repo / one scope over org-wide, and an expiration date so a leaked key dies on its own. If a connector breaks because the token's too narrow, widen it deliberately — that's the system working, not failing.

a token that can do everything is a key that opens every door. don't hand the agent the master.

09

Stack connectors into one real workflow. workflow

One connector is a feature. Several connectors is where it stops feeling like a chatbot and starts feeling like a teammate — because the agent can chain them in a single ask, no alt-tabbing.

This is a real shape I run for HumanLup client work. Notice every step is a different connector, and the human (me) only shows up at the gate that matters:

one prompt, four tools, one human gate 
you › "Pull the homepage copy from our Sanity dataset, draft a
       revision in our brand voice, open a PR on the site repo,
       and draft me an email to the client summarizing it."

1. sanity      → query_documents   (read the live copy)
2. filesystem  → read brand/voice/   (load the voice rules)
3. github      → create_branch + PR  (soft write, reviewable)
4. gmail       → create_draft        (NOT send — i review it)

agent › "PR #41 opened, email draft saved. Both await your OK."

Four tools, one sentence, and the only thing left for me is judgment — read the PR, read the draft, hit go. That's the operating-to-directing shift the whole notebook keeps circling. MCP is the wiring that makes it literal.

try it ↳
Pick two connectors you already have and write one prompt that needs both — "find the issue I opened yesterday and add it to my calendar for Friday." If it chains them without you copy-pasting, you've felt the point of this entire entry.
10

When NOT to reach for MCP. concept

Counter-intuitive, but the people who get the most out of MCP are the ones who don't bolt a connector onto everything. More tools in the agent's hands means more for it to read every turn — which means slower, pricier, and more likely to pick the wrong one. Connectors aren't free; each one is context tax.

My actual decision order, lifted straight from how I work: a quick ask > a native feature > a slash command > a one-line shell pipe > a connector. Reach for MCP only when the task genuinely needs to touch a live system you can't easily paste in. If you can copy three lines and move on, copy three lines.

one-off lookup
Just paste it. A connector for a thing you'll do once is overhead.
daily, live, multi-step
This is the MCP sweet spot. Wire it.
sensitive + no audit trail
Think twice. If you can't review what the agent did, don't grant the write.

the goal is fewer moving parts that do more, not more parts.

11

Where the connectors live — the registry. workflow

You don't have to know what exists. There's now an open MCP registry — a searchable index of available servers — plus curated directories. Before you build a connector or hand-roll an integration, search first. The thing you need almost certainly already exists.

finding a connector 
# the official open registry (browse / API)
registry.modelcontextprotocol.io

# curated lists worth a bookmark
github.com/modelcontextprotocol/servers   (reference servers)
github.com/punkpeye/awesome-mcp-servers    (community index)

# inside a capable agent, just ask:
you › "is there an MCP server for Linear? suggest one."

The reference servers (filesystem, fetch, memory, git) are the ones to read if you ever want to write your own — they're small, official, and deliberately boring. But that's a later notebook. For now: connect, scope, read-only first, and let the agent start reaching for itself.

heads up ↳
The flip side of "anyone can publish a connector" is "anyone can publish a connector." Before installing a community server that wants your tokens, check the stars, the author, and that the source is open. Prefer official vendor servers for anything that holds real credentials.
